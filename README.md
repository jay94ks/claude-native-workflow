# claude-native-workflow v2

Claude와 함께 쓰는 문서/워크플로우 관리 시스템 - 단일 설치형, DB 기반
문서 관리, 커스터마이즈 가능한 타입 체계, 실시간 메시징/변경 전파.

이전(3단계 등급 구분) 구현은 [`concept`](../../tree/concept) 브랜치에
그대로 보존되어 있다. 이 브랜치(`main`)는 그 경험을 바탕으로 완전히
새로 설계한 v2 구현이다 - 설계 배경과 전체 아키텍처는 계획 문서
(대화 세션에서 작성, 저장소에는 아직 커밋 안 됨 - 진행 상황은
[DESIGN-NOTES.md](DESIGN-NOTES.md) 참고)를 참고.

## 이번 라운드: 여러 줄 입력 + 다이얼로그 표시 순서 수정

코멘트 작성·질문 등록·답변/승인 메모 입력창이 한 줄짜리 입력창에서
여러 줄 입력 가능한 textarea로 바뀌었다(줄바꿈도 그대로 보임). 칸반
카드 다이얼로그에서 문서 참고 링크를 눌렀을 때(또는 그 반대) 새로 뜬
다이얼로그가 기존 다이얼로그에 가려 안 보이던 문제를 고쳤다 - 이제
어떤 순서로 몇 단계를 중첩해 열어도 항상 마지막에 연 다이얼로그가
맨 위에 온다.

## 이번 라운드: 변경 추적 리스트화 + Q&A 선택지 + 콤보박스/사이드바/피커 개선 + 코멘트 상태

변경 추적 화면의 git diff가 파일별 카드(접기/펼치기, +N/-M 배지)로
쪼개져 여러 파일이 바뀐 커밋도 한눈에 구분된다(문서 리비전 diff도
같은 카드 스타일). AI가 질의에 선택지를 제안할 수 있고(예: "토큰
버킷 vs 슬라이딩 윈도우" - 각 옵션의 부가 설명까지), 클릭하면 답변
입력칸에 그 값이 채워진다. 상태 전이 같은 콤보박스는 옵션에 라벨만
보이고 긴 설명은 아래 별도 텍스트로. 좌측 사이드바 문서 목록과 소스
파일 선택 다이얼로그 둘 다 전체를 한 번에 안 불러오고 필요한 만큼만
불러오도록(무한 스크롤 / 디렉터리 단위 지연 로드) 바꿨다. 코멘트는
open/closed/solved/etc 4단계 상태를 갖고, 작성자 본인만 바꿀 수
있다.

## 이번 라운드: 문서 탭 분리(보기/질의응답) + 소스 코드 뷰어 개편

문서 화면이 [보기]/[질의·답변] 두 하위 탭으로 나뉘었다 - 질의/답변이
많아질수록 문서 본문을 한참 내려가야 했던 문제를 해결하려고, 질의/
답변만 별도 탭(페이지네이션+검색+최신순)으로 옮겼다. 코멘트는 탭도
인라인도 아닌 별도 다이얼로그로 뺐다(문서/소스 코드/칸반 카드 공통
`TargetPanelDialog`). 소스 코드 뷰어는 텍스트 파일을 "보기"(읽기 전용)/
"편집" 모드로 분리하고(편집 버튼을 눌러야 Monaco가 편집 가능해짐),
이미지/영상 파일은 편집 없이 브라우저에서 바로 미리보기만 한다(블랙
리스트 없이 화이트리스트 두 종류만 분류 - 그 외는 전부 텍스트로 열되,
"원본 다운로드" 버튼이 항상 있어 내용이 깨져 보여도 원본 그대로 받을
수 있다). 이미지/영상·다운로드는 백엔드 로컬 디스크 캐시(blob sha
기준)에서 raw 바이트로 직접 서빙된다.

## 이번 라운드: 사이드바 검색(범위 선택 + 소스코드 색인 검색)

좌측 사이드바에 검색창이 생겼다 - 키워드 입력 후 엔터/버튼을 누르면
범위 선택 팝업이 뜬다: (1) 이 프로젝트 내에서, (2) 같은 프로젝트
그룹 안의 프로젝트들에서, (3) 같은 팀 안의 프로젝트 그룹/프로젝트
들에서. "소스코드 포함" 체크박스로 문서뿐 아니라 git 저장소의 소스
코드 내용까지 검색 대상에 넣을 수 있다(새 Meilisearch 인덱스로 소스
파일 내용을 색인 - 저장소 연결 시 백필, push마다 증분 동기화, 에디터
저장 시 즉시 동기화). 검색 결과는 항상 실제 멤버십으로 걸러진다 -
그룹/팀 스코프를 골라도 자신이 멤버가 아닌 프로젝트의 내용은 전혀
보이지 않는다. 웹 UI 전용 기능이며, 기존 CLI `docs search`(단일
프로젝트 문서 검색)는 그대로 유지된다.

## 이번 라운드: 코멘트/질의응답 통폐합 + 페이지네이션 + 엔티티 선택기

코멘트와 AI 질의/답변 시스템을 대상 종류에 상관없이 재사용되는 하나의
구조로 통폐합했다 - `Comment`/`Question`이 이제 `targetType: "document"
| "source" | "kanbanCard"` + `targetKey`로 다형화돼 있어, 대상이 하나
더 늘어도(예: 미래의 다른 엔티티) 새 테이블 없이 값 하나만 추가하면
된다(지난 라운드의 `KanbanCardComment`는 이번에 완전히 흡수·삭제됨).

- **모든 코멘트에 편집·삭제** - 문서 코멘트도 이번에 처음 편집이
  가능해졌다.
- **코멘트/질의는 문서·소스 코드 파일·칸반 카드 세 곳 전부** - 소스
  코드 화면에 파일을 열면 그 파일에 코멘트/질의 패널이 같이 뜬다.
- **AI 질의는 `kind`로 [승인 요청(approval)]/[답변 요청(answer)]을
  구분** - 승인 요청은 텍스트가 아니라 승인/거부 버튼(+선택 메모)으로
  답한다. `docs question <trackingCode> <text> [--kind ...]`(문서/
  칸반 카드)와 `docs question-source <projectId> <path> <text>`
  (소스 코드 파일) 둘 다 지원.
- **"이미 존재하는 것을 고르는" 모든 자리가 체크박스 선택기
  다이얼로그로 통일**(범용 `EntityPickerDialog.vue`) - 칸반 카드 근거,
  질문 근거, 개별 문서 접근 권한 대상, 멤버/팀장 추가 대상 사용자,
  문서의 연관 소스 코드까지 6곳 전부 텍스트 직접 입력 대신 목록에서
  체크(검색 가능) - 아직 없는 대상을 가리킬 수 있는 자리(소스 코드
  경로)만 수동 입력을 같이 남겼다.
- **문서/메시지/소스 코드 디렉터리/git 로그에 페이지네이션** - 기존
  CLI/MCP 라우트는 그대로 배열을 반환하고, 웹 전용 페이지네이션
  라우트를 따로 뒀다.

## 이번 라운드: 프로젝트별 칸반 보드

각 프로젝트의 "변경 추적" 탭 옆에 "칸반 보드" 탭이 새로 생겼다 -
"분류(컬럼) → 카드" 구조로 진행 흐름을 추적한다.

- 분류는 설계자가 웹 UI에서 만든다(기본 pending/doing/qa/done 4개로
  시작). 순서 변경은 드래그로, 너무 많아지면 숨길 수 있다 - **분류의
  순서/숨김은 설계자 개인 설정**이라(폴더 개인화 라운드와 같은 정신)
  다른 설계자의 화면엔 영향이 없다.
- 카드는 AI(CLI/MCP `kanban-*` 명령·MCP `kanban_*` 도구)와 설계자
  양쪽 다 만들 수 있다 - AI는 작업 현황에 맞춰 카드를 만들고 분류를
  옮기며, 카드 생성 시 판단 근거가 된 문서를 태깅할 수 있다. **설계자가
  웹에서 만든 카드는 그 즉시 메시지로 알림이 가고 "반드시 진행되어야
  하는 작업"으로 표시된다**(기존 메시지 기능을 그대로 재사용 - 새
  알림 채널을 안 만듦).
- 카드를 클릭하면 근거 문서/받은 지시/코멘트를 다이얼로그로 볼 수
  있다. 코멘트(작성·수정·삭제)는 설계자간 채널이라 문서 코멘트와
  마찬가지로 CLI/MCP엔 노출되지 않는다.
- 카드도 너무 많아지면 개별로 숨길 수 있다(전역 - 컬럼과 달리 개인
  설정이 아니라 보드 전체에 적용).

## 이번 라운드: 홈 대시보드 + 소스코드 연관 + 설계자별 개인 폴더 재설계 + 닉네임

4개 항목을 한 번에 반영했다:

- **홈 = 대시보드**: 프로젝트 "홈" 탭이 최근 변경 문서/최근 코멘트/
  최근 발신 메시지를 각 5건씩 보여주고, 각 섹션의 "더보기"로 전체
  목록(코멘트는 새 `/projects/:id/comments` 화면, 문서는 기존 문서
  탭에 `?recent=1`)이나 기존 메시지 탭으로 이동한다.
- **문서 ↔ 연관된 소스코드**: 문서 에디터에서 git 파일 경로를 직접
  연결해두고 클릭하면 소스 브라우저가 그 파일을 바로 열어 보여준다 -
  `docs link-source/unlink-source/source-links` CLI + 대응 MCP 도구도
  있음(코멘트/폴더와 달리 AI가 쓰는 신호라 CLI/MCP에도 노출).
- **폴더 = 설계자 개인 소유로 재설계**: 이전엔 프로젝트 공통이었던
  문서 정리용 폴더가 이제 **만든 설계자 한 명만의 것**이다 - 같은
  문서를 여러 설계자가 각자 다른 폴더에(또는 아무 폴더에도 안) 넣을
  수 있고, 다른 사람의 폴더는 보이지도 않는다. 프로젝트 멤버면
  viewer 역할도 자기 폴더를 만들고 쓸 수 있다(문서 내용을 안 바꾸는
  개인 정리 기능이라 editor 이상을 요구하지 않음). "문서" 탭에 폴더
  생성용 툴바와 순서(▲▼) 조절이 추가됐다. **브레이킹 체인지** -
  기존 프로젝트 공통 폴더/그 세부 권한 오버라이드 축은 완전히
  폐기됐다.
- **닉네임 + `#N` 자동 넘버링**: 설계자 계정에 닉네임을 설정할 수
  있다(중복 가능, 구분용으로 같은 닉네임 풀 안에서 `#1`부터 자동
  부여, 한번 바꾸면 7일간 재변경 불가). 안 정하면 공통 라벨
  "설계자"도 같은 방식으로 번호가 붙는다(예: `설계자 #3`). 코멘트/
  메시지/질의/리비전/멤버 목록 등 지금까지 내부 ID를 그대로 보여주던
  곳이 전부 `[닉네임 #N]` 형식으로 바뀌었다.

## 이번 라운드: 가이디드 마이그레이션 점검 - Meilisearch write-through 경합 수정

`docs migrate scan/apply`를 `concept` 브랜치의 실제 문서로 점검하다가
세 가지 진짜 버그를 발견해 고쳤다. 가장 중요한 건 **`core/search.ts`의
`indexSyncUpsert()`/`indexSyncDelete()`가 Meilisearch SDK의
`EnqueuedTaskPromise`를 그냥 `await`만 했다는 것** - 이 값은 "색인 작업이
큐에 들어갔다"는 응답이 오면 바로 풀리고, 실제로 색인이 끝났다는 보장이
없다. 문서를 만든 직후 바로 그 문서를 대상으로 다른 쓰기(링크 연결,
상태 전이)를 거는 순간 검색 엔진이 아직 그 문서를 못 찾는 경합이
실제로 재현됐다(마이그레이션처럼 생성을 쉼 없이 연달아 호출하는
경로에서 특히 잘 드러남 - 사람이 명령을 하나씩 치는 보통의 CLI
사용에서는 명령 사이 시간이 충분해 거의 안 보임). SDK가 반환하는
`EnqueuedTaskPromise`의 `.waitTask()`로 실제 처리 완료까지 기다리도록
고쳐 "쓰기 시점에 바로 동기화"라는 이 시스템의 write-through 설계
원칙이 이름값을 하게 만들었다 - 문서를 다루는 모든 쓰기 경로(생성/
저장/삭제)에 영향을 주는 근본적인 수정이라 마이그레이션 외의 일반
사용에도 안정성이 올라간다.

나머지 둘은 Windows PowerShell의 `>` 리다이렉트(README/SKILL.md가
안내하는 정확히 그 명령, `docs migrate scan ... > manifest.json`)가
기본으로 UTF-8 BOM을 파일 앞에 쓰는 데서 비롯됐다 - `migrate apply`가
그 매니페스트를 읽을 때 `JSON.parse`가 깨졌고(에러로 바로 드러남),
옛 문서 파일 자체가 BOM으로 시작하면 `scanDirectory`가 frontmatter를
못 찾아 **에러 없이 조용히 후보에서 빠졌다**(가장 위험한 실패 모드 -
사용자가 파일 하나가 통째로 누락된 줄도 모르게 됨). `cli/migrate.ts`가
읽는 세 지점(스캔 대상 .md, 매니페스트 JSON, apply가 다시 읽는 원본
파일) 전부 BOM을 벗기도록 고쳤다.

## 지금 상태: Phase 0~6 완료 (로드맵 전체)

- Prisma 스키마(PostgreSQL/MySQL/SQLite 3드라이버, 완전 정규화 - JSON
  컬럼 없음)
- 인증(회원가입/로그인/JWT+리프레시 토큰)
- git 자격증명 저장(AES-256-GCM 암호화)
- 팀/프로젝트 그룹/프로젝트 계층(팀 단위는 선택적)
- 커스터마이즈 가능한 문서 타입 체계(DocType/DocStatus/DocStatusTransition) -
  `doctype-create`(프로젝트)/`group-doctype-create`(프로젝트 그룹)/
  `team-doctype-create`(팀)로 원하는 스코프에 타입을 만들고,
  각 스코프 짝의 `*-doctype-status-add`/`*-doctype-transition-add`로
  상태·전이를 정의한다(새 타입은 상태가 0개라 최소 하나는 추가해야
  그 타입으로 문서를 만들 수 있음 - 세 스코프 전부 지원). 그룹/팀
  스코프 타입은 그 그룹/팀 소속 모든 프로젝트가 자동으로 상속받는다
  (project → group → team 순으로 조회, 더 구체적인 스코프가

## 이번 라운드: API 키 3종(팀/프로젝트/개인) 신원 위임 인증

REST API/CLI/MCP/웹 UI 전반에서 로그인 없이 쓸 수 있는 **API 키**
(`cnwk_...`)를 도입했다 - 세 종류 다 "그 키를 만든 설계자의 신원을
그대로 대행"하지만 접근 범위가 다르다: **팀 관리 키**(팀장 전용,
그 팀 소속 모든 프로젝트), **프로젝트 개인 키**(멤버 누구나, 그
프로젝트 하나만), **개인 키**(누구나, 로그인과 동등 - 접근 가능한
모든 프로젝트). 스코프 제한은 라우트 각각이 아니라
`getMemberRole()`/`isTeamAdmin()`/`resolveEffectivePermission()`
같은 핵심 권한 판정 함수 안에서 `AsyncLocalStorage`로 요청 전체에
자동 전파된다(`core/requestScope.ts`) - 문서/폴더/질문/코멘트/메시지/
git 라우트 수십 개를 하나도 안 건드리고도 전부 스코프 제한을 받는다.
팀/그룹 자체를 대상으로 하는 라우트(팀장 등록, 팀·그룹 스코프
DocType 관리, 전역 템플릿 수정)는 애초에 저 함수들을 거치지 않아
QA 패스에서 별도로 발견해 `isTeamAllowedByActiveScope()`/
`isGroupAllowedByActiveScope()`로 막았다(자세한 내용은 DESIGN-NOTES.md
"QA 패스 3회차" 참고). 범위가 있는 키로는 신원 자체를 다루는 동작(프로필 수정, git 자격증명,
팀/그룹/프로젝트 생성, 키 관리 자체)을 할 수 없다(권한 상승 방지).
키 값(secret)은 생성 시 응답으로 **딱 한 번만** 내려주고 DB에는
단방향 해시만 저장해 이후엔 만든 사람 본인도 다시 볼 수 없다. 배제
("삭제"가 아니라 soft revoke)는 행을 남기고 상태만 바꿔 감사 기록을
보존한다. 프로젝트 "설정" 탭 옆 새 "키 관리" 탭(`ProjectKeysManager.vue`),
팀 화면의 "키 관리" 토글(`TeamKeysManager.vue`), 내 정보 화면의
"API 키" 카드(`PersonalKeysManager.vue`)에서 각각 관리한다. 키
관리(`docs key create/list/revoke`)는 CLI 전용이고 MCP엔 없다(auth
register/login과 같은 급의 신원 관리 동작이라 완전성 원칙의 네
번째 의도적 예외).

## 이번 라운드: 설계자 프로필 / 프로젝트 숨김·팀장 / 세부 권한 / 표준 상태 / 메시지 재설계 / Q&A 재정의

- **설계자 프로필 + `[userId]` 참조**(`UserRef.vue`) - 웹 UI 전역(코멘트/
  메시지/질의/리비전/멤버 목록/문서 작성자)의 사용자 참조가 이제 전부
  `[userId]` 태그로 표시되고 클릭하면 프로필(`/users/:id`)로 이동한다.
  프로필 화면에서 본인 email/phone을 입력하고 타인 공개 여부를 선택할
  수 있고(`docs profile set`), 최근 작업 이력(`docs user activity`)도
  보인다(숨겨진 프로젝트의 활동은 멤버/팀장만 봄).
- **프로젝트 숨김 + 팀장**(`docs project-hide`, `docs team-admin-*`) -
  프로젝트를 숨기면 기존 멤버와 그 프로젝트가 속한 팀의 팀장에게만
  계속 보이고, 그 외에게는 목록에서 빠진다. 팀장은 숨김을 해제할 수도
  있다.
- **문서/문서타입/프로젝트 3단계 세부 접근 권한**(`docs access-set/
  access-list`, `AccessControlManager.vue`) - 프로젝트 owner가 협업
  설계자의 읽기/쓰기/삭제를 문서별 > 문서타입별 > 프로젝트 공통 순으로
  제한하거나 예외적으로 넓힐 수 있다. 제한이 적용되면 CLI/MCP 응답에
  `notices` 배너가 붙어 AI가 놓치지 않게 안내한다(같은 메커니즘을
  미확인 질의 안내에도 재사용).
- **표준 상태 코드 6종 고정**(`draft/review/pending/approved/deprecated/
  archived`) - 문서 **분류**(DocType)는 여전히 관리자가 자유 정의하지만,
  문서의 **현재 상태**는 이 6개 표준 어휘로 통일됐다(커스텀 코드/자유
  라벨 입력 폐지). `draft`가 아닌 상태에서 `draft`로는 어떤 경우에도
  전이할 수 없다(정의 자체가 거부됨). `doctype-apply-standard-flow`로
  새 타입에 표준 흐름(6상태 + draft를 제외한 모든 전이)을 한 번에 심을
  수 있다. 문서 에디터의 상태 선택은 자유 텍스트 입력에서 라벨+지침을
  병기하는 콤보박스로 바뀌었다.
- **메시지 대기/기록 분리 + 장애 복구용 조회** - 메시지는 "CLI/MCP가
  읽어갔는가"(`deliveredAt`)를 기준으로 대기/기록으로 나뉜다(CLI/MCP
  호출 자체가 "읽었다"는 뜻 - 웹 UI에서 보는 건 카운트 안 됨). 독립
  화면(`/projects/:id/messages`)으로 분리됐고, 문서 에디터의 "메시지로
  지시" 버튼은 그 문서의 추적 코드를 자동으로 본문에 병기한다(클릭하면
  다이얼로그로 문서 미리보기). `docs message recent`는 상태를 바꾸지
  않는 순수 조회로, 시스템 다운 후 재접속 시 "마지막에 무슨 일이
  있었는지" 확인하는 용도다.
- **질의/답변 재정의: AI가 묻고 설계자가 답한다** - 상태가
  `open`(AI 질의, 답변 대기) → `pending`(설계자 답변 완료, AI 확인
  대기 - 종결 아님) → `resolved`(AI 확인 완료, `docs question ack`)
  3단계로 바뀌었다. 질의 등록 시 판단에 참고한 문서를
  `--refs`로 구조적으로 태깅할 수 있다(`QuestionReference` 조인
  테이블). SKILL.md의 세션 시작 체크리스트에 "pending 확인" 항목이
  추가됐다.
- **코멘트의 AI 격리** - 코멘트는 설계자들끼리만 쓰는 채널이라는 원칙에
  따라 CLI(`comment` 명령군)/MCP(`comment_*` 도구)에서 완전히 제거됐다
  (REST API/웹 UI는 그대로 유지 - "CLI/MCP 명령어 완전성" 원칙의 두
  번째 의도적 예외).
- **문서 읽기/편집 모드 분리 + 다이얼로그 미리보기** - 문서 화면 기본이
  렌더링된 마크다운 읽기 모드로 바뀌었다("편집" 클릭 시 Monaco로
  전환). 메시지/코멘트/질의 본문 속 추적 코드는 전부 클릭 가능한
  링크로 자동 렌더링되고(`TrackingCodeText.vue`/`MarkdownBody.vue`),
  클릭하면 전역 다이얼로그(`DocumentPreviewDialog.vue`)로 그 문서를
  미리 볼 수 있다.
- **문서 정리용 폴더**(웹 전용) - DB에만 존재하는 문서 정리 계층(실제
  git 파일 트리와 무관). 문서/폴더 모두 부모 폴더를 가질 수 있고(중첩),
  쓰기 권한이 있는 설계자만 만들 수 있다(상위 폴더 쓰기 권한 필요 -
  폴더 단위 접근 권한 오버라이드로 세밀하게 제어 가능). **AI(CLI/MCP)는
  이 개념 자체를 모른다** - 코멘트와 같은 원칙으로, 관련 명령/도구/
  응답 필드가 전혀 없다(세 번째 의도적 예외 - "AI가 몰라도 되는 인간
  편의 기능").

**알려진 제한**: `git blame`은 Gitea REST API 자체에 blame 엔드포인트가
없어(1.27 기준, swagger로 직접 확인) 명확한 "지원하지 않음" 에러를
반환한다 - `git log/diff/show`로 변경 이력을 대신 확인한다(자체
호스팅·외부 연동 둘 다 동일 - blame만 플랫폼 자체 한계). "동기화
제안"은 외부(권위) 저장소로 브랜치·PR을 자동으로 열어주지 않는다 -
달라진 파일 내용을 보여주고 내보내는 것까지만 지원, 실제 반영은
설계자가 직접 한다(매 반영이 항상 사람 검토를 거치게 하려는 의도적
설계 - 다음 단계로 자동 PR 생성을 고려할 수 있음). Gitea는 사설 네트워크 호스트로의
웹훅 발송을 기본적으로 막으므로(SSRF 방지), Docker Compose 배포에서
웹훅이 실제로 오려면 `docker-compose.yml`의 `GITEA__security__
ALLOWED_HOST_LIST` 설정이 꼭 필요하다(이미 반영돼 있음 - 직접 겪고
고친 문제). `migrate apply`는 재실행해도 안전하지 않다(같은 매니페스트를
두 번 반영하면 문서가 중복 생성됨 - 실행 전 결과를 확인하고, 실패한
항목만 다시 매니페스트에 남겨 재시도한다) - 대상 DocType/DocStatus가
없으면 자동 생성하지 않고 그 항목만 에러로 보고하며, 옛 시스템의 답변
대기 체크리스트(`reply_pending`)는 본문 텍스트로만 그대로 옮겨지고
Question/Answer로 자동 변환되지 않는다(필요하면 `docs question`으로
다시 등록).

## 실행 방법

### Docker Compose (권장)

```bash
cd backend/docker
cp .env.example .env
docker compose up -d --build
```

`.env`를 채우지 않아도(전부 예시 값 그대로 둬도) 일단 기동은 된다 -
아래 항목별로 "채우지 않으면 무슨 기능이 꺼지는지"를 명시했으니, 필요한
만큼만 채우고 나머지는 나중에 채워도 된다(값을 채운 뒤엔
`docker compose up -d --build`를 다시 실행하면 반영됨).

백엔드는 `:8760`(포트 충돌 시 `.env`에 `BACKEND_HOST_PORT` 지정). 최초
기동 시(계정이 하나도 없으면) 이 시스템 자신의 관리자 계정이
`admin`/`12345678`로 항상 자동 생성된다(로그인 직후 바로 비밀번호를
바꾸는 걸 권장).

#### Meilisearch(검색 엔진) - 어디서 값을 "받아올" 필요가 없다

`MEILISEARCH_API_KEY`는 Meilisearch 사이트에 가입하거나 로그인해서
발급받는 값이 아니다 - **본인이 직접 정하는 비밀번호 같은 것**이다.
`.env`를 열어 `MEILISEARCH_API_KEY=` 뒤에 아무 무작위 문자열이나
채워 넣으면 끝(예: `openssl rand -hex 32`로 생성하거나, 터미널이
어려우면 그냥 길고 남이 못 맞출 문자열을 손으로 입력해도 된다). 이
값을 Meilisearch 컨테이너가 그대로 자기 "마스터 키"로 쓴다 - 별도
대시보드나 설정 화면 자체가 없다. 문서 검색/목록 조회가 전부 이
서비스를 거치므로(핵심 기능), 이 값만은 반드시 채워야 한다.

#### EMQX(실시간 메시징) - Meilisearch와 마찬가지로 대시보드가 필요 없다

`EMQX_API_KEY`/`EMQX_API_SECRET`도 Meilisearch 키와 똑같이 **본인이
직접 정하는 값**이다 - EMQX 대시보드에 로그인해서 발급받는 게 아니다.
`.env`에 이 두 값(및 `EMQX_SERVICE_USERNAME`/`EMQX_SERVICE_PASSWORD`,
`message wait`가 내부적으로 쓰는 전용 계정 - 이것도 마찬가지로
직접 정하는 값)을 채우고 `docker compose up -d --build`로 띄우면 그걸로
끝이다. EMQX 자체는 REST API 키를 이미지가 기본으로 안 만들어주지만,
이 프로젝트의 `docker-compose.yml`이 EMQX의 "부트스트랩 파일" 기능
(`api_key.bootstrap_file`, 실제 `emqx/emqx:5.8` 컨테이너로 동작 검증
완료)으로 `.env`의 두 값을 기동 시점에 그대로 API 키로 등록해준다 -
대시보드 로그인·발급 절차 자체가 필요 없다.

값을 비워두면(기본값) 시스템 자체는 정상 기동하되 실시간 알림(변경
추적 뷰·메시징 패널이 새로고침 없이 갱신되는 것, `message wait` 롱폴)
만 조용히 꺼진 채로 동작한다 - 나중에 값을 채우고 다시 띄우면 켜진다.

**주의**: 컨테이너가 이미 떠 있는 상태에서 `.env`의 이 값들을 바꿨다면
`docker compose up -d --build`만으로는 반영이 안 될 수 있다(부트스트랩
파일 내용이 바뀐 것만으로는 EMQX 컨테이너를 자동으로 재생성하지
않음 - 실측 확인) - `docker compose up -d --force-recreate emqx`처럼
명시적으로 재생성해야 새 값이 적용된다. 최초 설치(컨테이너가 아직
없는 상태)는 이 문제와 무관하게 항상 바로 적용된다.

(참고: EMQX 대시보드는 `http://localhost:18083`, 기본 계정
`admin`/`public`으로 여전히 접속 가능하다 - 부트스트랩으로 만든 키를
직접 눈으로 확인하고 싶거나, 나중에 키를 하나 더 추가하고 싶을 때
같은 용도로 쓸 수 있지만, 최초 설치 시엔 이제 들어갈 필요가 없다.)

#### Gitea(선택 - git 저장소를 이 시스템 안에서 직접 관리하려는 경우만)

git 저장소 연결/이력 조회 기능을 쓰지 않을 거라면 이 절은 건너뛰어도
된다(`GITEA_*` 값을 비워두면 그 기능만 에러를 반환할 뿐 나머지는
정상). 쓰려면 EMQX와 같은 패턴으로 1회성 수동 단계가 필요하다:

1. `http://localhost:3001`(Gitea 웹 UI)에 접속해 설치 마법사를
   완료한다(대부분 기본값 그대로 "설치" 눌러도 된다).
2. 마법사 마지막에 관리자 계정을 만든다(아이디/비밀번호는 본인이
   직접 정함 - 이후 Gitea 저장소는 전부 이 계정 아래 만들어진다).
3. 로그인 후 오른쪽 위 프로필 아이콘 → **Settings** → **Applications**
   로 이동해 **Generate New Token**으로 Personal Access Token을
   발급한다(권한은 최소 `repository`와 `user` 스코프를 읽기/쓰기로
   - `repository`만 주면 저장소 생성 시점에 403으로 막힌다).
4. `.env`의 `GITEA_ADMIN_USERNAME`(2번에서 만든 계정 아이디)과
   `GITEA_API_TOKEN`(3번에서 발급한 값)을 채운다.
5. `docker compose up -d --build`를 다시 실행한다.

#### 그 외(선택) - 외부에서 접속할 계획이 없다면 안 건드려도 된다

`PUBLIC_BACKEND_URL`을 채우면 `git link` 시 웹훅과 EMQX 인증/인가
훅이 자동 등록된다(로컬 전용 개발 환경이면 비워둬도 나머지 기능엔
지장 없음 - 웹훅/훅 등록만 건너뜀). 웹 UI의 실시간 변경 추적/메시징
패널 갱신을 쓰려면 `PUBLIC_EMQX_WS_URL`도 채운다(예:
`ws://localhost:8083/mqtt` - 8083 포트가 이미 다른 걸로 쓰이고 있으면
`EMQX_WS_HOST_PORT`로 호스트 노출 포트를 바꾸고 URL도 맞춰준다). 비워두면
`GET /api/realtime-config`가 `null`을 반환해 웹 UI가 실시간 갱신만 조용히
꺼진 상태로 동작한다.

### 호스트에 직접 설치

```bash
cd frontend && npm install && npm run build && cd ..   # backend가 이 dist/를 정적 서빙
cd backend
npm install
npm run build
DB_DRIVER=sqlite DATABASE_URL=file:./data.db \
JWT_SECRET=<32자 이상> CREDENTIAL_ENCRYPTION_KEY=<64자 hex> \
MEILISEARCH_HOST=<...> MEILISEARCH_API_KEY=<...> \
EMQX_API_URL=<...> EMQX_API_KEY=<...> EMQX_API_SECRET=<...> \
EMQX_MQTT_URL=<...> EMQX_SERVICE_USERNAME=<...> EMQX_SERVICE_PASSWORD=<...> \
npx prisma db push --schema prisma/schema.sqlite.prisma --skip-generate
node dist/api/server.js
```

Meilisearch/EMQX는 별도로 떠 있어야 한다(각자 공식 바이너리/Docker
이미지로 로컬 실행 가능). `frontend/dist`가 없으면 backend는 정상
기동하되 웹 UI 없이 API만 서빙한다(CLI/MCP는 지장 없음).

### 프런트엔드 개발

```bash
cd frontend
npm install
npm run dev   # :5173, /api를 backend(:8760)로 프록시
```

backend를 먼저(다른 터미널에서) 띄워둔 상태로 위 명령을 실행하면
핫 리로드로 화면을 바로 확인할 수 있다.

### CLI

```bash
cd backend
npm link   # 전역에 docs/docs-mcp 명령 설치
docs auth login --api http://localhost:8760 --username <u> --password <p>
docs project-create <이름>
docs new <projectId> SP --title "..." --body <로컬 파일>

# 가이디드 마이그레이션(concept 스타일 파일 기반 프로젝트 옮기기)
docs migrate scan ../concept/docs > manifest.json   # 로컬 스캔, API 호출 없음
# manifest.json을 열어 docTypeCode/statusCode/skip을 검토·수정한 뒤:
docs migrate apply <projectId> manifest.json
```

### MCP

`docs auth login`으로 한 번 로그인해두면(`~/.claude-native-workflow/
credentials.json` 공유), `docs-mcp`를 stdio MCP 서버로 등록해 CLI와
동일한 85개 도구를 그대로 쓸 수 있다(코멘트/폴더 관련 도구는 의도적으로
없음 - 위 "이번 라운드" 절 참고). `auth register/login/logout`은
비밀번호가 대화 컨텍스트에 남지 않도록 의도적으로 MCP 도구로 노출하지
않는다(CLI 전용) - `auth_whoami`만 로그인 상태 확인용 예외.

## 설계 원칙

- **CLI/MCP 명령어 완전성**: 클로드가 문서/워크플로우 상태를 읽거나
  쓰는 모든 동작은 CLI/MCP 명령으로 존재해야 한다. 단, 편집 중인
  문서의 로컬 스크래치 사본은 정상 작업 방식이다(단, git 커밋 대상은
  아님).
- **추적 코드 명시**: 클로드가 제안하거나 설계 내용을 작성할 때는
  관련 추적 코드(`XX-XXXXXXXX`)를 정확히 명시한다.
