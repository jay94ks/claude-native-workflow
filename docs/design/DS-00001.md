# DS-00001 워크플로우 재구성

## 배경

v1(초기 버전)은 `docs/PROTOCOL.md`의 규칙을 Claude가 프롬프트만 보고 손으로
지키는 방식이었다. `tools/docs/server.py`(대시보드)는 별도로 같은 로직을 자체
구현하고 있고, 새 프로젝트에는 `bootstrap-prompt.md` 전체를 복사-붙여넣기해야
했다.

설계자와의 대화로 확정된 요구사항:

- **초간단/평범/고급** 3개 등급을 **동시 사용 규모(단일 설계자 vs 팀)** 축으로
  나눈다. 각 등급은 설계자가 하나를 골라 설치하는 **독립적인 배포 경로**다
  (단계적 업그레이드 관계가 아니다 — 다만 세 등급 모두 `docs/` 마크다운
  포맷이라는 같은 "프로토콜 계약"은 공유한다).
- **Claude 접근성(공통 요구사항)**: 어느 등급이든, 설계자가 프롬프트로 지시하면
  Claude가 그 등급에 맞는 방법(Skill 안내 → Bash로 CLI 호출 / MCP 도구 호출 /
  REST API 호출)으로 문서 워크플로우 기능을 **알아서** 사용할 수 있어야 한다.
  등급마다 하부 구현은 다르지만, Claude 입장에서는 항상 Skill이 진입점이고
  그 Skill이 해당 등급의 실제 호출 방식을 감싼다.
- **설계자는 항상 문서를 직접 편집할 수 있다.** 어느 등급에서도 CLI/MCP/REST
  API 같은 "정해진 규약"을 통한 상호작용은 선택지이지 강제가 아니다 —
  `docs/*.md`는 결국 파일이므로 설계자가 손으로 고쳐도 된다. `authoring_mode`
  (뒤에 나옴)는 **Claude**의 행동을 제어하는 설정이지 설계자 자신의 편집
  권한을 제한하지 않는다. 고급 등급의 API role(뷰어/에디터/오너, SP-00002
  3절)도 REST API 경로에만 적용되는 접근 제어이고, git 저장소 접근 권한이
  있는 설계자는 role과 무관하게 git 경로로 직접 편집·커밋·푸시할 수 있다
  (막지 않는다 — git 자체의 저장소 권한 관리에 위임).
- **등급은 유료 단계가 아니다.** "초간단/평범/고급"은 기능을 돈 주고 사는 단계가
  아니라 배포 규모(단일 설계자 로컬 / 로컬 서비스 / 클라우드 다중 설계자)에
  맞춘 기본 설정 프리셋일 뿐이다. git 이력·diff·문서 코멘트 같은 "GitHub과
  유사한 협업 기반"은 **세 등급 모두에서** 켜고 끌 수 있는 토글 기능으로
  둔다(초간단도 예외 없음). REST API 모양도 세 등급이 최대한 동일하게
  유지한다 — 상세는 [SP-00003](../spec/SP-00003.md).
- **구현은 특정 언어에 종속되지 않는다("AI-native" 원칙).** 이 워크플로우의
  진짜 정본은 특정 언어로 쓰인 소스코드가 아니라, `docs/PROTOCOL.md` +
  `SP-*` + [SP-00003](../spec/SP-00003.md) 6절의 스키마/정합성 테스트
  픽스처다. 이걸 "pseudo-code 명세"로 보고, 이 워크플로우를 새 프로젝트에
  들여오는 Claude가 그 환경에 있는 컴파일러/스크립트 도구로 실제 구현체를
  즉석에서 만들어 정합성 테스트를 통과시키는 것도 유효한 배포 경로다 —
  "특정 바이너리를 배포"하는 대신 "명세 + 검증 기준을 배포하고 Claude가
  그 자리에서 구현하게" 하는 쪽이 AI 네이티브 도구의 기본 배포 모델에
  더 맞는다. 다만 이미 만들어 검증까지 끝낸 구현체(초간단의 `tier1/`)를
  아무 이유 없이 다시 생성시키는 건 위험만 늘리므로, 이 원칙은 **아직
  검증된 구현이 없는 부분**(평범/고급, [SP-00004](../spec/SP-00004.md) 등)
  에 우선 적용한다. 초간단은 이미 검증된 `tier1/`을 그대로 배포한다.

## 등급별 스택 (확정)

초간단은 다른 두 등급과 코드를 공유하지 않는 독립 구현체(Python)다. 평범과
고급은 **같은 Node.js 백엔드 코드베이스**를 공유한다 — 고급은 평범의 백엔드를
확장(다중 설계자·인증·클라우드 배포·DB 기본 활성화)한 것이라, DB 계층 등
핵심 로직은 두 등급이 같이 쓴다. 세 등급 모두가 공통으로 지키는 건 `docs/`
마크다운+프론트매터 포맷(=`docs/PROTOCOL.md`)이다.

### 초간단 (Tier 1) — 완전 단일 설계자, 로컬 전용

- **배포**: `.md` 파일로만 구성된 수동 프롬프트 세트(`bootstrap-prompt.md`).
  설치랄 게 없다 — 복붙하면 끝.
- **대시보드**: 정말 단순한 Python(stdlib only, zero-dependency) 웹 대시보드.
  지금 `tools/docs/`에 이미 구현·검증되어 있다.
- **Claude 접근**: 프롬프트 자체가 지침이 되어 Claude가 직접 마크다운을
  쓰거나(직접 편집), 필요하면 같이 심어진 소형 Python 스크립트를 Bash로 호출.
  MCP 없음, 자동화 없음 — 있는 그대로 가장 단순한 경로.
- **git 이력/diff/코멘트도 지원**: `subprocess`로 로컬 `git log`/`git diff`를
  호출하고, 코멘트는 stdlib `sqlite3`에 저장한다 — 추가 의존성 없이
  [SP-00003](../spec/SP-00003.md)의 공통 API 계약 대부분을 구현할 수 있다.
  다중 설계자 인증만 해당 없음(단일 로컬 설계자 전제).
- **현재 상태**: 문서 CRUD/답변 흐름은 완성됨. git 이력/diff/코멘트 API 추가가
  이번 재구성에서 새로 필요한 작업.

### 평범 (Tier 2) — 한 사람, 여러 프로세스/기기, 또는 소규모 협업

- **스택: Node.js + TypeScript로 전체 통일.** 대시보드(Quasar — Vue 3,
  `<script setup>`, scoped SCSS)뿐 아니라 MCP 서버(`@modelcontextprotocol/sdk`)와
  자동화/CLI까지 **하나의 Node 백엔드가 docs 조작 로직을 한 번만 구현**하고,
  대시보드·MCP·CLI가 전부 그 백엔드(로컬 API)를 호출하는 구조.
- **배포**: Docker(Compose)로 로컬에서 상시 기동. 필요하면 Claude Code
  플러그인으로 CLI/스킬을 함께 설치.
- **Claude 접근**: Skill이 우선 MCP 도구 호출을 안내하고, MCP 서버가 없는
  환경이면 Bash로 Node CLI(`npx docs-cli ...` 형태)를 호출하는 경로로 폴백.
  둘 다 같은 로컬 백엔드를 두드리므로 결과가 항상 일치한다.
- **동시 쓰기 보호**: 로컬 백엔드 프로세스가 유일한 writer라서, 백엔드 내부의
  단순한 mutex/큐로 충분하다(여러 클라이언트가 동시에 붙어도 백엔드가 직렬화).
- **git 연동이 기본 동작**: Claude가 문서를 생성/수정/답변 처리할 때마다
  백엔드가 (또는 백엔드 호출 이후 Skill 지침에 따라 Claude가) `docs/` 변경을
  git commit까지 수행하는 것을 기본값으로 한다. push/pull도 마찬가지로
  워크플로우 일부로 포함한다(예: 세션 시작 시 pull로 최신 상태 반영, 답변 처리나
  문서 생성 직후 commit, 설계자가 명시적으로 요청하거나 일정 시점마다 push).
  이는 평범 등급을 "혼자 여러 기기/세션" 시나리오뿐 아니라 고급 등급의 git 협업
  경로와도 자연스럽게 이어지게 한다 — 평범을 쓰던 설계자가 나중에 팀 저장소를 공유하게
  되어도 이미 커밋 이력이 정리되어 있다.
  구체적으로 어떤 작업(생성/답변/전환)마다 자동 commit할지, push 시점을 즉시로
  할지 배치로 할지는 PL 단계에서 정한다.
- **서비스 DB는 선택적으로 활성화 가능**: 고급(Tier 3)에서 쓰는 DB 계층(MySQL
  메인 + 오픈소스 DB 대부분, ORM으로 추상화)을 평범 등급의 Node 백엔드도 그대로
  재사용할 수 있게 만든다. 기본값은 "DB 없이 파일만"이지만, 설정으로 켜면
  검색/색인 캐시를 DB로 처리할 수 있다 — Tier 3와 같은 DB 계층을 공유하므로,
  평범에서 DB를 켜서 쓰던 프로젝트가 고급으로 옮겨갈 때도 스키마/코드가 그대로
  이어진다. (다중 프로젝트 관리 자체는 평범에 해당 없음 — 로컬 `docs/` 한 개만
  다루는 구조라서, 고급에서만 의미가 생기는 별도 계층이다.)
- **git 이력/diff·문서 코멘트가 기본 on**: SP-00003의 `git_log_ui`/`comments`
  토글이 평범에서는 기본으로 켜져 있다. Quasar 대시보드에 커밋 히스토리·diff
  뷰·코멘트 스레드 화면이 기본 포함된다(상세 [SP-00001](../spec/SP-00001.md)).

### 고급 (Tier 3) — 클라우드 기반, 다중 설계자

- **스택**: 평범(Tier 2)의 Node 백엔드를 확장해서 클라우드에 배포. 다중 설계자·
  인증·테넌시를 이 백엔드에 추가한다(코드베이스는 이어받되 배포 형태와 저장
  방식이 달라짐).
- **연결 방식**: MCP나 Claude 쪽에서의 접근은 **HTTP REST API 호출**로 클라우드
  서버에 저장/조회한다.
- **저장소는 git 저장소 기반을 유지한다** — 클라우드 백엔드가 자체 DB에만
  담아두는 게 아니라, `docs/`를 **git 저장소로 관리**하면서 그 위에 REST API를
  얹는 구조. 두 가지 협업 시나리오를 모두 지원해야 한다:
  1. **API 경로**: 여러 설계자의 Claude 세션이 REST API를 호출 → 서버가 각
     변경을 커밋으로 기록(감사 이력 확보).
  2. **git 경로**: 다른 설계자가 저장소를 직접 clone해서 로컬(초간단/평범 도구 포함)로
     편집·커밋·푸시, 브랜치/PR로 협업 → 서버는 웹훅으로 push를 감지해 상태를
     동기화.
  즉 REST API는 "git 저장소에 대한 또 하나의 쓰기 경로"이지, git을 대체하는
  별도 저장소가 아니다.
- **Claude 접근**: Skill이 REST API 엔드포인트로 인증된 호출을 하는 얇은
  클라이언트(스크립트 또는 MCP-원격 프록시)를 안내. 다른 설계자가 git 경로로 작업 중일
  때는 평범/초간단 등급의 로컬 도구를 그대로 써도 무방하다(같은 `docs/` 포맷
  계약을 공유하므로).
- **데이터베이스**: `docs/` 문서 원본은 계속 git이 정본이고, DB는 서비스 계층
  (설계자 계정·인증·테넌시·프로젝트 등록·검색/색인 캐시)을 담당한다. **MySQL을
  메인으로 지원**하되, 오픈소스 DB 데몬 대부분(PostgreSQL, MariaDB, SQLite 등)을
  같이 지원할 수 있도록 특정 DB에 종속되지 않는 데이터 접근 계층(ORM/쿼리
  빌더)으로 구현한다.
- **인증/계정**: ID/PW 기반 설계자 계정과 인증 토큰 체계를 확립한다. 구체
  명세는 [SP-00002](../spec/SP-00002.md)에 정리했다(계정/토큰/권한 모델/DB
  스키마/REST API).
- **웹 대시보드**: git 이력/diff/코멘트 화면 자체는 평범과 동일(등급 공통
  기능). 고급이 추가로 얹는 것은 프로젝트 선택/전환 UI와 멤버 관리 화면뿐이다
  (상세 [SP-00002](../spec/SP-00002.md) 8절).
- **[DC-00002](../decision/DC-00002.md)에서 확정**: 호스팅 위치(벤더 중립
  설계, 실배포처는 나중에), 환경변수/시크릿(dotenv + 플랫폼 기본 매니저),
  git 웹훅 동기화 대상(GitHub 1차), 지원 DB 우선순위(PostgreSQL → SQLite,
  MariaDB는 MySQL 커넥터로 이미 호환), 조직 단위 테넌시 확장(지금은 고려
  안 함, 필요해지면 별도 DS). 상세는 [SP-00002](../spec/SP-00002.md) 6~7절.

## 등급 간 관계

| | 초간단 | 평범 | 고급 |
|---|---|---|---|
| 언어 | Python | Node.js/TypeScript | Node.js/TypeScript (Tier2 확장) |
| 저장소 | 로컬 `docs/*.md`(git) | 로컬 `docs/*.md`(git, Node 백엔드가 관리) | git 저장소(클라우드 호스팅) + REST API |
| 접근 경로 | 직접 편집 + 로컬 스크립트 | MCP 우선, CLI 폴백 (로컬 백엔드 경유) | REST API(원격) 또는 git clone 경로 |
| git 연동 | 수동(설계자 몫) | **Claude가 commit/push/pull까지 기본 수행** | API 변경 자동 커밋 + 다른 설계자의 git 경로 병행 |
| git 이력/diff/코멘트 | ✅(subprocess+sqlite3) | ✅ 기본 on | ✅ 기본 on(+웹훅으로 git 경로 커밋도 반영) |
| 서비스 DB | 없음(코멘트는 sqlite 파일) | 선택적 활성화(끄면 sqlite) — Tier3와 동일 DB 계층 재사용 | MySQL 메인 + 오픈소스 DB 대부분(ORM으로 추상화), 기본 활성 |
| 다중 프로젝트/멤버 관리 | 해당 없음 | 해당 없음(로컬 `docs/` 1개) | ✅ 고급 전용 |
| 동시성 | 없음(단일 프로세스) | 백엔드 mutex | 서버 측 다중 설계자 처리 |
| 배포 | 복붙 | Docker | 클라우드 배포 |

초간단은 평범/고급과 코드를 공유하지 않으므로, `docs/PROTOCOL.md`(파일 포맷
계약)와 [SP-00003](../spec/SP-00003.md)(REST API 계약)을 세 등급 공통의
"단일 진실 공급원"으로 남긴다. 평범/고급은 여기에 더해 Node 백엔드
