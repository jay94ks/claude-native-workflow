# SP-00003 공통 REST API 계약

설계 근거: [DS-00001](../design/DS-00001.md).

## 1. 원칙

- **등급은 유료 단계가 아니다.** 초간단/평범/고급은 "돈을 내고 기능을 산다"가
  아니라 배포 규모(단일 설계자 로컬 / 로컬 서비스 / 클라우드 다중 설계자)에
  맞춘 **기본 설정 프리셋**일 뿐이다.
- **기능은 전부 토글 가능한 모듈**이다. git 이력/diff 조회, 문서 코멘트,
  서비스 DB, 인증/멀티유저 — 어느 것도 특정 등급 전용으로 잠겨 있지 않다.
  등급마다 기본값(무엇이 켜져 있는가)만 다르다.
- **REST API 모양은 세 등급이 최대한 동일하게 유지한다.** 초간단(Python
  stdlib)도 git 로그/diff/blame은 `subprocess`로 로컬 `git` 명령을 호출하면
  되고, 코멘트는 stdlib `sqlite3`로 저장하면 되므로 **추가 의존성 없이
  이 계약 대부분을 구현할 수 있다.** 오직 인증/멀티유저(계정·토큰·역할)만
  "여러 사람이 실제로 접근한다"는 전제가 있어야 의미가 있어서, 초간단에서는
  기본적으로 빠지지만 계약상 자리는 예약되어 있다(원하면 최소 구현으로 켤 수
  있게 설계를 막지 않는다).

## 2. 라우트 목록과 등급별 지원

| 라우트 | 설명 | 초간단 | 평범 | 고급 |
|---|---|---|---|---|
| `GET /api/tree` | 문서 트리 | ✅ | ✅ | ✅ (프로젝트 네임스페이스) |
| `GET /api/doc?path=` | 문서 1건(`&anchor=`이면 그 섹션만, 6절) | ✅ | ✅ | ✅ |
| `GET /api/search?q=` | 전문 검색(6절 탐색) | ✅ | ✅ | ✅ |
| `GET /api/pending` | 답변 대기 목록 | ✅ | ✅ | ✅ |
| `GET /api/design` | DC/RV/FX 목록 | ✅ | ✅ | ✅ |
| `GET /api/logs` | LG 목록 | ✅ | ✅ | ✅ |
| `GET /api/all` | 전체 문서 목록 | ✅ | ✅ | ✅ |
| `POST /api/docs` | 문서 생성 | ✅ | ✅ | ✅ |
| `POST /api/docs/:path/reply` | 답변 처리 | ✅ | ✅ | ✅ |
| `POST /api/plan/:id/transition-done` | PL→DN 전환 | ✅ | ✅ | ✅ |
| `POST /api/git/commit\|push\|pull` | git 조작 | ✅(로컬 git 필요) | ✅(자동화 기본 on) | ✅(서버가 대행) |
| `GET /api/git/log` `/commits/:sha` `/diff/:sha` `/blame` | 커밋 이력/diff/blame | ✅(`subprocess`) | ✅ | ✅ |
| `GET`/`POST /api/docs/:path/comments` | 문서 단위 코멘트 | ✅(`sqlite3`) | ✅ | ✅ |
| `POST /api/docs/:path/comments/:id/resolve` | 코멘트 해결 | ✅ | ✅ | ✅ |
| `GET /api/changes` / `POST /api/changes/:id/ack` | 변경 추적 큐(5절) | 해당 없음(자동 git 연동이 없음) | ✅ | ✅ |
| `GET /api/validate` | 문서 구조 검증(7절) | ✅ | ✅ | ✅ |
| `GET /api/trace` / `POST /api/trace` / `GET /api/trace/stream` | 추론 흔적(선택, [SP-00004](SP-00004.md)) | 해당 없음 | 선택 | 선택(권장) |
| `/api/auth/*` | 계정/토큰(회원가입·로그인·갱신·로그아웃) — 단일 `docs/`를 로그인으로 보호하는 용도 | 기본 ❌(단일 로컬 설계자) | 선택(끄면 무인증) | ✅ 필수 |
| `/api/projects/*` | 다중 프로젝트 관리/멤버 초대 | 해당 없음(로컬 `docs/` 1개뿐) | 해당 없음(로컬 `docs/` 1개뿐) | ✅ 고급에서만 추가 |

**코멘트 저장소는 "서비스 DB" 토글과 별개다.** `comments`/`git_log_ui`는
경량 기능이라 등급과 무관하게 내장 SQLite 파일(`docs/.workflow/comments.db`,
git에는 커밋하지 않음)에 저장하는 것을 기본으로 한다. `features.db`(3절)를
켜면 — 즉 MySQL 등 진짜 서비스 DB가 연결되면 — 코멘트도 그 DB로 옮겨간다.
고급은 `db`가 항상 켜져 있으므로 코멘트도 항상 서비스 DB에 있다(여러 서버
인스턴스가 동시에 붙는 환경이라 SQLite 파일로는 부족하기 때문).

`/api/projects/*`(다중 프로젝트)는 다른 라우트들과 달리 "토글 가능한 모듈"이
아니다 — 초간단/평범은 애초에 로컬 `docs/` 폴더 하나만 다루는 구조라 "여러
프로젝트를 한 서비스가 관리한다"는 개념 자체가 성립하지 않는다. 고급에서
클라우드 다중 설계자로 확장될 때 비로소 필요해지는, **고급 전용 추가 계층**
이다(SP-00002 4절). 반면 `/api/auth/*`는 "지금 이 `docs/` 하나를 로그인으로
잠글지"의 문제라 등급과 무관하게 켜고 끌 수 있다.

인증/다중 프로젝트의 세부 스펙은 [SP-00002](SP-00002.md)에, 그 외 라우트의
등급별 구현 디테일(Tier 2 Node 스택, git 자동화 기본값 등)은
[SP-00001](SP-00001.md)에 정리한다 — 이 문서는 "무슨 라우트가 있고 어느
등급에서 무엇이 기본값인가"만 담당한다.

## 3. 기능 토글 설정

`docs/.config.json`에 등급과 무관하게 개별 기능을 켜고 끄는 설정을 둔다:

```json
{
  "features": {
    "git_log_ui": true,
    "comments": true,
    "db": false,
    "auth": false
  }
}
```

| 등급 | 기본 프리셋 |
|---|---|
| 초간단 | `git_log_ui: true`, `comments: true`, `db: false`, `auth: false` |
| 평범 | `git_log_ui: true`, `comments: true`, `db: false`(원하면 on), `auth: false`(원하면 on) |
| 고급 | 전부 `true`(auth는 끌 수 없음 — 멀티유저의 전제 조건) |

**`db`만 예외다.** `git_log_ui`/`comments`/`auth`는 설정 파일 값을 그냥 바꿔도
안전하다(껐다 켜도 잃을 데이터가 없거나, 인증처럼 접근 제어만 바뀔 뿐 내용은
그대로다). 반면 `db`를 끄면 서비스 DB에 있던 `doc_comments`(원본 데이터, 캐시
아님)에 접근할 방법이 사라지므로, **`db.enabled`는 설정 파일 직접 수정이
아니라 데이터 이관까지 책임지는 전용 명령(`docs db enable`/`docs db disable`)
으로만 전환한다** — 절차는 [SP-00001](SP-00001.md) 6절.

즉 "초간단을 쓰던 설계자가 코멘트/git 이력 기능이 필요해졌다"고 해서 평범이나
고급으로 옮길 필요가 없다 — 같은 초간단 배포에서 설정만 켜면 된다. 반대로
평범/고급을 쓰는 설계자가 인증이 필요 없는 상황이면 꺼두고 로컬 신뢰 환경처럼 쓸 수
있다.

## 4. 각 등급의 구현 방식 차이 (같은 계약, 다른 구현체)

| | 초간단 | 평범/고급 |
|---|---|---|
| 언어 | Python stdlib | Node.js/TypeScript |
| git 이력 조회 | `subprocess.run(["git", "log", ...])` | `simple-git` 또는 git CLI 서브프로세스 |
| 코멘트 저장 | stdlib `sqlite3` | 선택적 활성화 시 ORM(MySQL/PostgreSQL/MariaDB/SQLite) |
| 인증 | (기본 없음. 켜고 싶다면 stdlib `hmac`/`hashlib` 기반 최소 토큰으로 구현 가능 — 이번 범위에서 만들지는 않음) | JWT(access) + DB 저장 refresh token |

같은 계약을 서로 다른 언어로 각자 구현하는 것이라, 코드는 공유하지 않지만
클라이언트(Skill, MCP 도구, 대시보드 프런트엔드)는 어느 등급에 붙어도 거의
동일하게 동작한다.

## 5. 변경 추적 큐 (Claude가 `git diff`를 직접 돌리지 않게)

여러 주체(다른 설계자의 REST API 호출, 웹훅으로 들어온 git push, 다른 설계자의 코멘트)가
`docs/`를 건드릴 수 있는 평범/고급 등급에서는, Claude가 "내가 없는 사이에 뭐가
바뀌었는지"를 알아야 할 때마다 커밋을 비교(diff)해서 알아내는 대신, **변경이
생기는 시점에 백엔드가 바로 큐에 기록해두고 Claude는 그 큐만 읽는다** —
`docs/reply/index.md`(미답변 큐)와 같은 패턴이다: 처리 전까지만 목록에 남고,
확인·처리하면 지운다.

### 데이터 모델

```
change_notices
  id             정수/uuid, PK
  doc_path       string
  source         enum(git_pull, webhook, api, comment)   -- 무엇이 이 변경을 만들었는지
  summary        string        -- 예: "DC-00005 갱신 (커밋 a1b2c3)", "새 코멘트 등록"
  ref            string null   -- 관련 커밋 sha 또는 코멘트 id 등
  created_at     datetime
```

저장 위치는 코멘트와 동일한 규칙을 따른다 — `db.enabled`가 꺼져 있으면 내장
SQLite, 켜져 있으면 서비스 DB([SP-00001](SP-00001.md) 6절).

### 큐에 항목이 쌓이는 시점

`git_pull`/`webhook`/`api`/`comment` 같은 개별 이벤트마다 따로 후킹해서
항목을 만들지 않는다 — **6절의 읽기 게이트**가 모든 조회의 공통 관문이라,
그 게이트가 "캐시에 있던 내용과 지금 읽은 내용이 다르다"고 판단하는
순간 자동으로 이 큐에 항목이 쌓인다. `source`(무엇을 통해 이 읽기가
일어났는지)만 호출부에서 실어 보내면 된다:

- `git pull`이 새 커밋을 가져온 뒤, 그 커밋들이 건드린 문서를 읽을 때
  (`source: git_pull`).
- 웹훅으로 다른 설계자의 push가 감지된 뒤, 영향받은 문서를 읽을 때
  (`source: webhook`).
- 다른 설계자의 REST API 요청이 문서를 바꾼 뒤, 그 결과를 다시 읽을 때
  (`source: api`).
- 코멘트가 새로 달려 문서를 다시 읽을 때(`source: comment`).
- 그 외 무엇이든 — 예를 들어 `authoring_mode: direct-edit`로 설계자가
  손으로 파일을 고친 경우도, 다음에 누군가(대시보드, CLI, Claude)가 그
  파일을 읽는 순간 게이트가 차이를 감지해 잡아낸다. **이전 설계는 이
  경로(직접 편집)를 놓치고 있었다** — 게이트로 통합하면서 자동으로
  해결된다.

내가 스스로 만든 변경(방금 내가 `docs new`/`docs reply`로 쓴 내용)은 쓰기
경로에서 캐시를 이미 최신 상태로 갱신해두므로, 그 직후 내가 다시 읽어도
캐시와 실제 내용이 일치해 큐에 안 쌓인다 — 별도의 "내가 한 건지" 판별 로직
없이 자연스럽게 자기 알림 스팸이 방지된다.

### API/CLI

```
GET  /api/changes            처리 안 된 변경 목록
POST /api/changes/:id/ack    확인·처리 완료 → 큐에서 제거

docs changes                 CLI로 목록 조회
docs changes ack <id>        CLI로 처리 완료 표시
```

### Claude 사용 원칙 — 핵심 사용 사례

이 큐가 만들어진 목적은 단순 "알림"이 아니라, 설계자가

> "문서 변경사항을 추적해서 계획이나 승인할 거 있으면 업데이트해줘."

처럼 프롬프트를 줬을 때 Claude가 바로 실행할 수 있는 **참고 자료**가 되는
것이다. 이런 프롬프트를 받으면(또는 세션 시작 시 큐에 항목이 있으면 먼저
알리는 것도 동일하게) Claude는 아래 순서로 처리한다:

1. `GET /api/changes`(또는 `docs changes`)로 미확인 변경 목록을 가져온다 —
   diff를 직접 계산하지 않는다.
2. 각 항목의 `doc_path`가 가리키는 문서를 열어, 그 문서의 프론트매터
   `links`와 — 반대 방향으로 — **다른 문서들 중 이 문서를 `links`에 포함한
   것**을 찾는다(특히 `PL`/`DC`/`RV`/`FX` 타입 위주로). 이 변경이 그 문서들의
   전제를 바꾸는지 판단한다.
3. 영향이 있으면 해당 `PL`/`DC`/`RV`/`FX` 문서를 갱신하거나, 필요하면 새
   `DC`/`RV`/`FX`(4절 "답변 대기" 형식)를 만들어 설계자의 승인을 요청한다
   (`docs/PROTOCOL.md` 7절 절차를 그대로 따름 — 실행 계획은 갱신 요약만 하고
   바로 실행하지 않는다).
4. 처리를 마친 항목은 `POST /api/changes/:id/ack`로 큐에서 지운다. 영향이
   없다고 판단한 항목도(검토는 했으므로) ack한다.

즉 이 큐는 "무엇이 바뀌었는가"를 diff 없이 알려주는 입력이고, 그 다음
"바뀐 게 하위 계획/승인 대상에 영향을 주는가"를 판단하는 건 Claude가
`links` 그래프를 따라가며 하는 몫이다.

세션 시작 시 큐에 항목이 있으면 먼저 알린다 — `docs/PROTOCOL.md` 7절의
"미답변 항목이 있으면 대화 시작 시 알린다"는 규칙과 나란히 동작하도록
`CLAUDE.md` 템플릿과 `docs/PROTOCOL.md`에도 같이 반영한다(PL-00001에서
처리).

## 6. 읽기 게이트 (비교·부분 읽기·탐색의 단일 관문)

### 6.1 왜 필요한가

Claude가 문서 작업을 할 때 실제로 쓰는 동작은 거의 다 세 가지로 좁혀진다:
**비교**(뭐가 바뀌었는지 diff), **부분 읽기**(문서 전체가 아니라 특정
섹션만), **탐색**(트리/목록/검색으로 관련 문서 찾기). 이 동작들과 "캐시
갱신"([SP-00001](SP-00001.md) 6절), "변경 감지"(5절)를 각 호출부(git pull
핸들러, 웹훅 핸들러, API 핸들러)가 저마다 따로 처리하게 두면 **놓치는
경로가 생긴다**(5절에서 확인한 직접 편집 케이스처럼).

대신 이 세 동작을 **하나의 게이트 함수**로 몰아서, 등급/언어에 상관없이
모든 조회가 이 게이트를 통과하게 만든다. 이 게이트가 "지금 읽은 내용이
캐시와 다른가"를 항상 확인하고, 다르면 그 자리에서 캐시 갱신(6.2절) +
변경 큐 적재(5절) + (켜져 있으면) 실시간 알림([SP-00004](SP-00004.md))까지
전부 처리한다 — 조회 동작 자체가 색인/알림 파이프라인의 유일한 입구가
되는 것이다.

### 6.2 의사코드 (모든 등급의 구현이 지켜야 하는 동작)

`docs/PROTOCOL.md` + 이 문서가 정본이고, 아래는 그 정본을 실행 가능한
형태로 옮긴 것이다 — 특정 언어에 종속되지 않는다(DS-00001의 "AI-native"
원칙). 어떤 언어로 구현하든 이 의사코드와 동등하게 동작해야 하고,
7절의 정합성 테스트로 그걸 검증한다.

```
# 상태: cache[path] = { text, meta, hash, read_at }  (mtime 대신 내용 해시 기준 —
#      6.2절의 in-memory/서비스-DB 캐시와 같은 저장소를 공유한다)

function read_doc(path, source):
    text = fs.read(path)
    h = hash(text)
    snapshot = cache.get(path)

    if snapshot is None:
        # 콜드 스타트 — "변경"이 아니라 "처음 봄". 알림 없이 캐시만 채운다.
        meta, body = parse_frontmatter(text)
        cache.put(path, { text, meta, hash: h, read_at: now() })
        return { meta, body }

    if snapshot.hash == h:
        return { meta: snapshot.meta, body: extract_body(snapshot.text) }  # 캐시 그대로 반환, 재파싱 없음

    # 캐시와 실제 내용이 다르다 — 무언가 이 게이트를 거치지 않고 파일을 바꿨다는 뜻
    meta, body = parse_frontmatter(text)
    diff = compute_diff(snapshot.text, text)
    cache.put(path, { text, meta, hash: h, read_at: now() })

    notice = change_notices.create(doc_path: path, source: source, summary: diff.summarize(), ref: diff.ref)
    trace_events.create(kind: "change", doc_path: path, detail: diff.summarize(), ref: notice.id)  # SP-00004
    if features.realtime:
        sse.push(notice)

    return { meta, body }

function read_section(path, anchor, source):
    { meta, body } = read_doc(path, source)          # 부분 읽기도 예외 없이 게이트를 통과
    return { meta, section: extract_section(body, anchor) }   # 헤딩 슬러그로 해당 섹션만 추출

function diff_doc(path, from_ref, to_ref):
    old_text = git.show(from_ref, path)
    new_text = git.show(to_ref, path)
    return compute_diff(old_text, new_text)          # 과거 스냅샷끼리 비교 — 캐시/알림과 무관

function explore(query, source):
    results = []
    for path in walk(docs_dir):
        { meta, body } = read_doc(path, source)      # 트리/목록/검색도 전부 게이트를 통과
        if query.matches(path, meta, body):
            results.append({ path, meta })
    return results
```

### 6.3 API 매핑

| 의사코드 함수 | API | 비고 |
|---|---|---|
| `read_doc` | `GET /api/doc?path=` | 이미 2절에 있는 라우트 — 내부 구현만 게이트를 타도록 정리 |
| `read_section` | `GET /api/doc?path=&anchor=` | 신설 — 앵커 지정 시 본문 대신 해당 섹션만 반환(Claude 자신의 컨텍스트 절약에도 유용) |
| `diff_doc` | `GET /api/git/diff/:sha` | [SP-00001](SP-00001.md) 2절에 이미 있음 |
| `explore` | `GET /api/tree`, `/api/all`, `/api/design`, 신규 `GET /api/search?q=` | 트리/목록은 이미 있음, 전문 검색(`search`)만 이번에 추가 |

### 6.4 구현 위치

- **초간단**: `core/docstore`의 `read_doc` 계열 함수들이 이 의사코드 그대로.
  캐시는 이미 만든 mtime(→ 위 의사코드에 맞춰 content-hash로 정밀화 고려)
  기준 인메모리 캐시([tier1/tools/docs/server.py](../../../tier1/tools/docs/server.py)의
  `get_doc_meta`).
- **평범/고급**: 같은 함수를 `core/`에 구현. `db.enabled`가 꺼져 있으면
  인메모리, 켜져 있으면 `docs_index` 테이블이 캐시 저장소를 겸한다.

## 7. 문서 구조 검증 (스키마) — "무엇이 유효한 문서인가"를 확정적으로 정의

### 7.1 왜 필요한가

Tier 1(Python)·Tier 2/3(Node)는 서로 코드를 공유하지 않고 각자
`docs/PROTOCOL.md`를 독립적으로 구현한다(DS-00001). 이 방식의 위험은 두
구현이 "무엇이 유효한 프론트매터인가"를 미묘하게 다르게 판단하게 되는
드리프트다 — 예를 들어 Tier 1은 `status: draft`를 허용하는데 Tier 2가
막는다거나, 반대로 잘못된 값을 한쪽만 통과시키는 식. 이걸 막으려고
"단일 엔진(C++)으로 전부 처리하게 override"하는 안을 검토했었는데, 그건
구현을 하나로 합치는 방식이라 비용이 크다. **대신 "무엇이 유효한가"를
코드가 아니라 스키마(데이터)로 못 박고, 모든 등급의 구현이 그 스키마를
지키는지 대조 검증하는 쪽**이 같은 확실성을 훨씬 적은 비용으로 준다.

### 7.2 스키마 파일

저장소 최상위 `schemas/<TYPE>.schema.json` (`IX`/`SP`/`PL`/`DN`/`DS`/`RM`/
`TP`/`DC`/`RV`/`FX`/`LG` — `RP`는 파일이 없으므로 제외)에 JSON Schema로
프론트매터 구조를 정의한다. `docs/PROTOCOL.md` 3절의 표(타입별 필수 필드,
`status` 열거값, `id`/`links` 패턴)를 그대로 기계가 읽을 수 있는 형태로
옮긴 것 — 두 문서가 어긋나면 스키마가 원본이고 PROTOCOL.md 표를 스키마에
맞춰 고친다.

검증 항목: 필수 필드 존재 여부, `type`이 폴더/파일명 접두사와 일치,
`id`가 파일명과 일치, `status`가 그 타입의 허용 열거값 안에 있는지,
`links` 배열 각 원소가 `TYPE-00000` 패턴을 따르고(가능하면) 실제 존재하는
문서를 가리키는지, `created`/`updated`가 `YYYY-MM-DD` 형식인지.

### 7.3 `docs validate` — 모든 등급 공통

```
GET  /api/validate               전체 docs/ 스캔, 위반 목록 반환
docs validate [--type DC,SP,...] [path...]   CLI
```

위반 하나당 `{path, field, rule, message}` 형태로 반환한다(어떤 파일의
어떤 필드가 어떤 규칙을 어겼는지 명확히). `docs new`/`docs reply` 등
core의 쓰기 경로는 저장 직전에 이 검증을 통과해야만 파일을 쓴다 —
`authoring_mode: direct-edit`로 손으로 편집한 경우를 위해 `docs validate`
전체 스캔도 별도로 제공한다(세션 시작 시나 CI에서 돌릴 수 있게).

구현은 등급마다 다르되 같은 스키마를 따른다:
- **초간단(Python, zero-dep)**: JSON Schema 스펙 전체가 아니라 여기서
  실제로 쓰는 부분집합(`required`/`enum`/`pattern`/`type`)만 해석하는
  소형 인터프리터를 stdlib만으로 직접 구현(새 의존성 없음).
- **평범/고급(Node)**: 검증 라이브러리(예: `ajv`)로 스키마 파일을 그대로
  로드해서 검증 — Tier 2/3는 이미 npm 의존성을 허용하는 등급이라 부담 없음.

### 7.4 정합성 테스트(드리프트 방지의 핵심)

`schemas/fixtures/`에 "유효한 예시 문서"와 "무효한 예시 문서"(각 위반
유형별로 최소 1개)를 넣어두고, Tier 1의 검증기와 Tier 2/3의 검증기 둘 다
이 픽스처에 대해 **같은 판정**을 내리는지 테스트한다(CI에서 두 구현을
나란히 돌림). 이게 "C++로 하나의 엔진에 몰아서 드리프트를 원천 차단"하려던
목표를 스키마+정합성 테스트로 달성하는 지점이다 — 구현은 여전히
독립적이지만, 판정 결과가 어긋나면 테스트가 바로 잡아낸다.
