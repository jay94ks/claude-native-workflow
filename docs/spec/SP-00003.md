# SP-00003 공통 REST API 계약

설계 근거: [DS-00001](../design/DS-00001.md).

## 1. 원칙

- **등급은 유료 단계가 아니다.** 초간단/평범/고급은 "돈을 내고 기능을 산다"가
  아니라 배포 규모(단일 설계자 로컬 / 로컬 서비스 / 클라우드 다중 설계자)에
  맞춘 **기본 설정 프리셋**일 뿐이다.
- **기능은 전부 토글 가능한 모듈**이다. git 이력/diff 조회, 문서 코멘트,
  서비스 DB, 인증/멀티유저 — 어느 것도 특정 등급 전용으로 잠겨 있지 않다.
  등급마다 기본값(무엇이 켜져 있는가)만 다르다.
- **REST API 모양은 세 등급이 최대한 동일하게 유지한다.** 초간단(Python
  stdlib)도 git 로그/diff/blame은 `subprocess`로 로컬 `git` 명령을 호출하면
  되고, 코멘트는 stdlib `sqlite3`로 저장하면 되므로 **추가 의존성 없이
  이 계약 대부분을 구현할 수 있다.** 오직 인증/멀티유저(계정·토큰·역할)만
  "여러 사람이 실제로 접근한다"는 전제가 있어야 의미가 있어서, 초간단에서는
  기본적으로 빠지지만 계약상 자리는 예약되어 있다(원하면 최소 구현으로 켤 수
  있게 설계를 막지 않는다).

## 2. 라우트 목록과 등급별 지원

| 라우트 | 설명 | 초간단 | 평범 | 고급 |
|---|---|---|---|---|
| `GET /api/tree` | 문서 트리 | ✅ | ✅ | ✅ (프로젝트 네임스페이스) |
| `GET /api/doc?path=` | 문서 1건 | ✅ | ✅ | ✅ |
| `GET /api/pending` | 답변 대기 목록 | ✅ | ✅ | ✅ |
| `GET /api/design` | DC/RV/FX 목록 | ✅ | ✅ | ✅ |
| `GET /api/logs` | LG 목록 | ✅ | ✅ | ✅ |
| `GET /api/all` | 전체 문서 목록 | ✅ | ✅ | ✅ |
| `POST /api/docs` | 문서 생성 | ✅ | ✅ | ✅ |
| `POST /api/docs/:path/reply` | 답변 처리 | ✅ | ✅ | ✅ |
| `POST /api/plan/:id/transition-done` | PL→DN 전환 | ✅ | ✅ | ✅ |
| `POST /api/git/commit\|push\|pull` | git 조작 | ✅(로컬 git 필요) | ✅(자동화 기본 on) | ✅(서버가 대행) |
| `GET /api/git/log` `/commits/:sha` `/diff/:sha` `/blame` | 커밋 이력/diff/blame | ✅(`subprocess`) | ✅ | ✅ |
| `GET`/`POST /api/docs/:path/comments` | 문서 단위 코멘트 | ✅(`sqlite3`) | ✅ | ✅ |
| `POST /api/docs/:path/comments/:id/resolve` | 코멘트 해결 | ✅ | ✅ | ✅ |
| `GET /api/changes` / `POST /api/changes/:id/ack` | 변경 추적 큐(5절) | 해당 없음(자동 git 연동이 없음) | ✅ | ✅ |
| `/api/auth/*` | 계정/토큰(회원가입·로그인·갱신·로그아웃) — 단일 `docs/`를 로그인으로 보호하는 용도 | 기본 ❌(단일 로컬 설계자) | 선택(끄면 무인증) | ✅ 필수 |
| `/api/projects/*` | 다중 프로젝트 관리/멤버 초대 | 해당 없음(로컬 `docs/` 1개뿐) | 해당 없음(로컬 `docs/` 1개뿐) | ✅ 고급에서만 추가 |

**코멘트 저장소는 "서비스 DB" 토글과 별개다.** `comments`/`git_log_ui`는
경량 기능이라 등급과 무관하게 내장 SQLite 파일(`docs/.workflow/comments.db`,
git에는 커밋하지 않음)에 저장하는 것을 기본으로 한다. `features.db`(3절)를
켜면 — 즉 MySQL 등 진짜 서비스 DB가 연결되면 — 코멘트도 그 DB로 옮겨간다.
고급은 `db`가 항상 켜져 있으므로 코멘트도 항상 서비스 DB에 있다(여러 서버
인스턴스가 동시에 붙는 환경이라 SQLite 파일로는 부족하기 때문).

`/api/projects/*`(다중 프로젝트)는 다른 라우트들과 달리 "토글 가능한 모듈"이
아니다 — 초간단/평범은 애초에 로컬 `docs/` 폴더 하나만 다루는 구조라 "여러
프로젝트를 한 서비스가 관리한다"는 개념 자체가 성립하지 않는다. 고급에서
클라우드 다중 설계자로 확장될 때 비로소 필요해지는, **고급 전용 추가 계층**
이다(SP-00002 4절). 반면 `/api/auth/*`는 "지금 이 `docs/` 하나를 로그인으로
잠글지"의 문제라 등급과 무관하게 켜고 끌 수 있다.

인증/다중 프로젝트의 세부 스펙은 [SP-00002](SP-00002.md)에, 그 외 라우트의
등급별 구현 디테일(Tier 2 Node 스택, git 자동화 기본값 등)은
[SP-00001](SP-00001.md)에 정리한다 — 이 문서는 "무슨 라우트가 있고 어느
등급에서 무엇이 기본값인가"만 담당한다.

## 3. 기능 토글 설정

`docs/.config.json`에 등급과 무관하게 개별 기능을 켜고 끄는 설정을 둔다:

```json
{
  "features": {
    "git_log_ui": true,
    "comments": true,
    "db": false,
    "auth": false
  }
}
```

| 등급 | 기본 프리셋 |
|---|---|
| 초간단 | `git_log_ui: true`, `comments: true`, `db: false`, `auth: false` |
| 평범 | `git_log_ui: true`, `comments: true`, `db: false`(원하면 on), `auth: false`(원하면 on) |
| 고급 | 전부 `true`(auth는 끌 수 없음 — 멀티유저의 전제 조건) |

**`db`만 예외다.** `git_log_ui`/`comments`/`auth`는 설정 파일 값을 그냥 바꿔도
안전하다(껐다 켜도 잃을 데이터가 없거나, 인증처럼 접근 제어만 바뀔 뿐 내용은
그대로다). 반면 `db`를 끄면 서비스 DB에 있던 `doc_comments`(원본 데이터, 캐시
아님)에 접근할 방법이 사라지므로, **`db.enabled`는 설정 파일 직접 수정이
아니라 데이터 이관까지 책임지는 전용 명령(`docs db enable`/`docs db disable`)
으로만 전환한다** — 절차는 [SP-00001](SP-00001.md) 6절.

즉 "초간단을 쓰던 설계자가 코멘트/git 이력 기능이 필요해졌다"고 해서 평범이나
고급으로 옮길 필요가 없다 — 같은 초간단 배포에서 설정만 켜면 된다. 반대로
평범/고급을 쓰는 설계자가 인증이 필요 없는 상황이면 꺼두고 로컬 신뢰 환경처럼 쓸 수
있다.

## 4. 각 등급의 구현 방식 차이 (같은 계약, 다른 구현체)

| | 초간단 | 평범/고급 |
|---|---|---|
| 언어 | Python stdlib | Node.js/TypeScript |
| git 이력 조회 | `subprocess.run(["git", "log", ...])` | `simple-git` 또는 git CLI 서브프로세스 |
| 코멘트 저장 | stdlib `sqlite3` | 선택적 활성화 시 ORM(MySQL/PostgreSQL/MariaDB/SQLite) |
| 인증 | (기본 없음. 켜고 싶다면 stdlib `hmac`/`hashlib` 기반 최소 토큰으로 구현 가능 — 이번 범위에서 만들지는 않음) | JWT(access) + DB 저장 refresh token |

같은 계약을 서로 다른 언어로 각자 구현하는 것이라, 코드는 공유하지 않지만
클라이언트(Skill, MCP 도구, 대시보드 프런트엔드)는 어느 등급에 붙어도 거의
동일하게 동작한다.

## 5. 변경 추적 큐 (Claude가 `git diff`를 직접 돌리지 않게)

여러 주체(다른 설계자의 REST API 호출, 웹훅으로 들어온 git push, 다른 설계자의 코멘트)가
`docs/`를 건드릴 수 있는 평범/고급 등급에서는, Claude가 "내가 없는 사이에 뭐가
바뀌었는지"를 알아야 할 때마다 커밋을 비교(diff)해서 알아내는 대신, **변경이
생기는 시점에 백엔드가 바로 큐에 기록해두고 Claude는 그 큐만 읽는다** —
`docs/reply/index.md`(미답변 큐)와 같은 패턴이다: 처리 전까지만 목록에 남고,
확인·처리하면 지운다.

### 데이터 모델

```
change_notices
  id             정수/uuid, PK
  doc_path       string
  source         enum(git_pull, webhook, api, comment)   -- 무엇이 이 변경을 만들었는지
  summary        string        -- 예: "DC-00005 갱신 (커밋 a1b2c3)", "새 코멘트 등록"
  ref            string null   -- 관련 커밋 sha 또는 코멘트 id 등
  created_at     datetime
```

저장 위치는 코멘트와 동일한 규칙을 따른다 — `db.enabled`가 꺼져 있으면 내장
SQLite, 켜져 있으면 서비스 DB([SP-00001](SP-00001.md) 6절).

### 큐에 항목이 쌓이는 시점

- `git pull`이 새 커밋을 가져왔을 때 → 그 커밋들이 건드린 문서마다 한 항목
  (`source: git_pull`). **이 시점에 이미 백엔드가 pull 전/후 커밋 범위를 알고
  있으므로, 그 결과로 항목을 만드는 것이지 나중에 다시 diff를 돌리는 게
  아니다.**
- 웹훅으로 다른 설계자의 직접 push가 감지됐을 때(고급, SP-00002 5절) → 동일하게
  `source: webhook`.
- 다른 설계자가 REST API로 문서를 바꿨을 때(고급, 나 아닌 설계자의 요청) →
  `source: api`.
- 코멘트가 새로 달렸을 때(내가 단 게 아니면) → `source: comment`.

내가 스스로 만든 변경(내 세션이 방금 만든 commit, 내가 방금 단 코멘트)은
큐에 넣지 않는다 — 자기 알림 스팸 방지.

### API/CLI

```
GET  /api/changes            처리 안 된 변경 목록
POST /api/changes/:id/ack    확인·처리 완료 → 큐에서 제거

docs changes                 CLI로 목록 조회
docs changes ack <id>        CLI로 처리 완료 표시
```

### Claude 사용 원칙 — 핵심 사용 사례

이 큐가 만들어진 목적은 단순 "알림"이 아니라, 설계자가

> "문서 변경사항을 추적해서 계획이나 승인할 거 있으면 업데이트해줘."

처럼 프롬프트를 줬을 때 Claude가 바로 실행할 수 있는 **참고 자료**가 되는
것이다. 이런 프롬프트를 받으면(또는 세션 시작 시 큐에 항목이 있으면 먼저
알리는 것도 동일하게) Claude는 아래 순서로 처리한다:

1. `GET /api/changes`(또는 `docs changes`)로 미확인 변경 목록을 가져온다 —
   diff를 직접 계산하지 않는다.
2. 각 항목의 `doc_path`가 가리키는 문서를 열어, 그 문서의 프론트매터
   `links`와 — 반대 방향으로 — **다른 문서들 중 이 문서를 `links`에 포함한
   것**을 찾는다(특히 `PL`/`DC`/`RV`/`FX` 타입 위주로). 이 변경이 그 문서들의
   전제를 바꾸는지 판단한다.
3. 영향이 있으면 해당 `PL`/`DC`/`RV`/`FX` 문서를 갱신하거나, 필요하면 새
   `DC`/`RV`/`FX`(4절 "답변 대기" 형식)를 만들어 설계자의 승인을 요청한다
   (`docs/PROTOCOL.md` 7절 절차를 그대로 따름 — 실행 계획은 갱신 요약만 하고
   바로 실행하지 않는다).
4. 처리를 마친 항목은 `POST /api/changes/:id/ack`로 큐에서 지운다. 영향이
   없다고 판단한 항목도(검토는 했으므로) ack한다.

즉 이 큐는 "무엇이 바뀌었는가"를 diff 없이 알려주는 입력이고, 그 다음
"바뀐 게 하위 계획/승인 대상에 영향을 주는가"를 판단하는 건 Claude가
`links` 그래프를 따라가며 하는 몫이다.

세션 시작 시 큐에 항목이 있으면 먼저 알린다 — `docs/PROTOCOL.md` 7절의
"미답변 항목이 있으면 대화 시작 시 알린다"는 규칙과 나란히 동작하도록
`CLAUDE.md` 템플릿과 `docs/PROTOCOL.md`에도 같이 반영한다(PL-00001에서
처리).
