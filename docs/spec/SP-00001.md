# SP-00001 평범(Tier 2) 명세

설계 근거: [DS-00001](../design/DS-00001.md).

## 1. 구성

하나의 Node.js/TypeScript 백엔드(`backend/`)가 docs 조작 로직을 한 번만
구현하고, 세 개의 얇은 진입점이 그것을 감싼다.

```
backend/
  src/
    core/           docs 조작 로직 (frontmatter, tracking, docstore, git, db)
    api/            로컬 HTTP API (Express/Fastify)
    mcp/             MCP 서버 (@modelcontextprotocol/sdk) — api/ 와 같은 core 호출
    cli/             CLI 커맨드 (commander 등) — api/ 와 같은 core 호출
  package.json
dashboard/            Quasar(Vue3) 프론트엔드 — backend의 api/ 를 호출
docker/
  docker-compose.yml  backend + dashboard 함께 기동
```

MCP 서버, CLI, 로컬 API가 전부 같은 `core/` 함수를 직접 호출한다(서로를 거쳐가지
않음). 대시보드만 네트워크로 로컬 API를 호출한다.

## 2. 로컬 HTTP API

라우트 목록과 등급별 지원 여부는 [SP-00003](SP-00003.md) 2절이 원본이다.
평범 등급은 인증 없이 기본 동작한다(신뢰된 로컬 환경 전제, `127.0.0.1` 또는
옵션으로 LAN 바인딩) — `docs/.config.json`의 `features.auth`를 켜면 그때부터
`/api/auth/*`가 활성화된다. `git_log_ui`/`comments`는 평범에서 **기본 on**
이다(SP-00003 3절 프리셋).

**코멘트/git 이력 기능의 범위**: `docs/PROTOCOL.md`의 답변 대기(`- [ ]
(Qn)`)는 공식적으로 기록되는 결정 요청이고, 코멘트는 그와 별개로 문서에 대한
비공식 토론용이다 — 마크다운 파일에는 쓰지 않고 코멘트 저장소(6절)에만
남긴다. PR처럼 "브랜치를 나눠 변경을 제안 → 승인해야 병합"되는 흐름은 만들지
않는다(`DC`/`RV`/`FX` + 답변(RP) 절차가 이미 그 역할을 함). 라인 단위 코멘트도
이번 범위 밖 — 문서 단위 코멘트까지만.

### 2.1 답변(RP) 처리 — 파일 증식 방지

`POST /api/docs/:path/reply`는 Tier 1(Python)에서 이미 검증된 규칙을 그대로
따른다(`docs/PROTOCOL.md` 6절):

- `RP`는 별도 파일/테이블을 만들지 않는다. 답변 전문은 대상 문서 자체의
  "## 답변 기록" 섹션에 `### RP-XXXXX` 소제목으로 append하고, `RP-XXXXX`는
  그 소제목이 만드는 문서 내 앵커(`#rp-00005`)로만 존재한다.
- `- [x] (Qn) ... → RP-XXXXX` 링크도 같은 문서 안의 앵커를 가리킨다.
- `LG`는 (Tier 1과 동일하게) **대상 문서당 1개**를 find-or-create — 질문마다
  새 LG를 만들지 않고, 있으면 처리 내역 한 줄을 이어붙인다.

질문이 몇 개인 `DC`/`RV`/`FX`를 답변 처리해도 새로 생기는 파일은 최대 1개
(그 문서의 LG, 이미 있으면 0개)뿐이다 — Tier 1에서 "질문마다 RP 파일 하나"로
시작했다가 파일이 급격히 늘어나는 문제를 겪고 고친 설계이므로, Tier 2 구현
때 그 실수를 반복하지 않는다.

### 2.2 조회 성능 — 캐시

`core/`의 트리/목록/답변대기 조회 함수들은 매 요청마다 전체 `docs/**/*.md`를
다시 읽지 않는다. Tier 1과 같은 원칙(파일 mtime이 바뀌지 않았으면 재파싱하지
않음)을 따르되, 구현은 배포 형태에 맞춘다:

- `db.enabled`가 꺼져 있으면(평범 기본값): 백엔드 프로세스가 살아있는 동안
  유지되는 인메모리 캐시(mtime 키). Tier 1의 in-memory 캐시와 동일한 설계.
- `db.enabled`가 켜져 있으면: `docs_index` 테이블(SP-00001 6절)이 이미 이
  역할을 겸한다 — 조회는 파일이 아니라 DB를 읽는다.

## 3. MCP 도구

| `docs_get` | GET /api/doc |
| `docs_pending` | GET /api/pending |
| `docs_list` | GET /api/design, /api/logs, /api/all (type 인자로 분기) |
| `docs_search` | GET /api/search?q= |
| `docs_new` | POST /api/docs |
| `docs_save` | POST /api/doc/save(git 자동 커밋 없음 — `new`/`reply`/`transition-done`과 다름) |
| `docs_reply` | POST /api/docs/:path/reply |
| `docs_transition_done` | POST /api/plan/:id/transition-done |

| `docs_comment` | GET/POST /api/docs/:path/comments, POST .../resolve |

표에 없는 `docs_changes`(변경 추적 큐 조회/확인)도 등록되어 있다 — 5절
읽기 게이트의 실제 소비자가 Claude라서 추가한 도구.

Claude 쪽 사용 원칙: MCP 서버가 등록되어 있으면 이 도구들을 우선 사용한다. 등록
안 되어 있으면 CLI(4절)로 폴백한다. 어느 경로든 동일한 `core/`를 타므로 결과는

## 4. CLI

```
docs new <TYPE> --title "..." [--links ID,ID...]
docs save <path> <file>   # 본문 전체 갱신, git 자동 커밋 없음
docs reply <path> <question_id> <answer text>
docs tree
docs pending
docs list --type DC,RV,FX
docs search <query>      # 전문 검색
docs transition-done <PL-id>
docs git sync            # pull → commit → push
docs git commit [-m "..."]
docs git push
docs git pull
docs git log [--path ...]
docs git diff <sha>
docs comment <path> <text>
docs comment resolve <path> <comment-id>
```

Node 프로젝트에 로컬 설치되어 `npx docs ...`로 실행하거나, 전역 설치 시
`docs ...`로 실행.

## 5. git 자동화 규칙 (기본값)

| 시점 | 동작 |
|---|---|
| 세션/백엔드 기동 시 | `git pull` (충돌 시 설계자에게 알리고 중단, 자동 병합 시도 안 함) |
| `docs new` / `docs reply` / `transition-done` 성공 직후 | 해당 변경분 `git commit` (커밋 메시지는 작업 종류+대상 문서 번호로 자동 생성, 예: `docs: answer DC-00003 (Q1) → RP-00007`) |
| push 시점 | 기본은 즉시 push. `docs/.config.json`의 `git.push_mode`를 `immediate`(기본) 또는 `manual`(설계자가 `docs git push`로 직접) 로 설정 가능 |

이 규칙은 `docs/.config.json`으로 끌 수 있다(`git.enabled: false`) — 로컬
`docs/`가 애초에 git 저장소가 아닌 경우 자동으로 비활성화된다.

## 6. 선택적 서비스 DB

기능 토글 전반(`git_log_ui`/`comments`/`db`/`auth`)의 정의와 등급별 기본값은
[SP-00003](SP-00003.md) 3절이 원본이다. 코멘트는 `db`가 꺼져 있으면 내장
SQLite 파일에 저장되고, `db`를 켜면 아래 서비스 DB로 옮겨간다.

`docs/.config.json`:

```json
{
  "db": {
    "enabled": false,
    "driver": "mysql",
    "connection": { "host": "...", "port": 3306, "user": "...", "password": "...", "database": "..." }
  }
}
```

`driver`는 `mysql`(기본/메인) · `mariadb` · `postgres` · `sqlite` 중 선택.
데이터 접근은 Prisma로 구현해 드라이버만 바꾸면 동작하게 한다
([DC-00001](../decision/DC-00001.md) Q4 확정).

### DB를 켜면 생기는 것 — 캐시 테이블 vs 원본 데이터 테이블

```
docs_index(id, type, path, title, status, updated_at, links_json, reply_pending)   -- 캐시
doc_comments(id, doc_path, body, created_at, resolved_at)                          -- 원본 데이터
```

이 둘은 되돌릴 수 있는 정도가 다르다:

- **`docs_index`는 순수 캐시다.** `docs/*.md`를 다시 스캔하면 그대로 재생성되므로,
  DB를 끄든 지우든 데이터 손실이 없다.
- **`doc_comments`는 캐시가 아니라 원본 데이터다.** 마크다운 파일 어디에도 없는
  내용이라, `db.enabled`를 그냥 `false`로 바꾸기만 하면 그 순간 코멘트에
  접근할 방법이 없어진다(끄기 전엔 서비스 DB에, 끈 뒤엔 로컬 SQLite를 보므로).
  **그래서 `db.enabled`는 설정 파일을 직접 고쳐서 바꾸는 값이 아니라, 아래
  전용 명령으로만 전환한다** — 명령이 데이터 이관까지 책임진다.

### 켜기/끄기 절차 (양방향 무손실)

```
docs db enable --driver mysql --connection '<접속정보 JSON>'
  1. 지정한 서비스 DB에 연결 확인, 스키마 생성
  2. 로컬 SQLite(docs/.workflow/comments.db)의 doc_comments를 통째로 이관
  3. 행 개수가 일치하는지 검증한 뒤에만 docs/.config.json의 db.enabled=true 기록
  4. 로컬 SQLite 파일은 지우지 않고 보관(백업)

docs db disable
  1. 서비스 DB의 doc_comments를 로컬 SQLite(docs/.workflow/comments.db)로
     통째로 내보냄(기존 로컬 파일이 있으면 덮어쓰기 전 확인)
  2. 행 개수가 일치하는지 검증한 뒤에만 docs/.config.json의 db.enabled=false 기록
  3. 서비스 DB 쪽 테이블은 기본적으로 남겨둔다(즉시 삭제하지 않음) —
     `--drop` 옵션을 줘야 실제로 지운다
```

두 명령 모두 검증에 실패하면(연결 안 됨, 행 개수 불일치 등) 설정 파일을 건드리지
않고 실패로 끝난다 — "설정값만 바꿨는데 데이터가 붕 뜨는" 상태를 만들지 않는다.
`docs_index`는 어느 쪽이든 그냥 버리고 다음 요청에서 재생성한다(이관 대상 아님).

Tier 3([SP-00002](SP-00002.md))의 `users`/`projects`/`project_members`/
`refresh_tokens` 테이블과 같은 DB 계층(같은 ORM 설정)을 공유한다 — 평범에서
DB를 켜서 쓰던 프로젝트가 고급으로 옮겨가도 스키마와 `doc_comments` 데이터가
그대로 이어진다. (고급은 `db.enabled`를 끌 수 없으므로 `docs db disable`은
평범 등급에서만 의미가 있다 — SP-00002 참고.)
