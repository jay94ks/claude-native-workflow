# SP-00004 추론 흔적 추적 및 실시간 협업

설계 근거: [DS-00001](../design/DS-00001.md), [SP-00003](SP-00003.md) 5절
(변경 추적 큐)의 확장.

## 1. 배경

설계자와 Claude의 상호작용에서 다음은 지금 `docs/*.md`(`DC`/`RP`/`LG`)에
최종 결과만 남고, 과정 자체는 어디에도 구조화되어 남지 않는다(채팅
트랜스크립트에만 있음):

- 무엇이 이 변경을 촉발했는가(트리거)
- 무엇을 바꿨고 왜 바꿨는가
- 그 과정에서 어떤 의문이 생겼고, 그걸 풀려면 뭐가 필요한가
- Claude가 무엇을 추천했고, 왜 그렇게 추천했는가
- 설계자가 무엇을 답했는가

git 커밋 사이클(커밋 → 푸시 → 풀 → 병합)은 이런 과정을 실시간으로
공유하기엔 너무 느리고 거칠다 — 특히 설계자가 여러 명인 고급 등급에서는
이게 서로의 진행 상황을 알기 어렵게 만드는 병목이 된다. 그래서 이 흔적은
`docs/*.md`(정본, git 관리)와는 별도로 **Tier 2/3 서비스 계층**(이미 있는
DB+API)에 둔다.

## 2. 데이터 모델 — `trace_events`

```
trace_events
  id               uuid, PK
  project_id       uuid, FK -> projects.id   -- 고급만. 평범은 항상 단일 프로젝트라 null
  session_id       string        -- 하나의 Claude 대화/세션을 묶는 키
  kind             enum(trigger, change, question, recommendation, answer, note)
  actor            enum(designer, claude)
  doc_path         string null   -- 관련 문서(있으면)
  summary          text          -- 한 줄 요약
  detail           text null     -- 상세 근거/본문
  ref              string null   -- 관련 RP 앵커/DC id/commit sha 등
  parent_event_id  uuid null     -- 예: answer → 그 question, recommendation → 그 trigger
  created_at       datetime
```

append-only 이벤트 로그다. 전형적인 흐름 예시:

```
trigger      "설계자가 X 기능을 요청함"
  └ change       "SP-00002 §3에 role 표 추가"
       └ question     "조직 단위 테넌시를 지금 넣을지가 불확실"
            └ recommendation  "지금은 보류 추천 — 근거: 실제 수요 없이 스키마만
                                넓히면 YAGNI 위반, project_members로 충분"
                 └ answer          "설계자: 보류, 나중에 별도 DS"
```

`parent_event_id`로 이 체인을 재구성할 수 있다.

## 3. API

```
GET  /api/projects/:id/trace?since=<cursor>&session=&doc_path=   폴링(기본, REST)
POST /api/projects/:id/trace                                     이벤트 기록
GET  /api/projects/:id/trace/stream                               실시간 스트림(선택, 5절)
```

`docs new`/`docs reply`/`transition-done` 등 core의 문서 조작 함수가 성공할
때마다 관련 `trace_events`를 자동으로 남기도록 훅을 건다 — 설계자나 Claude가
매번 수동으로 기록할 필요는 없다. `question`/`recommendation`은 Claude가
`AskUserQuestion`류 상호작용을 할 때 core를 통해 남긴다.

## 4. 기능 토글 — `features.realtime`

[SP-00003](SP-00003.md) 3절의 토글 체계를 그대로 따른다.

| 등급 | 기본값 | 의미 |
|---|---|---|
| 초간단 | 해당 없음 | 단일 설계자·단일 프로세스라 실시간 공유가 의미 없다. `trace_events` 자체를 만들지 않는다(이번 범위 밖). |
| 평범 | `false`(켤 수 있음) | 로컬에서 여러 프로세스/기기가 같은 프로젝트를 볼 때 유용(예: 노트북+데스크톱). |
| 고급 | `false`가 기본, 켜는 걸 권장 | 다중 설계자 협업의 핵심 가치라 여기서 가장 의미 있다. |

꺼져 있으면 `GET /trace?since=`로 폴링만 가능(REST 위에 가벼움 — 인프라
추가 없음). 켜면 `/trace/stream`으로 새 이벤트가 연결된 대시보드에 즉시
푸시된다.

## 5. 푸시 메커니즘 — SSE (WebSocket 대신)

설계자가 요청한 건 "웹소켓 기반 진짜 실시간"이었는데, 요구사항을 뜯어보면
**서버 → 여러 클라이언트로 새 이벤트를 단방향 브로드캐스트**하는 것이지
클라이언트가 소켓으로 뭔가 보내야 하는 양방향 상호작용은 아니다. 이 경우
Server-Sent Events(SSE)로도 체감 지연은 동일하면서 구현이 훨씬 단순하다
(순수 HTTP, 별도 프로토콜 업그레이드·연결 관리 라이브러리 불필요 — Express
에서 몇 줄로 구현 가능). 그래서 1차 구현은 SSE로 하고, 정말 클라이언트→서버
방향의 실시간 상호작용(예: 여러 설계자가 커서 위치를 공유하는 등)이
필요해지면 그때 WebSocket으로 바꾼다. 이 판단에 동의하지 않으면 바로
WebSocket으로 가도 된다 — API 모양(4절)은 동일하게 유지되므로 전환 비용은
크지 않다.

## 6. 대시보드

- 문서 뷰 하단 또는 별도 "활동" 탭에 관련 `trace_events` 타임라인을 표시
  (트리거 → 변경 → 질문 → 추천 → 답변 체인을 그대로 보여줌).
- `realtime`이 켜져 있으면 새 이벤트가 새로고침 없이 SSE로 바로 나타난다.
- 꺼져 있으면 탭을 열 때/일정 주기로 폴링.

## 7. 이번 범위 밖

- 동시 편집(OT/CRDT 기반 공동 편집) — 이건 "누가 뭘 했는지 실시간으로
  안다"이지 "여러 명이 동시에 같은 텍스트를 고친다"가 아니다.
- 초간단(Tier 1)의 `trace_events` 저장 — 단일 사용자라 우선순위 낮음.
- WebSocket으로의 전환(5절 참고, 필요해지면 나중에).
