# SP-00002 고급(Tier 3) 인증/계정 명세

설계 근거: [DS-00001](../design/DS-00001.md). [SP-00001](SP-00001.md)의 로컬
API·`core/`를 그대로 이어받아, 인증·다중 설계자·클라우드 배포를 얹은 것.

## 1. 설계자 계정

ID/PW 기반. 소셜 로그인·SSO는 이번 범위 밖(향후 확장 지점으로만 남김).

```
users
  id            uuid, PK
  username      string, unique
  email         string, unique
  password_hash string   -- argon2id
  created_at    datetime
  updated_at    datetime
```

- 회원가입 시 비밀번호는 서버에서 argon2id로 해시하여 저장, 평문은 저장/로그
  하지 않는다.
- 아이디/이메일 중복 체크는 가입 API에서 처리.

## 2. 인증 토큰

Access token(JWT, 단명, 예: 15분) + Refresh token(장기, 예: 30일, DB에
해시로 저장해서 서버 측에서 폐기 가능) 조합.

```
refresh_tokens
  id            uuid, PK
  user_id       uuid, FK -> users.id
  token_hash    string        -- 원문은 저장하지 않음
  issued_at     datetime
  expires_at    datetime
  revoked_at    datetime null
```

| 엔드포인트 | 설명 |
|---|---|
| `POST /api/auth/register` | `{username, email, password}` → 계정 생성 |
| `POST /api/auth/login` | `{username_or_email, password}` → `{access_token, refresh_token}` |
| `POST /api/auth/refresh` | `{refresh_token}` → 새 `access_token`(+ 회전된 `refresh_token`) |
| `POST /api/auth/logout` | `{refresh_token}` → 해당 refresh token 폐기(`revoked_at` 기록) |

이후 모든 API 호출은 `Authorization: Bearer <access_token>` 헤더 필요.

### 클라이언트(Claude 쪽) 토큰 보관

Skill이 안내하는 얇은 REST 클라이언트는 발급받은 토큰을 프로젝트 저장소
**밖**의 설계자 홈 디렉터리 설정 파일(예: `~/.claude-native-workflow/
credentials.json`, 파일 권한 600)에 보관한다. `docs/`나 git 저장소 안에는
토큰을 절대 커밋하지 않는다 — `.gitignore`에 관련 패턴을 기본 포함.

이 REST 클라이언트는 `docs3` CLI([tier3/backend](../../tier3/backend))로
구현됐고, 이를 Claude에게 안내하는 Skill은
[tier3/skill/.claude/skills/docs3-cli/SKILL.md](../../tier3/skill/.claude/skills/docs3-cli/SKILL.md)
가 참조 원본이다(설치 방법은 [tier3/skill/README.md](../../tier3/skill/README.md)).

## 3. 프로젝트/테넌시와 권한

MVP는 **프로젝트 단위** 테넌시만 지원한다(조직 단위 묶음은 이번 범위 밖,
향후 `organizations` 테이블을 얹어 확장 가능한 구조로만 남긴다).

```
projects
  id            uuid, PK
  name          string
  git_repo_url  string        -- 이 프로젝트의 docs/ 가 사는 git 저장소
  created_at    datetime

project_members
  project_id    uuid, FK -> projects.id
  user_id       uuid, FK -> users.id
  role          enum(owner, editor, viewer)
  joined_at     datetime
  PK(project_id, user_id)
```

| role | 할 수 있는 것 |
|---|---|
| `viewer` | 문서 조회만(GET류 전체) |
| `editor` | 조회 + 문서 생성/답변/전환(POST류) + git commit/push |
| `owner` | editor 권한 전부 + 멤버 초대/제거/역할 변경, 프로젝트 설정(연결된 git 저장소, DB 등) 변경 |

**이 role은 REST API 경로에만 적용된다.** 설계자가 프로젝트의 git 저장소에
대한 clone/push 권한을 별도로 갖고 있다면(git 호스팅사의 자체 권한 설정),
`viewer`로 등록되어 있어도 git 경로로는 직접 편집·커밋·푸시할 수 있다 —
이 시스템이 막을 방법도, 막을 필요도 없다(DS-00001 "설계자는 항상 문서를
직접 편집할 수 있다" 원칙). API role은 "REST API로 무엇을 허용할지"만
결정한다.

## 4. REST API (SP-00001의 로컬 API를 프로젝트 네임스페이스 + 인증으로 감쌈)

```
/api/projects/:projectId/tree
/api/projects/:projectId/doc?path=
/api/projects/:projectId/pending
/api/projects/:projectId/design
/api/projects/:projectId/logs
/api/projects/:projectId/all
/api/projects/:projectId/docs            POST
/api/projects/:projectId/docs/:path/reply POST
/api/projects/:projectId/plan/:id/transition-done POST
/api/projects/:projectId/git/commit|push|pull POST
```

라우트/요청·응답 형식은 [SP-00001](SP-00001.md) 2절과 동일하고, 앞에
`/api/projects/:projectId`가 붙고 인증 미들웨어(JWT 검증 + `project_members`
role 확인)가 추가될 뿐이다 — 그래서 평범 등급용으로 짠 클라이언트 로직을
고급 등급에서도 거의 그대로 재사용할 수 있다. 위 목록엔 없지만 실제로도
같은 패턴으로 존재하는 라우트: `search`/`validate`/`doc/save`(SP-00001과
동일), `git/log`·`blame`·`commits/:sha`·`diff/:sha`(읽기 전용 이력),
프로젝트별 코멘트(`docs/:path/comments` GET/POST, `.../resolve` POST),
변경 큐(`changes` GET, `changes/:id/ack` POST) — `docs3` CLI가 이 전부를
1:1로 감싼다([tier3/skill](../../tier3/skill/.claude/skills/docs3-cli/SKILL.md)
"명령 전체 목록" 참고).

프로젝트 관리용 엔드포인트:

```
POST   /api/projects                 프로젝트 생성(생성자가 owner)
GET    /api/projects                 내가 속한 프로젝트 목록
POST   /api/projects/:id/members     멤버 초대 {user_id 또는 email, role}
PATCH  /api/projects/:id/members/:userId   role 변경
DELETE /api/projects/:id/members/:userId   멤버 제거
```

## 5. git 동기화

- API 경로로 들어온 변경은 서버가 해당 프로젝트의 git 저장소에 자동 commit한다
  (커밋 작성자는 실제 요청한 설계자 이름/이메일로 기록해 감사 이력을 남긴다).
- `POST /api/webhooks/git`(GitHub 웹훅 수신 — [DC-00002](../decision/DC-00002.md#rp-00007)
  Q3에서 1차 지원 범위를 GitHub로 확정, GitLab은 수요가 보이면 이후 추가) —
  다른 설계자가 로컬에서 직접 clone→편집→push한 경우, 웹훅으로 push 이벤트를
  받아 서버 측 캐시(DB의 `docs_index` 등)를 최신화한다. 웹훅 검증(서명 확인)은
  GitHub의 표준 방식(HMAC-SHA256 서명 헤더)을 따른다.
- push 충돌(API 경로와 git 경로가 동시에 같은 파일을 바꾼 경우)은 이번 범위에서
  "먼저 도착한 쪽이 반영되고 나중 쪽은 실패 응답 + 재시도 안내"로 단순하게
  처리한다. 3-way 병합 자동화는 범위 밖(향후 과제로 명시).

## 6. 데이터베이스

[SP-00001](SP-00001.md) 6절의 DB 계층을 그대로 확장한다. MySQL 메인, 특정
DB에 종속되지 않는 ORM(Prisma, [DC-00001](../decision/DC-00001.md#rp-00004))
사용. Tier 3에서는 DB 활성화가 기본값(비활성 옵션 없음 — 계정·권한 자체가
DB 없이는 성립하지 않음).

**MySQL 다음 지원 우선순위**([DC-00002](../decision/DC-00002.md#rp-00008)
Q4에서 확정): PostgreSQL → SQLite 순서로 드라이버를 추가한다. MariaDB는
MySQL 커넥터로 이미 호환되므로 별도 구현이 필요 없어 우선순위에서 제외했다.

## 7. 배포 (호스팅·시크릿)

- **호스팅 위치**: 지금은 특정 벤더를 정하지 않는다 — Docker/Docker Compose
  기반이라 어떤 컨테이너 호스팅에서도 동작하며, 실제 배포처는 운영 상황
  (비용/팀 인프라)에 맞춰 나중에 정한다
  ([DC-00002](../decision/DC-00002.md#rp-00005) Q1).
- **환경변수/시크릿 관리**: dotenv + 배포 플랫폼 기본 시크릿 매니저. Vault
  같은 별도 도구는 이번 범위에서 도입하지 않는다
  ([DC-00002](../decision/DC-00002.md#rp-00006) Q2).

## 8. 웹 대시보드 — Tier 2 협업 기능의 다중 설계자 확장

커밋 이력/diff/blame/코멘트 자체는 등급 공통 기능이라 이미
[SP-00003](SP-00003.md) 2절 + [SP-00001](SP-00001.md) 2~3절에 정의되어 있다
(고급에서는 `/api/projects/:projectId/git/...`, `/api/projects/:projectId/
docs/:path/comments`처럼 프로젝트 네임스페이스가 붙을 뿐, 라우트 모양과
`doc_comments` 스키마는 동일 — `doc_comments.project_id`로 프로젝트별로
분리된다). 고급 등급이 대시보드에 **추가로** 얹는 것은:

- **프로젝트 선택/전환 UI**: 내가 속한 여러 프로젝트 중 하나를 골라 들어가는
  화면(`GET /api/projects` 기반).
- **멤버 관리 화면**: 3절 role과 4절 멤버 API를 붙인 초대/역할 변경 화면.
- 커밋 히스토리 타임라인에는 5절 웹훅으로 동기화된 git 경로 커밋과 API 경로
  자동 커밋이 같이 보인다(이 부분은 데이터 소스가 늘어난 것일 뿐 화면 자체는
  SP-00001과 동일).

명확히 범위 밖(브랜치 제안/승인 병합 흐름, 라인 단위 코멘트)으로 두는 것은
[SP-00001](SP-00001.md)에 이미 명시했다.

## 9. 이번 범위 밖 (명시적 보류)

- 소셜 로그인/SSO/OAuth
- 조직(organization) 단위 테넌시
- 3-way 자동 병합(git 경로 vs API 경로 동시 수정 충돌)
- PR 방식의 브랜치 제안/승인 병합 흐름, 라인 단위 코멘트(위 8절 참고)
