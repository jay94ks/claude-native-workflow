# DN-00001 워크플로우 재구성 실행 계획 (3개 배포 등급)

계획 원문: [PL-00001](../plan/PL-00001.md)

## 결과 보고

3개 배포 등급(초간단/평범/고급) 전부 구현하고 실제 환경에서 검증까지
완료했다.

- **초간단(Tier 1)**: 파일 기반 로컬 워크플로우, Python(stdlib only)
  대시보드. 문서 CRUD/답변 흐름, git 이력/diff/코멘트, 변경 추적 큐,
  본문 편집기까지 전부 실제 대시보드로 검증.
- **평범(Tier 2)**: Node/TypeScript 백엔드 하나(`core/`)를 MCP·CLI·REST
  API·Quasar 대시보드가 공유하는 구조로 재구현. git 자동화(commit/push/
  pull), 이력/diff/코멘트, 변경 큐, 선택적 서비스 DB(Prisma —
  mysql/postgres/sqlite), Docker 패키징까지 10개 하위 단계 전부 실제
  프로세스를 띄우고 CLI/API/MCP/대시보드로 직접 클릭·호출해 검증.
- **고급(Tier 3)**: Tier 2 백엔드를 로컬 패키지 의존성으로 확장(코드
  재작성 없이 재사용) — 계정/인증(argon2id + JWT + 회전형 refresh
  token), 프로젝트 단위 테넌시·권한(owner/editor/viewer), git 웹훅
  동기화(GitHub HMAC 서명 검증), 요청자 본인 이름으로 남는 커밋 감사
  이력, 다중 설계자 대시보드(프로젝트 선택/멤버 관리 — 문서 조회 화면
  자체는 Tier 2 컴포넌트를 그대로 재사용), Docker Compose 배포(MySQL
  포함), `docs3` REST CLI와 이를 Claude에게 안내하는 Claude Code Skill까지
  전부 실제 서버·컨테이너를 띄워 검증.

이 계획을 진행하며 "실제로 띄우고 눌러본다"는 검증 방식을 매 단계
일관되게 지킨 결과, 설계 단계에서는 드러나지 않았을 실제 버그를 다수
발견해 바로잡았다 — 대표적으로 Tier 2에서는 `git pull` 직후 변경 요약이
항상 비어 있던 문제, 답변 제출 후 대시보드 패널이 새로고침되지 않던
문제, Docker 컨테이너의 `127.0.0.1` 바인딩으로 인한 502; Tier 3에서는
프로세스 전역 상태 때문에 생길 뻔한 다중 프로젝트 동시성 버그(구현 전
설계 검토로 선제 차단), 두 계층에 나뉜 git 자동 커밋 설정이 서로
충돌하던 문제, 웹훅 서명 검증의 버퍼 길이 비교 누락, MySQL 컨테이너의
2단계 기동 과정과 얽힌 healthcheck 경쟁 상태 등. 각 버그의 발견 경위와
수정 내용은 아래 계획 원문과 `DESIGN-NOTES.md`의 세션별 기록에 상세히
남아 있다.

세 등급 모두 완료됐고, 후속 확장(등급 간 자동 마이그레이션, 조직 단위
테넌시, git 3-way 자동 병합)은 이 계획의 범위 밖으로 명시적으로
남겨뒀다 — 필요해지면 별도 `DS`/`SP`로 다시 설계한다.

## 계획 원문

설계 근거: [DS-00001](../design/DS-00001.md) · [SP-00003](../spec/SP-00003.md)
(공통 API 계약) · [SP-00001](../spec/SP-00001.md)(평범) ·

### 0단계. 저장소 구조 준비

- `tier1/`(초간단 참조 원본 + 대시보드) 분리 완료 — `bootstrap-prompt.md`도
  여기서 재생성되도록 정리됨.
- `tier2/`(Node 백엔드+Quasar 대시보드+Docker) 신설. 폴더 구조는
  [DC-00001](../decision/DC-00001.md) Q1에서 **B안**(tier2를 base로, tier3가
  확장)으로 확정됐다 — 즉 `tier3/`는 별도 전체 사본이 아니라, `tier2/backend`를
  참조/확장하는 얇은 레이어(인증·멀티테넌시·클라우드 배포 설정 차이만)로
  둔다.
- 루트 `docs/`(이 저장소 자신의 워크플로우 기록)는 그대로 유지.

### 1단계. 초간단(Tier 1) 정리 + 공통 API 계약 반영 — 완료

**완료된 부분** (`tier1/tools/docs/server.py` 실제 구현·실제 대시보드로 전부
검증함, 계획이 아니라 실적):

- 문서 CRUD/답변 흐름 `tier1/`로 이동, `scripts/build_prompt.py` 경로 갱신.
- `docs/PROTOCOL.md` 6절대로 `RP`를 파일 없이 대상 문서에 직접 기록하도록
  `answer_pending()` 재작성 — 질문이 몇 개든 늘어나는 파일이 최대 1개(LG)로
  제한됨(원래 "질문마다 RP 파일 1개"로 시작했다가 파일이 급증해서 고침).
  `LG`도 대상 문서당 1개로 find-or-create.
- `scan_meta`(구 `get_doc_meta`) — mtime+size 2단계 캐시로 정밀화, 콜드
  스타트가 아닌 변경 감지 시 `change_notices`를 적재(SP-00003 5·6절 읽기
  게이트). **직접 파일을 손으로 고친 변경도 다음 조회에서 실제로 잡힘**을
  확인(원래 설계가 놓치고 있던 경로).
- `GET /api/changes` / `POST /api/changes/:id/ack`(변경 큐),
  `GET /api/doc?path=&anchor=`(부분 읽기), `GET /api/search?q=`(전문 검색).
- `git log`/`git diff`/`git blame` 읽기 전용 엔드포인트(`subprocess`) —
  Windows에서 `text=True`가 로케일 인코딩(cp949)으로 디코드하다 한글이
  깨지는 실제 버그를 발견해 `encoding="utf-8"`로 고침.
- 코멘트 저장/조회/해결 엔드포인트(stdlib `sqlite3`,
  `docs/.workflow/data.db`, gitignore 대상).
- `docs validate` — `docs/PROTOCOL.md` 3절 규칙을 그대로 코드화한 손수 작성
  검증기(`GET /api/validate` + `--validate` CLI 플래그). 형식적인
  `schemas/*.schema.json` 추출은 Tier 2가 생겨 드리프트를 대조할 대상이
  생겼을 때로 미룸(그 전엔 검증기가 하나뿐이라 정합성 테스트 자체가 의미
  없음).
- 대시보드: 변경 큐 배너, 커밋 히스토리+diff 뷰, 코멘트 스레드, 답변
  다이얼로그에 (a) 이 문서가 `links`로 연결한 관련 SP/DS/PL 문서를 펼쳐
  보여주는 참고 패널, (b) `- 권장:`/`- 대안:` 옵션 원클릭 채우기(설계자 요청
  으로 추가 — `docs/PROTOCOL.md` 4절에 표기 규칙 반영)를 붙임.
- **문서 본문 편집기**(설계자 요청으로 추가, 원래 계획엔 없었음): 각 문서
  뷰의 "편집" 버튼으로 굵게/취소선/제목/코드/링크 툴바가 달린 마크다운
  편집 모드 진입, `POST /api/doc/save`로 저장. **프론트매터는 건드리지
  않음**(id/type/status/links는 여전히 답변 처리나 Claude와의 대화로만
  바뀜) — 저장 전 `docs validate`와 같은 검증을 통과해야 실제로 쓰여짐.
  `docs/PROTOCOL.md` 8절에 반영.

완료 기준 전부 실제 대시보드에서 확인함: 답변 플로우 그대로 동작, git
이력/diff 렌더링, 코멘트 작성/해결, 직접 편집이 변경 큐에 잡힘, `docs
validate`가 의도적으로 깨뜨린 문서(잘못된 `status`/`created` 형식/`id`
불일치/`links` 패턴 오류)를 정확히 잡아냄, 본문 편집기로 저장한 파일의
프론트매터가 그대로 보존됨.

### 2단계. 평범(Tier 2) — [SP-00001](../spec/SP-00001.md) 구현 — 완료

순서대로 진행(각 항목이 다음 항목의 전제):

1. **`backend/src/core/`** — 완료. `docs/PROTOCOL.md` 규칙을 TypeScript로
   포팅(frontmatter parse/dump, `.tracking.json` 기반 번호 발급, mtime+size
   읽기 게이트 캐시, 답변대기 스캔, `docs validate`, 문서 생성, RP-폴딩 답변
   처리, `PL→DN` 전환, 색인 표 재생성). Tier 1(Python)에서 검증된 로직을
   그대로 이식 — 새 설계 없이 포팅 위주로 진행함. 실제로 검증한 것과 다른
   결정 2가지:
   - `PL→DN` 전환 스텁은 `docs/PROTOCOL.md` 5절 예시(`{id, type, status}`
     3필드만)가 아니라 `created`/`updated`/`links`(새 `DN`을 가리킴)도 유지 —
     3필드 스텁은 7절 필수 필드 규칙(검증)을 스스로 어겨서, 쓰기 경로가
     저장 전 검증을 통과해야 한다는 원칙(SP-00003 7.3절)과 맞지 않음.
   - `POST /api/docs`(문서 생성)는 Tier 1에 없던 새 능력 — Tier 1은 대시보드가
     생성을 하지 않고 Claude가 파일을 직접 쓰지만, SP-00003 2절 라우트
     표와 SP-00001 4절 CLI(`docs new`)가 이미 이 라우트를 전제하고 있어
     Tier 2부터는 API로도 문서를 생성할 수 있게 구현(대상 타입의
     `index.md` 표에 행을 자동으로 붙이거나 "아직 문서 없음" 자리를
     치환함).
   - `change_notices`/`trace_events`(SP-00003 5·6절 읽기 게이트의 알림
     절반)는 아직 미구현 — git 자동화(5번)·변경 큐(7번) 단계에서 저장소가
     생긴 뒤에 붙인다. 지금은 mtime+size 캐시(게이트의 "캐시" 절반)만 있음.
   - `tsc --noEmit` 통과 + 실제로 서버를 띄우고(스캐치 `docs/` 사본에)
     Tier 1과 동일 시나리오(문서 생성 → 답변대기 질문 추가 → 답변 처리 →
     RP 앵커/LG 파일/색인 갱신 확인 → 앵커 부분 읽기 → `PL→DN` 전환 →
     `docs validate` 재확인)를 `curl`/`node --eval fetch`로 끝까지 확인함
     (curl에 한글을 직접 넘기면 Windows 콘솔 코드페이지 때문에 깨지는
     것도 확인 — 이건 이 리포 코드 버그가 아니라 curl 호출 쪽 문제라 Node
     `fetch`로 우회 테스트).
2. **`backend/src/api/`** — 완료(1번 core가 다루는 범위만). `GET /api/tree`,
   `/api/doc`(`&anchor=`), `/api/pending`, `/api/design`, `/api/logs`,
   `/api/all`, `/api/search`, `/api/validate`, `POST /api/doc/save`,
   `POST /api/docs`, `POST /api/docs/:path/reply`(슬래시 포함 경로라
   `:path` 대신 정규식 라우트로 캡처),
   `POST /api/plan/:id/transition-done`. git/comments/changes 라우트는
   해당 core 모듈이 붙는 5~7번에서 추가.
3. **`backend/src/cli/`** — 완료. SP-00001 4절 중 core가 이미 다루는 부분만
   (`commander`): `docs tree`/`pending`/`design`/`all`/`get <path>`/
   `new <type> --title --links`/`reply <path> <qid> <answer...>`/
   `transition-done <id> --report`/`validate`, 전역 `--root`. api/server.ts와
   마찬가지로 core를 직접 호출(HTTP를 거치지 않음). `git`/`comment` 하위
   명령은 5~6번 core가 생긴 뒤 추가. `--root`를 서브커맨드 앞뒤 어디에
   둬도 동작함을 확인(commander의 전역 옵션 상속).
4. **`backend/src/mcp/`** — 완료. `@modelcontextprotocol/sdk`로 SP-00001 3절
   중 core가 다루는 7개 도구(`docs_tree`/`docs_get`/`docs_pending`/
   `docs_list`/`docs_new`/`docs_reply`/`docs_transition_done`)를 등록,
   core 직접 호출. `git_log`/`docs_comment`는 6번에서 추가(`git_sync`는
   5번에서 추가됨 — 아래).
   MCP SDK의 `Client`+`StdioClientTransport`로 실제 서버 프로세스를 띄워
   7개 도구를 전부 호출하는 시나리오(2번 API 검증과 동일한 시나리오)로
   검증 — 한글 인자도 JSON-RPC 경유라 깨지지 않음을 확인(2번에서 발견한
   curl 콘솔 인코딩 문제와 무관).
5. **git 자동화** — 완료. `core/config.ts`(`docs/.config.json` 로더, 기본값
   포함) + `core/git.ts`(`simple-git`)로 SP-00001 5절 구현:
   - `docs new`/`docs reply`/`transition-done` 성공 직후 `docs/`만 자동
     `git add`+commit(메시지는 작업 종류+대상 문서 번호, 예:
     `docs: answer DC-00003 (Q1) → RP-00007`), `push_mode: immediate`(기본)면
     이어서 push까지. 이 셋 모두 core 함수 시그니처가 `Promise`로
     바뀌어(git 호출이 비동기라) `api`/`cli`/`mcp` 호출부도 전부 `await`로
     맞춤(Express 4는 동기 throw만 자동으로 에러 미들웨어로 보내서, 비동기
     라우트는 `asyncRoute` 래퍼로 감싸 `next(err)`에 명시적으로 연결).
   - `docs git pull`/`commit`/`push`/`sync` — CLI 하위 명령 + `POST
     /api/git/pull|commit|push|sync` + MCP `git_sync` 도구.
   - 백엔드(`api/server.ts`)와 MCP 서버(`mcp/server.ts`) 기동 시 자동
     `git pull`("세션/백엔드 기동 시"). 충돌이면 자동 병합을 시도하지
     않고 그대로 보고만 하고(로그/도구 결과), 서버는 계속 뜬다.
   - `docs/`가 git 저장소가 아니거나 `docs/.config.json`의
     `git.enabled: false`면 모든 git 동작이 조용히 no-op(`attempted: false`).
   - 실 bare 저장소 + 두 개의 클론("설계자 A/B")으로 검증: A의 `docs new`가
     자동 commit+push되어 origin에 실제로 도착 → B가 만든 커밋을 A가
     `docs git pull`로 정상 반영 → 같은 줄을 양쪽에서 고쳐 진짜 merge
     conflict를 만들고 `docs git pull`이 자동 병합 없이 그대로 보고하는지
     확인(`git status`로 conflict marker가 실제로 남아있음까지 확인 후
     `git merge --abort`로 정리) → `push_mode: manual`이면 commit은 되지만
     push는 안 됨, 이후 수동 `docs git push` → non-fast-forward 거부까지
     확인 → API `/api/git/*` 라우트도 동일 시나리오로 재확인.
   - 검증 중 발견한 버그: `pull()`의 실패 결과를 전부 `conflict: true`로
     표시하고 있었다(원격 없음/upstream 미설정 같은 진짜 충돌이 아닌
     실패까지 "충돌"로 오분류). git 출력에 `CONFLICT`가 실제로 있을 때만
     `conflict: true`로 좁혀서 고치고, 두 케이스(진짜 충돌/그 외 실패)를
     각각 재현해 구분되는지 재확인.
6. **git 이력/diff/blame + 코멘트** — 완료. `core/gitlog.ts`(`simple-git`
   `log()`/`show()`/`raw(["blame",...])`로 Tier 1의 subprocess 기반
   git_log/git_commit_detail/git_diff/git_blame과 동일한 정보 제공,
   포맷 문자열을 직접 파싱하는 대신 simple-git의 구조화된 `log()` 사용) +

      실제로 렌더링되는 것까지 전부 확인 후 `down` + 이미지/스캐치 폴더
      정리.

완료 기준: Tier 1에서 검증한 것과 동일한 시나리오(문서 열람 → 답변 대기 카드 →
답변 제출 → RP/LG 생성 → 색인 갱신 → 상태 전이)가 Quasar 대시보드 + Node
백엔드에서 동일하게 재현되고, 그 과정에서 `docs/`가 자동으로 git commit됨을
확인 — **완료**(대시보드/CLI/API/MCP 전부 실 시나리오로 검증). 코멘트를
몇 개 작성한 뒤 `docs db enable` → `docs db disable`을 연달아 실행해 코멘트가
한 개도 유실되지 않는지까지 확인 — **완료**(8번). 다른 클라이언트가
`docs/`를 바꾼 뒤 `git pull`을 실행하면 diff를 직접 돌리지 않고도 변경 큐에
항목이 잡히고, `ack` 후 큐에서 사라지는지 확인 — **완료**(7번, 대시보드
배너로도 재확인). "문서 변경사항을 추적해서 계획이나 승인할 거 있으면
업데이트해줘" 프롬프트로 Claude가 큐를 읽고 `links`로 영향받는 문서를
찾아 갱신 요약을 제시하는 시나리오(SP-00003 5절)는 **Claude의 대화 습관에
대한 것이라 도구 자체의 완료 기준이 아니므로 별도 자동화 테스트 대상은
아님** — 지금 세션도 실질적으로 그 패턴(변경 큐 확인 → 관련 문서 갱신)을
따르고 있음.

Docker 이미지/compose까지 끝나 **2단계(평범/Tier 2) 전체가 완료**됐다 —
core/api/cli/mcp/git 자동화/git 이력·코멘트/변경 큐/선택적 DB/대시보드/
Docker 10개 항목 전부 실제로 띄우고 클릭·호출해 검증. 진행하며 실제로
잡은 버그 목록(전부 이 문서와 `DESIGN-NOTES.md`에 각 단계별로 기록):
읽기 게이트 diff 요약이 `git pull` 직후엔 항상 실패하던 것(7번), 자기
자신이 만든 변경이 변경 큐에 스팸처럼 쌓이던 것(9번, `invalidateCache`
누락), 대시보드가 답변 후 열린 패널을 안 새로고침하던 것(9번), Docker
컨테이너 안 `127.0.0.1` 바인딩으로 프록시가 502를 내던 것(10번) — 전부
"실제로 띄우고 눌러본다"는 이 세션의 반복된 검증 방식이 아니었으면
못 잡았을 것들.

### 3단계. 고급(Tier 3) — [SP-00002](../spec/SP-00002.md) 구현

Tier 2 백엔드 코드베이스를 확장한다(새로 만들지 않음) — 구체적으로는
`tier3/backend`가 `tier2/backend`를 로컬 패키지 의존성으로 참조해 `core/`
함수를 그대로 재사용하고, 그 위에 인증/프로젝트/웹훅만 얹는 얇은 레이어로
간다(DC-00001 RP-00001의 "B안" 결정).

**착수 전 발견한 선행 문제(0번, SP-00002엔 없던 항목)**: `tier2/backend`의
`core/`는 애초에 "프로세스 하나 = 프로젝트 하나"를 전제로 설계됐다 —
`paths.ts`가 "현재 프로젝트 루트"를 프로세스 전역 변수 하나로 들고 있고
(`setProjectRoot()`), `docstore.ts`의 읽기 게이트 캐시도 `docs/` 기준
상대경로를 키로 쓴다. 그런데 SP-00002 4절의 `/api/projects/:projectId/...`
설계는 **프로세스 하나가 여러 프로젝트를 동시에 처리**하는 걸 전제한다 —
두 요청이 인터리빙되면 (a) 전역 루트 변수를 서로 덮어써서 요청 A가 프로젝트
B의 `docs/`를 건드리거나, (b) 두 프로젝트에 동명 파일(`spec/SP-00001.md`
같은)이 있으면 캐시가 서로의 내용을 섞어 보여줄 수 있다 — 실제로 겪은
버그가 아니라 Tier 3를 얹기 전에 설계를 보고 미리 판단한 것.
- `paths.ts`를 `AsyncLocalStorage`로 바꿨다 — Tier 2(CLI/API/MCP)가 쓰는
  `setProjectRoot()`는 그대로 두되(`enterWith`로 남은 실행 전체에 적용,
  기존 동작 안 바뀜), Tier 3용으로 `runWithProjectRoot(root, fn)`을
  추가해서 요청 하나의 비동기 체인에만 루트를 격리한다. `core/`의 다른
  파일들은 전부 `getProjectRoot()`/`docsDir()`를 그대로 호출하므로 한 곳만
  고치면 됐다.
- `docstore.ts`의 `metaCache`를 `docs/` 상대경로 키에서 **절대경로** 키로
  바꿨다 — 상대경로는 서로 다른 프로젝트의 동명 파일을 같은 캐시 항목으로
  착각할 수 있지만, 절대경로는 그럴 일이 없다.
- 검증: (1) 기존 Tier 2 CLI 시나리오(문서 생성/트리/검증)가 그대로 동작하는
  회귀 테스트, (2) `runWithProjectRoot`로 서로 다른 두 프로젝트를 일부러
  인터리빙(A 시작 → 50ms 대기 중 B 시작+완료 → A 재개+완료)시켜 각자
  자기 루트만 보고, 파일도 각자의 `docs/`에만 정확히 쓰이는지 직접 확인.
1. **DB 스키마** — 완료. `users`/`refresh_tokens`/`projects`/
   `project_members` 모델을 세 스키마 파일(mysql/postgres/sqlite) 전부에
   추가(SP-00002 1~3절) — Tier 2의 `docs_index`/`doc_comments`와 같은 ORM
   설정 공유. `role`은 Prisma `enum`이 아니라 평문 `String`으로 뒀다
   (sqlite 변형엔 네이티브 enum이 없어서 세 provider 공통 표현이 이거뿐 —
   값 검증은 애플리케이션 코드 담당). `doc_comments`에 `project_id`(nullable)
   를 추가 — SP-00002 8절 "모든 프로젝트가 하나의 서비스 DB를 공유하고
   project_id로 나눈다"는 요구사항 때문(프로젝트별로 DB 커넥션을 따로 두는
   게 아님). 세 스키마 전부 `prisma generate` 통과 확인, 기존 Tier 2
   코멘트+서비스 DB enable/disable 플로우가 스키마 확장 후에도 그대로
   동작하는 것까지 재확인(회귀 테스트).
**`tier3/backend`를 새로 만들었다** — `tier2/backend`를 `file:../../tier2/
backend`로 참조하는 별도 npm 패키지(DC-00001 RP-00001 "B안" 그대로).
npm의 `file:` 의존성이 이 환경(Windows)에서 심볼릭 링크로 걸려서
`tier2/backend`의 `dist/`·`generated/`(Prisma 클라이언트)를 그대로 깊은
경로로 import할 수 있다는 것도 실제로 확인. 단 `tier2/backend/tsconfig.json`
의 `declaration`을 `false`→`true`로 바꿔야 했다 — 라이브러리로 소비되는
게 이번이 처음이라, 그동안 `.d.ts`를 안 만들어도 됐던 것.

2. **인증** — 완료. `tier3/backend/src/core/auth.ts`: `argon2id` 비밀번호
   해시, JWT(15분) access token, 고엔트로피 난수 + SHA-256 해시 저장 방식의
   refresh token(30일, 원문은 저장 안 함 - SP-00002 2절). `POST /api/auth/
   {register,login,refresh,logout}`. refresh는 **회전(rotation)** 방식 —
   쓴 토큰은 그 자리에서 바로 폐기하고 새로 하나 내준다(탈취된 토큰이
   재사용되면 그 순간 이미 폐기돼 있어 막힘). 실제로 회원가입→로그인→
   refresh→(같은 토큰 재사용 시도 → 실패 확인)→logout→(로그아웃 후 재사용
   시도 → 실패 확인)까지 curl로 전부 재현.
3. **프로젝트 네임스페이스** — 완료. `core/projects.ts`(생성/멤버 초대·
   역할변경·제거/목록), `middleware/auth.ts`의 `authenticate`(JWT 검증) +
   `requireProjectRole(minRole)`(SP-00002 3절 role 표 그대로 owner>editor>
   viewer 랭크 비교) + `withProjectRoot()`. **`api/server.ts`는 tier2의
   `api/server.ts`(Express 앱)를 마운트하지 않고, tier2의 `core/` 함수를
   똑같이 직접 호출한다** — SP-00001 1절의 "MCP/CLI/API가 서로를 거치지
   않고 같은 core를 직접 호출한다" 원칙을 tier3도 그대로 따른 것(mount
   방식은 `/api/projects/:id/api/tree`처럼 경로가 이중으로 겹쳐 SP-00002
   4절이 원하는 모양과도 안 맞았음). `POST /api/projects`(생성 - 생성자가
   owner) 시 `core/workspace.ts`가 `git_repo_url`을 `TIER3_PROJECTS_DIR/
   <projectId>/`로 clone. 실제로 두 계정(생성자=owner, 초대받은 사람=처음
   viewer→나중 editor로 승격)으로 트리 조회(둘 다 200) → viewer가 문서
   생성 시도(403) → editor로 승격 후 재시도(성공) → 답변 대기 질문에
   editor가 답변(성공)까지 curl로 재현.
4. **git 동기화** — 완료(커밋 작성자 지정 + 웹훅 서명 검증 + 웹훅 캐시
   갱신 전부).
   - `core/workspace.ts`의 `commitAsAndPush`가 요청한 설계자의 이름/이메일로
     커밋한다(SP-00002 5절). 그런데 tier2의 `core/create.ts`/`reply.ts`/
     `transition.ts`는 저장 직후 **자기도** 자동 commit+push를 한다
     (SP-00001 5절, 저장소에 설정된 고정 git user로만) — 그대로 두면 커밋이
     두 번 생기고 작성자도 엉뚱하게 남는다. `core/` 자체를 고치는 대신,
     프로젝트 clone 직후 그 체크아웃의 `docs/.config.json`에서
     `git.enabled=false`를 써서 tier2 쪽 자동 커밋을 꺼버리고, tier3가
     매 요청 끝에서 직접 올바른 작성자로 커밋하도록 함 — 실제로 owner와
     editor가 각각 만든 커밋의 author가 정확히 그 사람 이름/이메일로
     남는 것과, bare 저장소까지 실제로 push되는 것을 `git log`로 확인.
   - `POST /api/webhooks/git` — GitHub 표준 방식(HMAC-SHA256, `X-Hub-
     Signature-256`)으로 서명 검증(SP-00002 5절). 이 라우트만 전역
     `express.json()`보다 **앞서** `express.raw()`를 등록해뒀다 — 안 그러면
     전역 파서가 스트림을 먼저 소비해서 HMAC 검증에 필요한 원문 바이트가
     없어진다(실제로 짜면서 바로 알아채고 고침, 배포 전 발견). 검증 성공/
     서명 없음/서명 불일치 세 케이스를 curl로 확인하다가 진짜 버그
     하나 발견: `crypto.timingSafeEqual`은 두 버퍼 길이가 다르면 (상수
     시간 비교가 아예 불가능하니) **예외를 던진다** — 공격자가 짧거나
     이상한 길이의 서명 헤더를 보내면 그게 그대로 `asyncRoute`의 catch로
     빠져서 401이 아니라 500류의 내부 에러 메시지가 담긴 400으로 샜다.
     길이를 먼저 비교하고 다르면 바로 401로 처리하도록 고침 — 세 케이스
     (정상 서명/짧은 서명/길이는 맞지만 틀린 서명) 전부 재확인.
   - **웹훅 캐시 최신화도 이어서 완료**. `core/projects.ts`의
     `findProjectsByRepoUrl`이 웹훅 페이로드의 `repository.{clone,html,
     ssh}_url`을 정규화(프로토콜/`.git`/대소문자 차이를 무시)해서 저장된
     `git_repo_url`과 매칭되는 프로젝트를 찾고, 매칭된 각 프로젝트의
     체크아웃에서 `runWithProjectRoot`로 스코프해 tier2의 `pull()`을
     실행한다 — "캐시 최신화"의 실체는 pull이 로컬 파일을 최신 커밋으로
     맞추는 것뿐이고, 그다음 어떤 조회든 읽기 게이트가 알아서 diff를
     감지해 변경 큐에 올린다(2단계 7번에서 이미 만든 경로를 그대로 씀,
     여기서 다시 구현 안 함).
   - **웹훅을 실제로 연결하다가 tier2/tier3 사이의 설계 충돌을 하나 더
     발견**: 프로젝트 clone 직후 tier2의 자동 커밋을 끄려고 써둔
     `git.enabled=false`가, tier3가 자체적으로 쓰려는 `pull()`/`push()`
     까지 전부 막아버렸다 — `gitAutomationEnabled()`가 `enabled` 하나로
     "쓰기 후 자동 커밋"과 "pull/push 명령 자체"를 함께 게이팅하고
     있었기 때문. 웹훅 pull이 "git 자동화가 꺼져 있습니다"로 막히는 걸
     실제로 보고서야 발견 — tier2의 `GitConfig`에 `auto_commit`(기본
     `true`)을 새로 추가해서 "쓰기 후 자동 커밋만 끄기"와 "git 자체를
     못 쓰게 막기"를 분리하고, `afterWrite()`가 `auto_commit`만 보게
     고침. tier3는 이제 `auto_commit=false`만 쓰고 `enabled`는 그대로
     `true`로 둠. tier2 자체의 fallback 동작(설정 파일 없을 때 기본값)이
     안 바뀌었는지 회귀 테스트로 재확인, 웹훅 pull이 이제 정상 동작하는
     것도 처음부터 다시(새 프로젝트로) 재현해 확인.
5. **클라이언트 토큰 보관** — 완료. "Skill이 안내하는 얇은 REST 클라이언트"
   자체를 `tier3/backend`에 `docs3` CLI(`src/cli/index.ts`)로 구현했다.
   - `core/credentials.ts`: `~/.claude-native-workflow/credentials.json`
     (파일 권한 600)에 `api_base`/`access_token`/`refresh_token` 저장 —
     프로젝트 저장소 밖이라 그 자체로 어떤 프로젝트의 `.gitignore`와도
     무관하다(SP-00002 2절 "docs/나 git 저장소 안에는 토큰을 절대
     커밋하지 않는다"를 코드 경로 자체로 만족).
   - `core/apiclient.ts`: 저장된 access token으로 호출하고, 401을 받으면
     refresh token으로 갱신(회전된 새 refresh token도 같이 다시 저장 —
     안 하면 다음 401 때 이미 폐기된 토큰을 씀) 후 재시도.
   - `docs3 login/logout/whoami/projects/project-create/members/invite/
     tree/doc/pending/new/save/reply/transition-done/git {commit,push,
     pull}`. tier2의 CLI와 달리 core를 직접 호출하지 않는다 - REST
     클라이언트가 로컬 파일을 가질 이유가 없어서(서버가 어딘가 원격에
     있고, 이 CLI는 그 REST API를 부르는 게 전부). `save`(문서 본문 전체
     갱신)는 처음엔 빠져 있다가 Skill 문서를 쓰며 발견해 나중에 추가했다
     (아래 참고).
   - 실제 검증: `os.homedir()`가 실제 사용자 홈을 가리키므로, 테스트
     전체를 `USERPROFILE`/`HOME`을 스캐치 디렉터리로 override해서 진행
     (진짜 홈 디렉터리를 절대 안 건드리고, 테스트 후 실제로 안 건드렸는지
     따로 확인). `docs3 login` → 자격 증명 파일 생성 확인 → `whoami`/
     `project-create`/`new`/`tree`/`pending`/`reply`(한글 인자 포함)까지

     지워지는 것까지 확인.

     RP-00006 "dotenv + 배포 플랫폼 기본 시크릿 매니저"). `mysql` healthcheck를
     처음엔 `-proot`로 하드코딩했다가 실제 비밀번호와 안 맞는 버그를 바로

있고, Tier 2를 실제로 채택하는 **다른** 프로젝트엔 전혀 전달되지 않는다는
걸 놓친 판단이었다.

바로잡은 내용:
- `tier2/skill/.claude/skills/docs-cli/SKILL.md` + `tier2/skill/README.md`를
  `tier3/skill`과 같은 패턴(참조 원본, 이 저장소 자신은 미사용)으로 신설.

  없었다는 걸 재확인 — `POST /api/doc/save`(대시보드 편집기가 이미 쓰고
  있던 라우트)는 있는데 CLI/MCP만 안 뚫려 있었다. `docs save <path>
  <file>`, MCP `docs_save`를 추가.
- 이 명령을 검증하다가 **진짜 버그를 하나 발견** — Skill 문서(tier2/tier3
  둘 다)에 "로컬 파일(프론트매터 포함 전체 마크다운)을 그대로 넘긴다"고
  잘못 적어놨었다. 실제로는 `saveDocBody`가 받은 문자열을 그대로 새
  프론트매터 뒤에 이어붙이므로(`dumpFrontmatter(meta, body)`), 프론트매터를
  포함해서 넘기면 저장된 파일 안에 프론트매터 블록이 **두 번** 겹쳐
  들어간다 — 스크래치 환경에서 실제로 재현해서 확인(대시보드 편집기가
  쓰는 `doc.body`엔 애초에 프론트매터가 없다는 것도 `DocViewer.vue`
  코드로 재확인). 두 Skill 문서 모두 "본문만 넘긴다, 프론트매터는 절대
  포함하지 않는다"로 정정하고, tier2/tier3 양쪽 다 본문만 넘긴 재현
  테스트로 깨끗하게 저장되는 것까지 재확인.
- `tier2/backend/npm run build`·`tier3/backend/npm run build` 둘 다 재확인
  (tier3가 tier2를 `file:` 의존성으로 참조하므로 tier2 변경이 tier3
  빌드를 깨지 않는지까지).
- 겸사겸사 저장소 전체를 스캔해서(문서 검증기 + 상대링크 스캐너) 실제
  깨진 링크 하나(`SP-00003.md`가 `tier1/tools/docs/server.py`를
  `../`가 하나 많은 경로로 가리킴)와, `PL-00001` 전환 이후 안 고쳐둔
  "구현 노트는 PL-00001 N단계 참고" 링크 여러 개(README.md 두 곳,
  DC-00001/DC-00002, SP-00003 — 전부 `DN-00001`을 가리키게 정정)도
  같이 잡았다.

### tier3 CLI 전체 재검증(같은 방식으로 한 번 더)

설계자가 "tier3 CLI도 같은 방식으로 한번 더 검증해줘"라고 요청해서, 이번엔
개별 명령이 아니라 **`tier3/backend/src/api/server.ts`의 라우트 전체를
`docs3` CLI 명령과 1:1 대조**하는 방식으로 훑었다. 결과: `save` 하나가
아니라 **15개 명령이 통째로 빠져 있었다** — `register`(가입 경로 자체가
없음), `design`/`logs`/`all`/`search`/`validate`(읽기 목록·검증),
`git log`/`blame`/`show`/`diff`(이력 조회 — `commit`/`push`/`pull`만
있었음), `comment list`/`add`/`resolve`, `changes list`/`ack`, 멤버
역할변경/제거(`PATCH`·`DELETE .../members/:userId` 라우트는 있는데
대시보드만 그걸 쓰고 CLI엔 없었음). tier2의 `docs` CLI엔 이미 다 있던
것들이라 규모 차이가 크다는 걸 이번에 제대로 확인했다 — 규모가 커서
전부 추가할지 먼저 확인받은 뒤 진행.

15개 명령을 전부 추가하면서 진짜 버그를 하나 더 잡았다 - `git/blame`·
`git/diff/:sha` 라우트는 `res.type("text/plain").send(...)`로 순수
텍스트를 돌려주는데, 기존 `apiCall<T>()`는 항상 `res.json()`을 부르므로
그대로 쓰면 파싱 에러가 난다. `core/apiclient.ts`를 리팩터링해서
인증/refresh 로직을 공유하는 내부 `apiFetch()`로 뽑아내고, JSON용
`apiCall()`과 텍스트용 `apiCallText()`로 나눴다 - 스크래치 서버에서
`git blame`/`git diff`가 실제로 읽을 수 있는 텍스트를 돌려주는 것까지
확인.

`changes <projectId>`를 tier2처럼 인자 없는 명령으로 만들 수 없다는 것도
설계하면서 알아챘다 - tier2의 `docs changes`는 프로젝트가 하나뿐이라
인자가 없어서 `docs changes ack <id>` 서브커맨드와 안 겹치지만, tier3는
`<projectId>`가 꼭 필요해서 `changes <projectId>`로 두면 `ack`
서브커맨드와 위치 인자가 모호해진다. `git`/`comment`처럼 `changes`
자체를 `list`/`ack` 서브커맨드를 가진 그룹으로 바꿔 피했다(`docs3
changes list <projectId>` / `docs3 changes ack <projectId> <id>`).

검증은 스크래치 환경(bare 저장소 + SQLite 서비스 DB)에 실제 서버를
띄우고 새로 추가한 15개 명령을 **전부** 실행해서 확인했다 - `register`
→ `login` → `project-create` → `design`/`logs`/`validate`(빈 프로젝트라
전부 `[]`) → `new`로 SP 생성 → `all`/`search`(한글 검색어) → `save`
(본문만, 이전에 고친 규칙대로) → `new`로 DC 생성 → `save`로 답변 대기
질문 추가 → `pending` → `reply` → `comment add`/`list`/`resolve` →
`git log`(실제 커밋 이력, 매 명령이 요청자 이름 `fulltest`로 커밋된 것
확인) → `git show`/`diff`/`blame`(텍스트 응답 정상 확인) → 두 번째
계정 가입 → `invite` → `members` → `member-role`(editor로 변경 확인)
→ `member-remove`(제거 확인) → `git commit`/`push`/`pull` → `logout`.
`changes ack`는 실제 변경 알림을 재현하지 않고 라우트/명령 배선만
확인(다른 명령들과 동일한 패턴이라 저위험으로 판단).

스크래치 셋업 중 실수 하나도 겪었다 - bare 저장소를 `git init --bare`로
만든 뒤 `main` 브랜치에만 push했는데, 이 환경의 git 기본 브랜치가
`master`라서 bare 저장소의 `HEAD`는 계속 (커밋 없는) `master`를
가리키고 있었다. 그 상태로 `project-create`를 호출하니 clone은
성공하지만 작업 트리가 완전히 비어서 `docs/.config.json`을 못 찾는
`ENOENT`가 났다 - tier3 코드 버그가 아니라 테스트 셋업 실수라는 걸
`git branch -a`/`HEAD` 확인으로 바로 잡아내고, `master`에 다시
push해서 해결.

`tier2/skill`과 마찬가지로 `SKILL.md`의 "명령 전체 목록"에 15개를
전부 반영하고, `SP-00002` 4절(REST API 라우트 목록)에도 표에 없던
라우트(search/validate/doc-save/git 이력/코멘트/변경 큐) 존재를
명시하는 문장을 추가했다. `tier2/tier3 backend` 둘 다 재빌드 확인,
전체 문서 검증기 + 링크 스캐너 재실행, 스크래치 환경·백그라운드 서버
정리, 실제 홈 디렉터리 안 건드림.

### tier2 CLI/MCP도 같은 방식으로 라우트 전체 대조

이어서 "tier2 CLI도 같은 방식으로 전체 라우트 대조해줘"라는 요청으로
`tier2/backend/src/api/server.ts`의 라우트 25개 전부를 `docs` CLI +
MCP 도구와 1:1 대조했다. tier3와 달리 tier2는 이미 거의 완비돼 있었고
**빠진 건 `search` 하나뿐**이었다 — `GET /api/search?q=` 라우트는
있는데 CLI(`docs search`)도 MCP(`docs_search`)도 없었다. `docs
search <query>` CLI 명령과 `docs_search` MCP 도구를 추가하고, 스크래치
환경에서 문서를 하나 만든 뒤 한글 검색어로 CLI와 MCP 양쪽 다 실제
검색 결과가 나오는 것까지 확인했다. `tier2/skill`의 SKILL.md와
`SP-00001` 3·4절에도 반영. `tier2/tier3 backend` 재빌드 확인, 문서
검증기 재실행, 스크래치 환경 정리.

이걸로 tier2/tier3 두 CLI(및 tier2 MCP) 모두 실제 REST 라우트 표면과
완전히 1:1로 맞춰졌다.

### tier1 — "CLI"가 아니라 대시보드 UI와 라우트를 대조

"tier1 CLI도 같은 방식으로 전체 대조해줘"라는 요청을 받았는데, 실제로는
전제부터 정정이 필요했다 — Tier 1은 애초에 CLI가 없다(DS-00001 설계
그대로: Claude는 `docs/*.md`를 직접 Read/Edit/Bash로 편집하고
`docs/reply/index.md`를 직접 확인하지, HTTP API를 부르지 않는다).
그래서 같은 방법론을 적용할 수 있는 유일한 대상은 `tier1/tools/docs/
server.py`의 백엔드 라우트 vs 그 **유일한 실제 소비자**인 대시보드
프론트엔드(`static/app.js`) - Claude가 아니라 사람 설계자가 쓰는
화면이다.

라우트 25개와 `static/app.js`가 실제로 호출하는 `api(...)` 지점을
전부 대조해서 준동문(백엔드엔 있는데 프론트가 전혀 안 쓰는 라우트)
4개를 찾았다:
- `GET /api/pending`(전체 미답변 목록) - 화면엔 지금 열어본 문서
  안의 질문만 보여주는 클라이언트 측 `scanPending()`만 있고, 프로젝트
  전체를 훑는 화면이 없었다.
- `GET /api/search?q=` - 백엔드는 완성돼 있는데 `index.html`에
  검색창 자체가 없었다.
- `GET /api/git/blame` - 이력 화면에 diff는 있는데 blame 보기가 없었다.
- `GET /api/git/commits/:sha` - 커밋 클릭 시 diff만 보여주고, 구조화된
  "변경된 파일" 목록은 안 보여주고 있었다.

규모(dependency-free vanilla JS 프론트엔드 수정)를 먼저 확인받은 뒤
4개 전부 연결했다 - 사이드바에 검색창(입력 시 트리를 검색 결과로
대체, 지우면 트리 복귀), "답변 대기" 탭 신설(문서 전체 미답변 질문을
한 화면에, 클릭하면 해당 문서를 열고 바로 답변 다이얼로그까지 띄움),
커밋 이력 섹션에 "blame 보기" 토글 버튼, 커밋 클릭 시 diff 위에
"변경된 파일" 목록을 같이 표시. 기존 `loadList()`/`loadHistorySection()`
을 크게 안 건드리고 얹는 방향으로 짰다.

검증은 스크래치 프로젝트(pending 질문 있는 DC 문서 + git 커밋 3개)에
`server.py`를 별도 포트로 띄워 브라우저로 직접 확인했다 - 검색(한글
쿼리, 결과 클릭, 지우면 트리 복귀), 답변 대기 탭(클릭 시 문서+답변
다이얼로그 동시에 열림, 옵션 원클릭까지), blame 토글, 커밋 클릭 시
파일 목록+diff 동시 표시, 기존 "문서" 탭 회귀 없음까지 확인. 브라우저
콘솔 에러 없음.

이 과정에서 진짜 사고를 하나 낼 뻔했다 - 스크래치 서버를 처음엔
포트 8760으로 띄웠는데, 이 저장소에서 동시에 작업 중인 **다른 세션**
(`claude-native-workflow-44`)이 이미 그 포트에서 저장소 루트를 `--root
.`로 가리키는 자기 대시보드를 띄워두고 있었다 - 새 프로세스가 그
포트에 제대로 안 붙고 기존(다른 세션 소유) 프로세스가 계속 응답해서,
처음엔 내가 만든 스크래치 문서가 아니라 **이 저장소의 진짜 운영
문서**가 뜨는 걸 보고 당황했다. 다른 세션의 프로세스는 건드리지
않고 내 스크래치 서버만 다른 포트(8799)로 다시 띄워서 해결 - 읽기
전용 GET 호출 몇 개 말고는 그 세션에 아무 영향도 주지 않았다.

### QA 확대: tier2/dashboard(Quasar)도 같은 준동문 패턴 발견 - 3개 연결

설계자가 "QA 진행하면서 미비되거나 보완해야될걸 찾으면서 문서화도 하고
커밋, 푸시도 단위별로 진행하도록 해"라고 지시해서, tier1에서 찾은 것과
같은 패턴("클라이언트가 백엔드 라우트/메서드를 갖고 있는데 화면엔 아무도
안 부름")을 tier2/dashboard(Quasar, tier1보다 훨씬 풍부한 컴포넌트
라이브러리를 쓰는 SPA)에도 적용해봤다.

`tier2/dashboard/src/api.ts`의 `client` 객체를 실제 `.vue` 파일들이
부르는 지점과 대조 - `validate`/`gitBlame`/`gitCommit`(구조화된 파일
목록) 3개가 완전히 준동문이었다(`search`는 `ReplyDialog.vue`가 링크
ID→경로 변환용으로 내부적으로만 쓰고 있어서 사람이 쓰는 검색창은
역시 없었음 - tier1과 똑같은 증상). 전체 문서를 훑는 "답변 대기" 뷰도
`App.vue`엔 tree/design/logs 3탭뿐이라 없었다(`DocViewer.vue`가 `client.
pending()`을 부르긴 하지만 현재 연 문서로 필터링해서 보여줄 뿐).

tier1에서 만든 것과 같은 4가지를 이번엔 Quasar 컴포넌트로 연결했다 -
`App.vue` 사이드바에 검색 입력(디바운스, 결과가 트리/탭을 대체, 지우면
복귀), "답변 대기" 탭 신설(전체 미답변 질문, 클릭하면 곧장 그 문서를
열고 답변 다이얼로그까지 뜸 - `DocViewer` 안에서 여는 경로와 별개로
`onReplyFromPendingTab`을 새로 만듦, `currentDoc`을 직접 채워야
`ReplyDialog`의 참고 문서 링크가 동작하기 때문), 헤더에 "검증" 버튼
(`client.validate()` 결과를 다이얼로그로), `DocViewer.vue`의 커밋 이력
섹션에 "blame 보기" 토글과 커밋 클릭 시 "변경된 파일" 목록(`client.
gitCommit()`)을 diff 위에 추가. `api.ts`에 원래 없던 `SearchResult`
타입도 새로 만들어 `search()`의 실제 반환 모양(`snippet` 포함, 기존
`DocListItem[]` 타입은 부정확했음)에 맞췄다.

`tier3/dashboard`가 `DocViewer.vue`/`DocTree.vue`를 상대경로로 그대로
재사용하므로, blame·커밋 파일 목록은 tier3에도 자동으로 같이 적용된다
(별도 작업 불필요) - 다만 검색/전체 답변 대기/검증은 tier3가 자기
`App.vue` 격인 `DashboardView.vue`를 따로 갖고 있어서 그쪽은 별도로
봐야 한다(다음 QA 단위).

검증: `tier2/dashboard`와 `tier3/dashboard` 둘 다 `vue-tsc -b` 통과
확인 후, 스크래치 프로젝트(pending 질문 있는 DC 문서 + 실제 git
커밋)에 `tier2/backend`+`tier2-dashboard` dev 서버를 띄워 브라우저로
직접 확인 - 검색(결과 클릭, 지우면 트리 복귀), 답변 대기 탭(클릭 시
문서+다이얼로그 동시 오픈), blame 토글, 커밋 클릭 시 파일 목록+diff
동시 표시, "검증" 다이얼로그("모든 문서가 유효합니다")까지 전부 확인,
콘솔 에러 없음. 스크래치 서버/환경 정리.

### QA 단위 이어서: tier3/dashboard의 `DashboardView.vue`에도 동일 적용

예고한 대로 다음 QA 단위 - tier3는 `App.vue`를 안 쓰고 자기 `Dashboard
View.vue`(프로젝트 헤더+역할 배지+멤버/pull/전환 버튼)를 따로 갖고
있어서 검색/전체 답변 대기/검증이 tier2 쪽 수정만으로는 안 딸려왔다.
같은 3가지(검색 입력, "답변 대기" 탭+`onReplyFromPendingTab`, 헤더
"검증" 버튼+다이얼로그)를 `DashboardView.vue`에도 그대로 옮겨 붙였다 -
`DocViewer.vue`를 상대경로로 재사용하는 덕에 blame·커밋 파일 목록은
이미 공짜로 따라와 있었으니 이걸로 tier3도 tier2와 완전히 같은
기능 집합을 갖추게 됐다.

검증은 실제 Tier 3 스택(스크래치 bare 저장소+SQLite 서비스 DB로
`tier3/backend`를 띄우고 `tier3-dashboard` dev 서버 연결)에서 했다 -
`docs3` CLI로 계정 생성·프로젝트 생성·pending 질문 있는 DC 문서까지
미리 만들어두고, 브라우저로 로그인 → 프로젝트 진입 → 검색(결과 클릭
확인) → "답변 대기" 탭(클릭 시 문서+답변 다이얼로그 동시 오픈, 커밋
이력에 실제 요청자 이름 `qatest`로 남은 것도 같이 확인) → "검증"
버튼(다이얼로그에 "모든 문서가 유효합니다") 전부 확인, 콘솔 에러
없음. `vue-tsc -b` 통과도 재확인. 스크래치 환경/백그라운드 서버 정리.

이걸로 tier1/tier2/tier3 세 대시보드 전부 같은 QA 방식(백엔드가 갖고
있는 기능인데 화면에 안 뚫려 있는 것 찾기)을 한 바퀴 돌았다.

### QA 확대: validator 정합성 재확인 + 선택적 서비스 DB 실기 검증에서 진짜 버그 발견

두 가지를 추가로 점검했다.

**1) `docs/PROTOCOL.md` 3절 검증 규칙이 Tier1(Python)·Tier2(TypeScript)
두 엔진에서 여전히 1:1로 일치하는지** — SP-00003 7.4절 "정합성 원칙"이
명시적으로 요구하는 것. `tier1/tools/docs/server.py`의 `validate_doc`과
`tier2/backend/src/core/validate.ts`의 `validateDoc`을 줄 단위로 대조
(id required/pattern/consistency, type required, created·updated
required/pattern, status required/enum + `STATUS_ENUM` 값까지, links
type/pattern) - 전부 정확히 일치, 드리프트 없음. 겸사겸사
`tier1/tools/docs/server.py --validate` 플래그도 정상 문서/의도적으로
깨뜨린 문서 양쪽으로 실제 실행해 exit code(0/1)까지 확인 - 문제 없음.

**2) 선택적 서비스 DB(`docs db enable/disable`, SP-00001 6절 "양방향
무손실")를 실제 PostgreSQL로 검증** — 이 세션 전체에서 지금까지 이
기능은 항상 SQLite를 "서비스 DB" 대역으로 세워놓고만 테스트해왔다(진짜
MySQL/PostgreSQL로 검증한 적이 한 번도 없었음). Docker로 실제
`postgres:16-alpine` 컨테이너를 띄워 처음으로 진짜 검증했다.

첫 `enable`(로컬 코멘트 1개 → 서비스 DB로 이관, 행 개수 일치 확인)은
정상 동작했다. 그런데 `disable`(기본값 `--drop` 없음 - 서비스 DB
쪽 행은 안 지워짐, 로컬 SQLite로만 회수) 후 **다시 `enable`하니
`Unique constraint failed on the fields: (id)`로 실패**했다 - 실제로
재현해서 원인을 봤다: 이전 사이클에서 서비스 DB에 남아있던 행(id 1, 2)
위에 로컬 상태(같은 id 1, 2)를 그대로 `create()`하려 해서 기본키가
충돌한 것. `disable`이 로컬 쪽은 `replaceLocalComments`로 지우고
다시 채우는데(대칭적으로 무손실), `enable`은 서비스 DB 쪽을 안
지우고 무조건 `create()`만 해서 생긴 비대칭 버그 - "enable→disable
을 --drop 없이 한 번이라도 거치면 그다음 enable은 항상 실패한다"는
뜻이라, 문서가 말하는 "양방향 무손실" 토글이 실제로는 **두 번째
사이클부터 깨져 있었다**.

`enableServiceDb`에 `disableServiceDb`의 `replaceLocalComments`와
대칭되는 처리를 추가해서 고쳤다 - 서비스 DB에 `create()`하기 전에
먼저 `deleteMany()`로 비운다(disable 단계에서 이미 로컬로 전부
회수해둔 뒤라 로컬이 최신 진실이므로, 서비스 DB의 남은 행은 지워도
안전). 고친 뒤 `enable → disable(기본, --drop 없음) → enable →
disable(--drop) → enable` 5단계 전체 사이클을 실제 postgres로 다시
돌려서 매 단계 행 개수와 실제 내용(`psql`로 직접 조회)까지 확인,
전부 깨끗하게 통과. `tier2/tier3 backend` 재빌드 확인. 컨테이너/
스크래치 환경 정리.

고친 게 특정 드라이버에만 우연히 맞은 건 아닌지 확인하려고, SP-00001
6절이 "메인"이라 부르는 MySQL로도 실제 `mysql:8` 컨테이너를 띄워
같은 회귀 시나리오(첫 enable → disable(기본) → 재enable)를 재현했다 -
수정 전이었다면 여기서도 똑같이 실패했을 조합인데 깨끗하게 통과.
`mysql` CLI로 직접 조회했을 때 한글이 깨져 보인 건 그 CLI 클라이언트
자체의 문자셋 표시 문제였고(이 세션에서 반복적으로 겪은 것과 같은
종류), `docs comment list`(애플리케이션 자신의 JSON 출력)로 다시
확인하니 완전히 정상 - 실제 데이터 손상이 아니었다. 컨테이너/스크래치
환경 정리.

### QA: 저장형 XSS(stored XSS) 진짜 취약점 발견 + 수정

관점을 바꿔서 보안 쪽을 봤다 - `tier2/dashboard`(그리고 그대로 재사용
하는 `tier3/dashboard`)의 `DocViewer.vue`가 문서 본문을 `marked.parse()`
→ `v-html`로 렌더링하는데, `marked`는 마크다운 소스에 섞인 raw HTML을
기본적으로 그대로 통과시킨다(별도 sanitize 옵션이 v5+에서 제거됨) -
반면 `tier1`의 손수 짠 렌더러는 `inline()`에서 처음부터 `&`/`<`/`>`를
이스케이프하고 그 위에 마크다운 문법만 다시 여는 구조라 애초에 이
문제가 없다.

스크래치 프로젝트에 `<img src="x" onerror="...">`를 본문에 심은 문서를
만들어 실제로 재현했다 - 브라우저에서 열자마자 `onerror` 핸들러가
실행돼 `window.__xssFired`가 세팅되고 탭 제목까지 "XSS-FIRED"로
바뀌는 것을 직접 확인했다. **저장형 XSS가 실제로 동작하는 진짜
취약점**이었다 - 문서 본문을 쓸 수 있는 사람(로컬 tier2 사용자,
또는 tier3에서 editor/owner 권한)이면 누구나 그 문서를 여는 다른
사람의 브라우저에서 임의 스크립트를 실행시킬 수 있었다는 뜻이다.
tier3처럼 여러 설계자가 서로 다른 신뢰 수준(owner/editor/viewer)으로
같은 프로젝트를 보는 구조에서는, editor 권한만 있어도 owner의
브라우저에서 스크립트를 실행시켜 `localStorage`에 든 로그인 토큰을
훔쳐가는 권한 상승 공격까지 이론적으로 가능했다.

`tier2/dashboard`에 `dompurify`를 추가하고(자체 타입을 이미 내장하고
있어 `@types/dompurify`는 설치했다가 다시 뺐다), `marked.parse()` 결과를
`v-html`에 넣기 전에 `DOMPurify.sanitize()`로 한 번 걸러내도록 고쳤다 -
`v-html`을 쓰는 곳이 이 한 군데뿐이라는 것도 grep으로 확인(같은 컴포넌트의
`ReplyDialog.vue`는 문서 본문을 이미 `{{ }}` 텍스트 보간으로만 보여줘서
애초에 안전했음). 같은 페이로드로 재검증 - `onerror`가 더는 실행되지
않고(`window.__xssFired`가 세팅 안 됨, 탭 제목 그대로), `<img>` 태그
자체나 `<b>raw html bold</b>` 같은 안전한 raw HTML은 그대로 정상
렌더링되는 것까지 확인(위험한 이벤트 핸들러만 걷어내고 구조는 보존 -
과도한 차단으로 정상 마크다운/HTML이 깨지지 않음). `tier2/tier3
dashboard` 둘 다 `vue-tsc -b`와 `vite build`(프로덕션 빌드) 통과 확인 -
`dompurify`가 tier2/backend의 `file:` 의존성과 같은 방식으로 tier3가
그대로 재사용하는 것도 확인(별도 설치 불필요, Docker 이미지 빌드
과정도 그대로 재사용됨). 스크래치 환경 정리.

### QA: 경로 순회(path traversal) 진짜 취약점 발견 + 수정(tier1/tier2 둘 다)

XSS를 고치고 나서 관련된 보안 경계를 하나 더 훑었다 - `docs/` 밖 접근을
막는 `isInsideDocs`류 검사가 `getDoc`/`saveDocBody` 같은 문서 CRUD
경로엔 있는데, git 이력류 함수(`gitLog`/`gitBlame`, tier1 Python의
`git_log`/`git_blame`)엔 아예 없다는 걸 코드 대조로 알아챘다.

같은 git 저장소 안에(하지만 `docs/` 밖에) 비밀 파일을 하나 두고
`GET /api/git/blame?path=../SECRET.txt`를 실제로 호출해서 재현 -
**그 파일 전체 내용이 blame 출력 그대로 응답에 실려 나왔다.** 진짜
경로 순회 취약점이었고, `git/log`/`git/blame`은 `viewer` 권한만 있어도
호출되는 읽기 전용 라우트라(Tier 3 기준) 위험도가 실제로 높았다 -
쓰기 권한이 전혀 없는 사람도 같은 저장소 안의 `docs/` 밖 파일(예:
`.env`, 다른 소스 코드)을 git 이력을 통해 읽어갈 수 있었다는 뜻이다.
`gitCommitDetail`(방금 만든 "변경된 파일" 목록 기능이 쓰는 함수)도
같이 봤더니, `git show --stat`에 `-- docs`처럼 범위를 좁히는 pathspec이
없어서 `docs/`와 다른 파일을 같이 바꾼 커밋의 "변경된 파일" 목록에
`docs/` 밖 파일명이 그대로 새어나가는 것도 확인(내용은 아니고 경로
뿐이지만 이것도 `docs/` 밖 정보).

`tier2/backend/src/core/gitlog.ts`에 `assertInsideDocs()` 헬퍼를 추가해
`gitLog`/`gitBlame`이 `resolveInDocs()`만 하고 끝나던 걸 `isInsideDocs()`
검사까지 하도록 고치고(범위 밖이면 `NotFoundError`→404), `gitCommitDetail`/
`gitDiff`(이건 이미 스코프돼 있었음)도 `-- docsDir()`로 통일했다. 같은
문제가 `tier1/tools/docs/server.py`의 Python 구현에도 그대로 있다는 걸
확인해서 `resolve_in_docs_or_raise()` 헬퍼로 대칭으로 고쳤다(`git_log`/
`git_blame`/`git_commit_detail` 전부).

재현했던 그대로(`../SECRET.txt`)로 재검증 - tier2/tier1 둘 다 이제
404/에러로 막히고, 정상적인 `docs/` 안 경로(`spec/SP-00001.md`)는
그대로 잘 동작(회귀 없음), `docs/`와 `SECRET.txt`를 같이 바꾼 커밋의
"변경된 파일" 목록에서도 `SECRET.txt`가 더는 안 보이는 것까지 확인.
`tier2/tier3 backend` 재빌드 확인(tier3는 이 함수들을 그대로 가져다
쓰는 얇은 라우트라 별도 코드 변경 불필요 - 공유 구현이 고쳐지면 자동
적용). 스크래치 환경/서버 정리.
