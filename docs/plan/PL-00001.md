# PL-00001 워크플로우 재구성 실행 계획

설계 근거: [DS-00001](../design/DS-00001.md) · [SP-00003](../spec/SP-00003.md)
(공통 API 계약) · [SP-00001](../spec/SP-00001.md)(평범) ·
[SP-00002](../spec/SP-00002.md)(고급). 1단계 완료, 2단계 진행 중(아래 참고).

## 0단계. 저장소 구조 준비

- `tier1/`(초간단 참조 원본 + 대시보드) 분리 완료 — `bootstrap-prompt.md`도
  여기서 재생성되도록 정리됨.
- `tier2/`(Node 백엔드+Quasar 대시보드+Docker) 신설. 폴더 구조는
  [DC-00001](../decision/DC-00001.md) Q1에서 **B안**(tier2를 base로, tier3가
  확장)으로 확정됐다 — 즉 `tier3/`는 별도 전체 사본이 아니라, `tier2/backend`를
  참조/확장하는 얇은 레이어(인증·멀티테넌시·클라우드 배포 설정 차이만)로
  둔다. 구체적인 참조 방식(모노레포 워크스페이스, 심볼릭 링크, 빌드 시
  합성 등)은 2단계 착수 시 정한다.
- 루트 `docs/`(이 저장소 자신의 워크플로우 기록)는 그대로 유지.

## 1단계. 초간단(Tier 1) 정리 + 공통 API 계약 반영 — 완료

**완료된 부분** (`tier1/tools/docs/server.py` 실제 구현·실제 대시보드로 전부
검증함, 계획이 아니라 실적):

- 문서 CRUD/답변 흐름 `tier1/`로 이동, `scripts/build_prompt.py` 경로 갱신.
- `docs/PROTOCOL.md` 6절대로 `RP`를 파일 없이 대상 문서에 직접 기록하도록
  `answer_pending()` 재작성 — 질문이 몇 개든 늘어나는 파일이 최대 1개(LG)로
  제한됨(원래 "질문마다 RP 파일 1개"로 시작했다가 파일이 급증해서 고침).
  `LG`도 대상 문서당 1개로 find-or-create.
- `scan_meta`(구 `get_doc_meta`) — mtime+size 2단계 캐시로 정밀화, 콜드
  스타트가 아닌 변경 감지 시 `change_notices`를 적재(SP-00003 5·6절 읽기
  게이트). **직접 파일을 손으로 고친 변경도 다음 조회에서 실제로 잡힘**을
  확인(원래 설계가 놓치고 있던 경로).
- `GET /api/changes` / `POST /api/changes/:id/ack`(변경 큐),
  `GET /api/doc?path=&anchor=`(부분 읽기), `GET /api/search?q=`(전문 검색).
- `git log`/`git diff`/`git blame` 읽기 전용 엔드포인트(`subprocess`) —
  Windows에서 `text=True`가 로케일 인코딩(cp949)으로 디코드하다 한글이
  깨지는 실제 버그를 발견해 `encoding="utf-8"`로 고침.
- 코멘트 저장/조회/해결 엔드포인트(stdlib `sqlite3`,
  `docs/.workflow/data.db`, gitignore 대상).
- `docs validate` — `docs/PROTOCOL.md` 3절 규칙을 그대로 코드화한 손수 작성
  검증기(`GET /api/validate` + `--validate` CLI 플래그). 형식적인
  `schemas/*.schema.json` 추출은 Tier 2가 생겨 드리프트를 대조할 대상이
  생겼을 때로 미룸(그 전엔 검증기가 하나뿐이라 정합성 테스트 자체가 의미
  없음).
- 대시보드: 변경 큐 배너, 커밋 히스토리+diff 뷰, 코멘트 스레드, 답변
  다이얼로그에 (a) 이 문서가 `links`로 연결한 관련 SP/DS/PL 문서를 펼쳐
  보여주는 참고 패널, (b) `- 권장:`/`- 대안:` 옵션 원클릭 채우기(설계자 요청
  으로 추가 — `docs/PROTOCOL.md` 4절에 표기 규칙 반영)를 붙임.
- **문서 본문 편집기**(설계자 요청으로 추가, 원래 계획엔 없었음): 각 문서
  뷰의 "편집" 버튼으로 굵게/취소선/제목/코드/링크 툴바가 달린 마크다운
  편집 모드 진입, `POST /api/doc/save`로 저장. **프론트매터는 건드리지
  않음**(id/type/status/links는 여전히 답변 처리나 Claude와의 대화로만
  바뀜) — 저장 전 `docs validate`와 같은 검증을 통과해야 실제로 쓰여짐.
  `docs/PROTOCOL.md` 8절에 반영.

완료 기준 전부 실제 대시보드에서 확인함: 답변 플로우 그대로 동작, git
이력/diff 렌더링, 코멘트 작성/해결, 직접 편집이 변경 큐에 잡힘, `docs
validate`가 의도적으로 깨뜨린 문서(잘못된 `status`/`created` 형식/`id`
불일치/`links` 패턴 오류)를 정확히 잡아냄, 본문 편집기로 저장한 파일의
프론트매터가 그대로 보존됨.

## 2단계. 평범(Tier 2) — [SP-00001](../spec/SP-00001.md) 구현

순서대로 진행(각 항목이 다음 항목의 전제):

1. **`backend/src/core/`** — 완료. `docs/PROTOCOL.md` 규칙을 TypeScript로
   포팅(frontmatter parse/dump, `.tracking.json` 기반 번호 발급, mtime+size
   읽기 게이트 캐시, 답변대기 스캔, `docs validate`, 문서 생성, RP-폴딩 답변
   처리, `PL→DN` 전환, 색인 표 재생성). Tier 1(Python)에서 검증된 로직을
   그대로 이식 — 새 설계 없이 포팅 위주로 진행함. 실제로 검증한 것과 다른
   결정 2가지:
   - `PL→DN` 전환 스텁은 `docs/PROTOCOL.md` 5절 예시(`{id, type, status}`
     3필드만)가 아니라 `created`/`updated`/`links`(새 `DN`을 가리킴)도 유지 —
     3필드 스텁은 7절 필수 필드 규칙(검증)을 스스로 어겨서, 쓰기 경로가
     저장 전 검증을 통과해야 한다는 원칙(SP-00003 7.3절)과 맞지 않음.
   - `POST /api/docs`(문서 생성)는 Tier 1에 없던 새 능력 — Tier 1은 대시보드가
     생성을 하지 않고 Claude가 파일을 직접 쓰지만, SP-00003 2절 라우트
     표와 SP-00001 4절 CLI(`docs new`)가 이미 이 라우트를 전제하고 있어
     Tier 2부터는 API로도 문서를 생성할 수 있게 구현(대상 타입의
     `index.md` 표에 행을 자동으로 붙이거나 "아직 문서 없음" 자리를
     치환함).
   - `change_notices`/`trace_events`(SP-00003 5·6절 읽기 게이트의 알림
     절반)는 아직 미구현 — git 자동화(5번)·변경 큐(7번) 단계에서 저장소가
     생긴 뒤에 붙인다. 지금은 mtime+size 캐시(게이트의 "캐시" 절반)만 있음.
   - `tsc --noEmit` 통과 + 실제로 서버를 띄우고(스캐치 `docs/` 사본에)
     Tier 1과 동일 시나리오(문서 생성 → 답변대기 질문 추가 → 답변 처리 →
     RP 앵커/LG 파일/색인 갱신 확인 → 앵커 부분 읽기 → `PL→DN` 전환 →
     `docs validate` 재확인)를 `curl`/`node --eval fetch`로 끝까지 확인함
     (curl에 한글을 직접 넘기면 Windows 콘솔 코드페이지 때문에 깨지는
     것도 확인 — 이건 이 리포 코드 버그가 아니라 curl 호출 쪽 문제라 Node
     `fetch`로 우회 테스트).
2. **`backend/src/api/`** — 완료(1번 core가 다루는 범위만). `GET /api/tree`,
   `/api/doc`(`&anchor=`), `/api/pending`, `/api/design`, `/api/logs`,
   `/api/all`, `/api/search`, `/api/validate`, `POST /api/doc/save`,
   `POST /api/docs`, `POST /api/docs/:path/reply`(슬래시 포함 경로라
   `:path` 대신 정규식 라우트로 캡처),
   `POST /api/plan/:id/transition-done`. git/comments/changes 라우트는
   해당 core 모듈이 붙는 5~7번에서 추가.
3. **`backend/src/cli/`** — 완료. SP-00001 4절 중 core가 이미 다루는 부분만
   (`commander`): `docs tree`/`pending`/`design`/`all`/`get <path>`/
   `new <type> --title --links`/`reply <path> <qid> <answer...>`/
   `transition-done <id> --report`/`validate`, 전역 `--root`. api/server.ts와
   마찬가지로 core를 직접 호출(HTTP를 거치지 않음). `git`/`comment` 하위
   명령은 5~6번 core가 생긴 뒤 추가. `--root`를 서브커맨드 앞뒤 어디에
   둬도 동작함을 확인(commander의 전역 옵션 상속).
4. **`backend/src/mcp/`** — 완료. `@modelcontextprotocol/sdk`로 SP-00001 3절
   중 core가 다루는 7개 도구(`docs_tree`/`docs_get`/`docs_pending`/
   `docs_list`/`docs_new`/`docs_reply`/`docs_transition_done`)를 등록,
   core 직접 호출. `git_sync`/`git_log`/`docs_comment`는 5~6번에서 추가.
   MCP SDK의 `Client`+`StdioClientTransport`로 실제 서버 프로세스를 띄워
   7개 도구를 전부 호출하는 시나리오(2번 API 검증과 동일한 시나리오)로
   검증 — 한글 인자도 JSON-RPC 경유라 깨지지 않음을 확인(2번에서 발견한
   curl 콘솔 인코딩 문제와 무관).
5. **git 자동화**: SP-00001 5절 규칙을 core에 구현(commit/push/pull, 실패 시
   처리). `docs/.config.json`의 `git.enabled`/`git.push_mode` 반영.
6. **git 이력/diff/blame + 코멘트**: SP-00003 2~3절, SP-00001 2·6절. `core`에
   git log/diff/blame 읽기 모듈과 코멘트 저장(기본 내장 SQLite, `db.enabled`
   켜지면 서비스 DB로) 구현.
7. **변경 추적 큐**: SP-00003 5절. `git pull` 직후(또는 코멘트 생성 시) 백엔드가
   그 결과로 `change_notices`를 채워 넣도록 구현(사후 diff 재계산 없음).
   `GET /api/changes`/`POST /api/changes/:id/ack`, CLI `docs changes`/
   `docs changes ack`. `docs/PROTOCOL.md` 7절과 `CLAUDE.md` 템플릿에 "세션
   시작 시 변경 큐 확인" 규칙 추가(기존 답변 큐 확인 규칙과 나란히).
8. **선택적 서비스 DB**: SP-00001 6절. ORM 도입, `docs_index`(캐시)/
   `doc_comments`(원본 데이터) 테이블. `docs db enable`/`docs db disable`
   CLI 명령으로 데이터 이관까지 검증하며 전환하도록 구현(설정 파일 직접
   수정으로는 `db`를 못 바꾸게 막음). 기본은 꺼짐(SQLite) 상태로 동작 확인.
9. **`dashboard/`**: Quasar(Vue 3, `<script setup>`, scoped SCSS) 프론트엔드.
   Tier 1 대시보드의 화면 구성(트리/문서·설계·기록 탭/답변 다이얼로그/처리
   요령 섹션)에 커밋 히스토리·diff 뷰·코멘트 스레드 화면을 더해 로컬 API를
   호출하도록 구현.
10. **Docker**: `docker/docker-compose.yml`로 backend+dashboard 동시 기동.

완료 기준: Tier 1에서 검증한 것과 동일한 시나리오(문서 열람 → 답변 대기 카드 →
답변 제출 → RP/LG 생성 → 색인 갱신 → 상태 전이)가 Quasar 대시보드 + Node
백엔드에서 동일하게 재현되고, 그 과정에서 `docs/`가 자동으로 git commit됨을
확인. 커밋 히스토리/diff/코멘트 화면과 MCP 도구 호출로도 동일 결과가 나오는지
별도 확인. 코멘트를 몇 개 작성한 뒤 `docs db enable` → `docs db disable`을
연달아 실행해 코멘트가 한 개도 유실되지 않는지까지 확인. 다른 클라이언트가
`docs/`를 바꾼 뒤 `git pull`을 실행하면 diff를 직접 돌리지 않고도 변경 큐에
항목이 잡히고, `ack` 후 큐에서 사라지는지 확인. 이어서 "문서 변경사항을
추적해서 계획이나 승인할 거 있으면 업데이트해줘" 프롬프트로, Claude가 큐를
읽고 `links`로 영향받는 `PL`/`DC` 문서를 찾아 갱신 요약을 제시하는 시나리오까지
확인(SP-00003 5절).

## 3단계. 고급(Tier 3) — [SP-00002](../spec/SP-00002.md) 구현

Tier 2 백엔드 코드베이스를 확장한다(새로 만들지 않음).

1. **DB 스키마**: `users`/`refresh_tokens`/`projects`/`project_members`
   테이블 추가(SP-00002 1~3절). Tier 2의 `docs_index` 캐시 테이블과 같은
   ORM 설정 공유.
2. **인증**: 회원가입/로그인/토큰 갱신/로그아웃 API(SP-00002 2절), argon2id
   해시, JWT 발급/검증 미들웨어.
3. **프로젝트 네임스페이스**: SP-00001의 로컬 API 라우트를
   `/api/projects/:projectId/...`로 감싸고 인증+role 검사 미들웨어 추가
   (SP-00002 4절). 프로젝트 생성/멤버 관리 API 추가.
4. **git 동기화**: API 경로 자동 commit(요청자 이름으로), 웹훅 수신 엔드포인트
   (SP-00002 5절). 충돌 시 단순 실패 처리(3-way 병합은 범위 밖).
5. **클라이언트 토큰 보관**: Skill이 안내하는 REST 클라이언트가 홈 디렉터리
   설정 파일에 토큰을 저장하도록 구현(SP-00002 2절, `.gitignore` 기본 패턴
   포함).
6. **다중 설계자 UI 확장**: git 이력/diff/코멘트 자체는 2단계에서 이미 구현됨
   (프로젝트 네임스페이스만 3번 항목에서 자동으로 씌워짐). 대시보드에 프로젝트
   선택/전환 화면과 멤버 관리 화면만 추가(SP-00002 8절).
7. **클라우드 배포**: 호스팅 위치·환경변수/시크릿 관리·웹훅 대상 호스팅사·
   DB 지원 우선순위·조직 단위 테넌시 확장 여부는
   [DC-00002](../decision/DC-00002.md)에서 확정한 대로 진행.

완료 기준: 두 개의 테스트 계정으로 같은 프로젝트에 서로 다른 role(editor/
viewer)로 접근 → viewer는 조회만 되고 쓰기는 403 → editor가 REST API로 답변
제출 → git 커밋 생성 확인 → 대시보드 커밋 히스토리에 방금 그 커밋이 보이고
diff가 렌더링됨 → 문서에 코멘트 작성/해결 처리 확인 → 별도로 로컬 clone에서
직접 push한 변경이 웹훅으로 서버 캐시/커밋 히스토리에 반영되는지까지 확인.

## 4단계. 문서 정리 및 마무리

- `README.md`, `docs/PROTOCOL.md`를 최종 3-등급 구조에 맞게 갱신(등급별 설치
  안내 링크 포함).
