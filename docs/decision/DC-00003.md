# DC-00003 tier2/tier3 CLI npm 공개 배포 여부

"새 프로젝트를 시작했을 때 사용자 상호작용 흐름이 명확하지 않다"는
지적을 QA로 조사하다가 발견 - `tier2/skill/README.md`/`tier3/skill/README.md`가
`docs`/`docs3` CLI를 "`npm install -g` 하거나 `npx`로 실행"하라고
안내하고 있었는데, `tier2/backend`/`tier3/backend`의 `package.json`이
둘 다 `"private": true`라 실제로는 npm 레지스트리에 공개돼 있지 않아
그 명령이 동작하지 않는다는 걸 확인(가짜 안내였음).

당장의 궁여지책은 이미 적용했다 - Tier 2는 이미 떠 있는 Docker
컨테이너 안의 빌드 산출물을 `docker compose exec`로 그대로 쓰는 경로
(로컬 설치 불필요, 실제로 검증 완료)를 문서화했고, Tier 3의 `docs3`
CLI는 원격 REST API를 호출하는 얇은 클라이언트라 설계자 자신의
머신에서 실행돼야 하므로 clone+build+`npm link`를 임시 안내로 문서화
했다. 하지만 Tier 3는 여러 설계자가 각자 자기 머신에서 `docs3`를
써야 하는 구조라(SP-00002의 핵심 전제), clone+build 임시책은 매번
"저장소를 통째로 받아서 두 단계 빌드해야 한다"는 마찰이 반복된다 -
정식으로 npm에 공개 배포할지는 별도 결정이 필요하다고 판단해 DC로
등록한다.

## 선택지

**Q1. npm 공개 배포 여부**
- 지금처럼 `"private": true`를 유지하고 clone+build+`npm link` 안내만
  계속 쓸지, 아니면 `@claude-native-workflow/tier2-backend`(`docs`)/
  `@claude-native-workflow/tier3-backend`(`docs3`)를 실제로 npm
  레지스트리에 공개 배포할지.
- 공개 배포를 선택하면 뒤따르는 추가 결정: 패키지명을 지금 스코프
  (`@claude-native-workflow/...`) 그대로 쓸지, npm 계정/조직을 새로
  만들지, 버전 정책(0.x 동안은 breaking change 자유롭게 vs semver
  엄수)을 어떻게 가져갈지, CI에 `npm publish` 자동화를 붙일지 수동
  배포로 남길지.
