# 설계 노트 (SP-XJQCTF6Y)

v3는 밑바닥부터 다시 시작하는 구현이다. 아직 이 저장소를 관리하는
claude-native-workflow 설치가 정해지지 않았으므로, 설계 논의는 우선
이 파일에 기록한다 - 설치가 갖춰지면 그때 DB 문서로 이관한다(v2가
그랬던 것처럼).

이 문서는 설계에서 정의한 문서 엔티티 모델을 그대로 따른다 - `##
라운드 N` 각 절이 이 `doc` 문서의 챕터에 해당한다. `branch`/
`commit_id`가 아직 `null`인 것은 설계 자체가 아직 커밋되지 않은
초기 설계 단계이기 때문이다(설계상 "둘 다 null이면 초기 설계용으로
간주"하는 규칙과 일치) - 이 라운드 내용이 실제로 커밋되면 그 커밋의
branch/commit_id로 갱신한다.

**용어**: "설계자"를 영문/스키마 필드명으로 표기할 땐 `designer`가
아니라 **`architect`**를 쓴다(예: `architectId`) - 본문의 한글
"설계자"라는 단어 자체는 그대로 쓰되, 영문 식별자/필드명은 전부
`architect` 계열로 통일한다.

## 라운드 1 (2026-09-20) - 초기 아키텍처 스케치

### 조직 구조
- **`팀`/`프로젝트 그룹` 개념을 채택하지 않는다** - v2에서 있어도 실효성이
  낮았다는 판단.
- **collaborator 시스템은 GitHub과 유사한 구조로 간다.** organization
  레벨은 두지 않는다 - 프로젝트(저장소)에 collaborator만 붙는 구조로,
  팀/프로젝트 그룹이 하던 역할을 상위 조직 단위 없이 collaborator가
  대체한다.
- **collaborator 권한 레벨은 `Read`/`Write`/`Admin` 세 단계**로
  구분한다(GitHub의 저장소 권한 단계와 유사). **`Admin`은 프로젝트당
  단 1명뿐이다** - GitHub과 달리 여러 명이 동시에 Admin일 수 없다
  (프로젝트 설정 변경, collaborator 초대, 템플릿 배포 등 "그
  프로젝트의 Admin"이 하는 동작은 전부 이 한 명만 할 수 있다).
- **Admin은 프로젝트를 다른 collaborator에게 양도(transfer)할 수
  있다** - 양도하면 그 collaborator가 새 Admin이 되고, 기존 Admin은
  Admin 권한을 잃는다(자기 권한은 `Read`/`Write`로 내려가거나
  나가는 건 별개 - 아래 참고).
- **Admin이 프로젝트에서 나가려면 두 가지 방법뿐이다**: (1) 다른
  누군가에게 Admin을 **양도**하거나, (2) GitHub의 "Danger Zone"에
  해당하는 **"제한구역"에서 프로젝트 자체를 파기(delete)**한다 -
  Admin 없이 프로젝트만 남는 상태는 허용하지 않는다.
- **버전 호환성이 깨지므로, 로컬 운영 설치본(`C:/CNW`)에는 v3를 절대
  반영하지 않는다** - v2가 계속 그 설치의 운영 버전으로 유지된다.
- UI는 GitHub과 최대한 유사하게 구성한다.

### 역할(클로드 vs architect) 구분

질의/답변 액터 규칙, `opinion` 방향, `BT`/`test`/`tracker`의 자동
처리 등 여러 규칙이 "이 요청이 클로드인지 architect인지"에 의존하는데,
그 판별 기준은 **접속 경로(채널) 하나로 단순화한다** - 개별 신원을
따지지 않는다:

- **CLI/MCP로 들어오는 요청은 일률적으로 클로드가 한 것으로 간주한다.**
- **WEB UI로 들어오는 요청은 architect가 한 것으로 간주한다.**

즉 "누가 로그인했는가"가 아니라 "어느 채널로 들어왔는가"가 역할을
정한다 - `architectId`/`apiKey`는 그 요청을 누가 보냈는지(감사/
`author` 기록용) 식별하는 것이고, "클로드 vs architect" 액터 판정은
채널로만 갈린다.

### 저장소(git) 관리
- **v2와 달리, 내부 저장소(시스템이 직접 들고 있는 git 저장소)의
  유지보수가 메인 흐름이다** - 외부 저장소(GitHub/GitLab 등)를
  링크해서 그쪽을 원본으로 삼는 게 기본이 아니라, 시스템 안에서 직접
  커밋/브랜치가 쌓이는 내부 저장소가 기본이다.
- **외부로 내보내는 push-mirror 기능은 옵션이다** - 필요하면 내부
  저장소의 내용을 외부 저장소로 미러링해서 내보내는 부가 기능일
  뿐, 필수 경로가 아니다.
- **왜 옵션으로 바꿨는지**: v2에서는 매번 publish 절차(내부 → 외부
  동기화)를 거쳐야 해서 작업 속도가 느려지고 흐름이 정체되는 느낌이
  있었다. v3에서는 내부 저장소에 커밋/브랜치를 쌓는 건 자유롭게
  진행하고, **외부 저장소로의 동기화는 설계자가 직접 push 버튼을
  눌러야만 일어나는 명시적 동작**으로 바꾼다 - 자동/매 라운드 publish
  없음.

### API 응답 규격
- 시스템 등록 상태를 종합 확인하는 명령이 필요하다 - 구체적인 형식은
  "API/MCP/CLI 설계" 절의 `docs.status` 액션 정의(마지막 절 "문서
  등록 현황 조회 응답") 참고. 최초 스케치는 `notices`/`opinions`/
  `plans`/`questions`처럼 `type`별로 필드를 따로 뒀었는데, 이후
  "통합 명령"/표준 응답 규격 원칙과 맞춰 `kind`별/상태별로 통일된
  구조로 다시 정리했다.
- **모든 응답은 아래 형태로 규격화된다**:
  ```
  {
    notices: [ ... ],
    status: <응답 코드>,
    result: <응답 - 객체/문자열 등>
  }
  ```
- **리스트 응답은 `result` 필드 내부가 아래 형태로 규격화된다**:
  ```
  { "page": 현재 페이지 번호, "total": 총 항목 갯수, "items": [ ... ] }
  ```
- **커서 기반 페이지네이션도 같이 지원한다**: 위 형태에 `nextCursor`를
  추가한다 - `{ page, total, items, nextCursor }`. `nextCursor`가
  있으면 더 가져올 페이지가 있다는 뜻이고, 없으면 마지막 페이지다.
  요청할 땐 `page` 번호 대신 직전 응답의 `nextCursor` 값을 그대로
  넘겨서 이어서 조회할 수 있다(`cursor` 파라미터) - 둘 다 받되
  `cursor`가 있으면 그걸 우선한다. 대용량 결과(검색 등)를 이어서
  훑을 땐 이 방식이 기본이 된다.
- **CLI/MCP도 이 커서를 그대로 노출한다** - `docs list`/`docs
  search`(CLI)와 `docs_query`(MCP)에 `--cursor`/`cursor` 옵션을
  두고, 응답의 `nextCursor`를 그대로 다음 호출에 넘겨서 이어볼 수
  있게 한다 - API의 페이지네이션 규격을 그대로 반영, 별도 규격을
  만들지 않는다.
- **bulk 동작(액션 배열 요청)의 응답 형식**: `result`가 곧 배열이고,
  요청한 액션 배열과 **인덱스가 1:1로 매칭**된다 - 항목 개수만큼
  반복된다.
  ```
  {
    ...
    "result": [
      { "ok": true, "data": { ... } },
      { "ok": false, "reason": [ "...", ... ] },
      ...
    ]
  }
  ```
  `ok`가 `false`인 항목만 `reason`에 실패/거부 원인을 문자열
  배열로 담는다("해당 문서는 OOOO 동작을 할 수 없습니다. 대신
  VVVV를 이용하세요" 같은 설명). **`ok`가 `true`인 항목은 `data`에
  그 액션이 만들어낸 결과 데이터를 담는다** - 예를 들어 `docs.add`는
  새로 등록된 문서의 추적 코드/`etag`를 `data`에 실어 돌려준다.
  이 표준 응답 규격(`notices`/`status`/`result`) 밖에 별도 에러
  포맷을 만들지 않는다 - 즉
  명령이 통합됐다고 응답 형태가 type/동작마다 달라지지 않는다.

### 변경 사항 스테이징
- 변경 사항을 로컬에 쌓아놓고 한번에 올리는(push) 명령 방식으로
  변경한다 (git의 add/commit/push와 유사한 흐름). 로컬에 쌓이는
  단위가 바로 아래 "API 설계 원칙"의 액션 객체이고, push 시점에
  쌓인 액션 배열을 한 번에 그 단일 엔드포인트로 보낸다.

### 문서 엔티티 모델
- **문서 → 챕터 → 질의 → 답변**: 이 중 `doc`/`question`/`answer`(및
  `plan`/`tracker`)는 같은 엔티티(같은 테이블/스키마)를 공유하는
  `type`이지만, **챕터는 별도 `type`이 아니라 문서에 속한 하위
  구조다** - 즉 챕터 자체는 독립된 추적 코드를 가진 엔티티가 아니라,
  하나의 `doc` 문서 내부를 구획하는 구조(섹션)로 존재한다.
- **챕터 추적 방식과 그 한계**: 챕터는 Markdown의 `##` 같은 헤딩
  표기로 "챕터 제목" 문자열을 매개로 추적한다(별도 챕터 ID가 없다).
  그래서 **챕터 제목이 바뀌면 그 챕터에 달려있던 `question`/`answer`
  와의 연결이 깨진다** - 이건 오류로 취급하지 않고, 그렇게 연결이
  끊긴 질의/답변은 그냥 **"과거 질문/답변 기록"으로 취급**한다(그
  챕터를 자동으로 재매칭하려 하지 않는다).
- 이게 복잡해지지 않는 이유: 챕터에 달린 `question`/`answer`도
  **`parent_id`는 어차피 그 문서 자체(`doc`)를 가리킨다** - 챕터
  제목은 그 관계 위에 얹힌 부가 정보(어느 챕터를 가리켰는지)일 뿐이다.
  그래서 챕터 제목이 바뀌어도 `parent_id` 체인 자체(문서 체인 구조)는
  전혀 깨지지 않고, 단지 "어느 챕터였는지"에 대한 부가 정보만 낡은
  값으로 남을 뿐이다.
- 문서간 참조: 연관된 문서들을 태깅한다 (이 문서가 태깅 / 다른 문서가
  태깅, 다대다로 여러 개 가능). **입력은 추적 코드의 배열이 아니라,
  `[{ code: <추적 코드>, etag: <태깅 시점의 그 문서 etag> }, ...]`
  형태다** - 태깅하려는 대상 문서가 그 사이 바뀌지 않았는지(읽어간
  시점 그대로인지) 확인하기 위해, 각 추적 코드마다 그 시점의 etag를
  같이 실어 보낸다.
- 파일 참조: 이 문서와 연관된 파일들을 태깅한다 - **모든 `type`의
  문서에 공통으로 매달 수 있는 필드**다(특정 타입 전용이 아님).
- 문서 종류(`type`): `doc`, `plan`, `question`, `answer`, `tracker`,
  `test`, `opinion`.
- 질의는 챕터 단위로 진행하도록 구성한다 - 즉 `question`이 어떤
  `doc`의 특정 챕터를 가리켜서 달린다.
- 답변은 해당 질의에만 달 수 있다.
- **의견(`opinion`)도 문서 시스템에 통합한다** - 별도 시스템이
  아니라 `문서` 엔티티 모델을 공유하는 `type` 중 하나로 구현한다.
  **방향이 고정돼 있다: 설계자가 클로드에게 작성하는 용도** - `question`
  처럼 질의자가 클로드/설계자 둘 다 될 수 있는 게 아니라, `opinion`은
  항상 설계자가 작성하고 클로드가 읽고 처리하는 일방향 채널이다.
  `question`과 달리 답변(`answer`)을 강제하지도 않는 자유 코멘트
  개념이다. 라운드 1 초반에 언급한 시스템 상태 조회 응답의 `opinions`
  필드가 바로 이 `opinion` 타입 문서들을 상태별로 집계한 것이다.
- **문서 체인(`parent_id`)**: `id` 외에 `parent_id`를 둬서 "하위
  문서" 개념을 도입한다 - **질의/답변에 국한되지 않고 어떤 `type`의
  문서든 하위 문서를 가질 수 있다.** 예를 들어 어떤 답변에 또다시
  의문점이 생기면 그 답변을 `parent_id`로 가리키는 하위 질의를 등록할
  수 있는 식이지만, 그 외에도(예: 문서 아래 후속 문서, 계획 아래
  하위 계획 등) 같은 방식으로 쓸 수 있다. `related`(다대다 태깅)와는
  별개로, 이건 1:N의 계층적 부모-자식 관계다.
- **`type`별 상세 제약도 함께 수립한다** - `parent_id`가 아무 조합이나
  허용하는 범용 필드가 아니라, `type` 조합마다 구체적인 유효성 규칙을
  둔다는 원칙이다. 예(`question`/`answer`):
  - `answer`의 `parent_id`는 **그 질의에 달린 답변을 찾기 위한
    용도**이므로, 한 `question`에 직접 자식으로 달리는 `answer`는
    **최대 1개**로 제한한다(이미 존재하면 새 답변 등록이 거부되고,
    수정은 기존 답변을 갱신/대체하는 방식으로 처리 - 위 "답변에
    `discard`가 없는 이유"와 같은 맥락).
  - `answer`의 `parent_id`가 가리키는 문서는 **반드시 `question`
    이어야 한다**(다른 `type`을 부모로 가질 수 없다).
  - `doc`의 `parent_id`가 있다면 그 부모는 **반드시 `doc`**이어야
    한다("후속 문서" 관계) - 카디널리티 제한은 없다(하나의 문서 아래
    후속 문서가 여러 개 달릴 수 있음).
  - `plan`은 `doc`과 달리 **부모 타입을 `plan`으로 제한하지 않는다**
    - 계획은 "하위 계획"으로 다른 계획 밑에 달릴 수도 있지만, 애초에
    어떤 문서(`doc`/`question`/`answer`/`opinion` 등) 때문에 그
    계획이 발행된 경우도 있어서, `tracker`/`opinion`처럼 부모 타입을
    특정 타입으로 제한하지 않는다. 카디널리티도 제한 없음(같은
    부모에서 여러 계획이 나올 수 있고, 하나의 계획이 여러 하위
    계획으로 나뉠 수도 있음). (`question`/`answer`처럼 답변이 딱
    하나만 달려야 하는 특수한 경우가 아니면 기본적으로 카디널리티
    제한은 두지 않는 쪽이 기본값이다.)
  - `question`은 **어디든 부착 가능하다** - 부모 타입을 제한하지
    않는다(어떤 `type`의 문서에도 질의를 달 수 있음, `doc`의 특정
    챕터를 가리켜서 다는 것도 이 관계의 한 예). 카디널리티도 제한
    없음 - 같은 부모에 여러 질의가 달릴 수 있다. (반대로 `answer`는
    위에서 정한 대로 부모가 반드시 `question`이고 최대 1개로 제한된
    특수 케이스다.)
  - `tracker`/`opinion`은 앞의 둘과 성격이 다르다 - 같은 `type`끼리
    계층을 이루는 게 아니라, **다른 문서에 "붙어서" 그 문서를 추적/
    코멘트하는 관계**다. 그래서 `parent_id`가 가리키는 부모의 `type`
    을 특정 타입으로 제한하지 않는다(어떤 `type`의 문서든 추적/의견의
    대상이 될 수 있음). 카디널리티도 제한하지 않는다 - 같은 문서를
    여러 `tracker`가 추적하거나, 같은 문서에 여러 `opinion`이 달릴
    수 있다.
  - 이런 식으로 다른 `type` 조합의 체인에도 구체적인 카디널리티/
    허용 부모 타입 제약을 앞으로 계속 정해나간다.

### 상태값
- 문서(`doc`) 상태: `draft`(초안), `review`(검토), `active`(승인),
  `done`(완료), `discard`(폐기).
- 계획(`plan`) 상태: `added`, `read`, `done`, `discard`.
- 질의(`question`) 상태: `added`, `read`, `done`, `discard`.
  (질의자가 "클로드" 또는 "설계자"일 수 있음)
- 답변(`answer`) 상태: `added`, `read`, `done`.
  (질의자가 "클로드"일 땐 "설계자"만 답변 가능, 반대도 마찬가지)
  **`discard`가 없는 이유**: 답변은 등록 후 철회하고 다시 작성하는
  경우가 있는데, 그걸 "폐기된 기록"으로 남겨두면 AI가 히스토리를 읽을
  때 혼동을 줄 수 있어서 의도적으로 뺐다 - 철회 시엔 폐기 상태로
  남기는 대신 내용을 갱신/대체하는 방식으로 처리한다.
- **질의가 해소되기 전까지 문서 상태를 변경할 수 없다.**
- **상태 코드는 등록 처리 시 explicit하게 검사**하고, bulk 동작에
  대해서는 개별 항목이 어떻게 처리됐는지 알려줘야 한다.
- **모든 문서 관련 동작은 "변경 코드"(문서가 등록되거나 변경, 상태가
  바뀔 때마다 갱신되는 랜덤 문자열)를 반환해야 한다.** → 이후
  "동시 편집 충돌 방지" 절에서 정의하는 `etag`가 바로 이 변경 코드다
  (같은 개념, 이름만 `etag`로 확정).
- 추적(`tracker`) 상태: `added`, `resumed`, `ended`, `canceled` -
  어떤 문서의 현황을 추적하기 위한 문서.
- 테스트(`test`) 상태: `added`, `discard` - `BT`처럼 어떤 테스트를
  했는지 기록하는 기록성 문서라 두 상태만 관리한다.
- 의견(`opinion`) 상태: `added`, `read`, `done`, `discard` (`plan`과
  같은 패턴 - 등록/열람/처리완료/폐기).

### 문서 상태 전이 규칙 (제안 - 확인 필요)

*아래는 지금까지 정해진 규칙(액터 구분, discard 없음 등)을 바탕으로 한
제안이다. 확정된 게 아니라 다음 라운드에서 설계자 확인/수정이 필요하다.*

**공통 원칙**
- 액터는 "클로드"와 "설계자" 두 역할로만 구분한다(collaborator가
  여럿이어도 문서 워크플로우상으로는 이 두 역할로 수렴).
- 상태는 기본적으로 앞으로만 전진한다(되돌리는 전이는 없음).
- `discard`/`canceled`는 진행 중 어느 상태에서든 갈 수 있는 종료
  상태다(단, `answer`엔 애초에 `discard` 자체가 없음 - 이미 결정).
- 질의가 `done`/`discard`로 해소되기 전까지, 그 질의가 달린 `doc`의
  상태는 바뀌지 않는다(이미 결정된 규칙).
- **연쇄 전이**: 위 "설계자만" 전이 제한은 클로드가 자기 판단만으로
  단독 전이하는 경우를 막기 위한 것이지, 설계자가 요청한 작업을
  수행하는 과정에서까지 막는 게 아니다 - 설계자가 명시적으로 요청한
  작업을 처리하는 흐름 안에서는, 그 요청 자체를 승인으로 간주해
  클로드가 여러 단계(예: `added`→`read`→`done`)를 한 번에 연쇄
  전이시킬 수 있다.
- **다만 breaking change는 예외다** - 연쇄 전이 도중이라도 그 전이가
  breaking change(예: 버전/API 호환성을 깨는 변경)에 해당하면, 클로드
  혼자 판단해서 진행시키지 않는다 - 그 지점에서 멈추고 설계자에게
  명시적으로 확인받는다. 즉 "설계자 요청 = 포괄 승인"이 적용되는 건
  breaking change가 아닌 전이까지만이다.

**`doc` 상태 전이**
- `draft` → `review`: 작성자 본인이 검토 요청 시 전이.
- `review` → `active`: **설계자만** 전이 가능(최종 승인 권한).
- `active` → `done`: 클로드/설계자 누구든 실제 작업 완료 시 전이.
- 임의 상태 → `discard`: **설계자만** 전이 가능.
- 예외: `BT`는 이미 결정된 대로 클로드가 스스로 `active`/`discard`까지
  처리할 수 있다(설계자 승인 불필요).

**`plan` 상태 전이**
- `added`: 보통 클로드가 등록(별도 계획이 필요한 항목을 발견했을 때).
- `read`: 설계자가 확인하면 전이.
- `done`/`discard`: **설계자만** 전이 가능(계획은 원래 "설계자의
  결정이 필요한 사항"이 취지라 처리 여부도 설계자 몫).

**`question`/`answer` 상태 전이**
- 질의 `added`: 질의자(클로드 또는 설계자)가 등록.
- 질의 `read`: 상대방(답변할 쪽)이 열람하면 전이.
- 답변 `added`: 상대방이 등록(질의자가 클로드면 설계자만, 반대도
  마찬가지 - 이미 결정).
- 답변 `read`: 질의자가 답변을 열람하면 전이.
- 답변 `done`: 질의자가 "이걸로 해소됨"이라 확정할 때 전이 - 이때
  원 질의도 함께 `done`으로 전이.
- 질의 `discard`: 질의자 본인만 전이 가능(자기가 낸 질문 철회).

**`tracker` 상태 전이**
- `tracker`는 자동화된 흐름의 현재 상태를 추적하기 위한 문서로,
  `added`/`resumed`/`ended`/`canceled` 전이 전부 **클로드가 전적으로
  알아서 관리한다** - 설계자 승인/개입 없이 클로드 판단으로 등록,
  재개, 종료, 취소한다.

**`test` 상태 전이**
- `test`는 `BT`처럼 어떤 테스트를 했는지 기록하는 기록성 문서라
  `added`/`discard` 두 상태만 관리한다 - 등록/폐기 모두 클로드가
  스스로 처리한다(`BT`와 동일한 성격).

**`opinion` 상태 전이**
- `added`: **설계자만** 등록 가능(설계자 → 클로드 방향으로 고정).
- `read`: 클로드가 열람하면 전이.
- `done`: 클로드가 그 의견을 반영/처리했을 때 전이.
- `discard`: 설계자 본인만 전이 가능(자기가 낸 의견 철회 - `question`
  의 `discard` 규칙과 동일한 발상).

모든 상태 전이 규칙이 정리됐다 - 추가 확인/수정 사항은 다음 라운드
절로 이어서 기록한다.

### 분류 코드 (`kind`)
- 문서(`doc`): `SP`(설계 명세), `RP`(결과 보고), `RM`(지시/지침 사항),
  `QA`(QA 시나리오), `BT`(돌파구, break-through).
- 계획(`plan`): `PL`.
- 질의/답변: `QU` / `AN`.
- 테스트(`test`, `doc`와 별도 `type` - QA와는 별개 개념으로 보통
  QA에서 인용됨): `TC`(Test case).
- 의견(`opinion`): `OP`.
- `answer`도 전용 구조화 필드를 두지 않고 **자유 양식 Markdown**으로
  통일한다("`type`별 전용 필드는 만들지 않는다" 절과 같은 원칙) -
  "승인/거부/자유답변"이라는 별도 enum 필드를 만드는 게 아니라,
  그 질의(`question`)가 애초에 어떤 성격인지에 따라 답이 자연스럽게
  둘 중 하나의 형태로 쓰이는 것뿐이다:
  1. AI가 승인/거부를 요구하는 질의라면 - 답은 "승인"/"거부"로
     시작하는 자유 텍스트(뒤에 자유 코멘트를 덧붙여도 됨).
  2. 애초에 자유 답변이 요구되는 질의라면 - 그냥 자유 서술.
  두 경우 다 저장은 같은 자유 Markdown 본문 필드에 한다 - 연관 문서
  태깅은 가능.
- 답변에 대해 다시 질의를 등록할 수 있다 - 위 "문서 체인" 참고, 새
  질의의 `parent_id`가 그 답변을 가리킨다.
- `BT`는 클로드가 스스로 승인/폐기하며 만드는 기록성 문서다.

### git 연동
- **모든 문서는 git branch와 마지막 commit ID를 따라다닌다** - 즉
  commit 후에 문서를 남겨야 한다.
- commit을 하지 않고 문서만 생성하는 경우, 마지막 commit을 기준으로
  "후속 의견서" 형태로 기록한다.
- git branch가 분리되거나 커밋을 revert하면, 문서도 자동으로
  분리되고 revert되는 구조다.
- 다만 이후에 어떤 branch가 있었고 어떤 커밋과 어떤 문서가 있었는지
  조회할 수 있어야 한다.
- v1/v2와 달리 **git 동작 자체를 오버라이드하지 않고, 내부 콜백으로만
  변동을 추적한다.**
- 프로젝트가 처음 시작할 땐 git 커밋/브랜치가 아무것도 없을 수 있다
  → `branch`, `commit_id`가 둘 다 null이면 초기 설계용으로 간주한다.
- **`branch`/`commit_id`를 채우는 방법은 채널(위 "역할 구분" 절)마다
  다르다**:
  - **CLI/MCP** - 로컬 git 저장소의 현재 상태(현재 checkout된 branch,
    `HEAD` commit)를 **자동으로 인식**해서 채운다 - 호출자가 명시적
    으로 넘길 필요 없다.
  - **WEB UI** - git 작업 디렉터리가 없으므로 규칙이 다르다: **새
    문서**(`parent_id` 없음)는 그 프로젝트의 현재 `HEAD` 기준으로
    채우고, **어딘가에 매달리는 문서**(`parent_id` 있음)는 **매달리는
    부모 문서의 `branch`/`commit_id`를 그대로 물려받는다**(부모가
    가리키던 시점 그대로 유지 - HEAD가 그 사이 움직였어도 상관없이).

### `remember` 항목 (메모리) - 문서 체계와 별개

클로드 세션 자체의 메모리 시스템(사용자/피드백/프로젝트/참고자료 네
분류로 파일을 나눠 지속 관리하는 방식)에서 이미 검증된 패턴을 그대로
가져왔다.

- **왜 문서 체계와 분리하는지**: `doc`/`plan`/`question`/`answer`/
  `tracker`/`test`는 전부 git branch/commit을 따라다니는 "이력"이라,
  브랜치가 갈라지거나 커밋을 revert하면 그 문서도 같이 갈라지고
  revert된다(이미 결정된 규칙). 하지만 설계자의 성향, 프로젝트의
  배경 사실, 참고 자료 위치처럼 **브랜치/커밋과 무관하게 계속
  유지돼야 하는 지식**은 이 규칙을 적용하면 안 된다 - 그래서
  `remember` 항목은 챕터/상태 전이/git 추적을 전혀 따르지 않는 별도
  엔티티로 둔다.
- **분류(제안)**:
  - `user`: 설계자의 역할/선호/지식 수준에 대한 정보.
  - `feedback`: 설계자가 준 작업 방식 피드백(하지 말아야 할 것 /
    계속해야 할 것, 왜 그런지 포함).
  - `project`: 진행 중인 작업의 배경/목표/결정 사항 중 코드만 보고는
    알 수 없는 것.
  - `reference`: 외부 시스템 포인터(어디서 뭘 찾을 수 있는지).
- **필드(초안)**:
  ```
  {
    id: 'xxxxxxxx',
    owner: <architectId (collaborator 식별자)>, // (프로젝트, 설계자) 단위로 개인화
    category: 'user' | 'feedback' | 'project' | 'reference',
    title: 제목,
    summary: 한줄 요약(다른 항목과 구분용),
    content: 본문(Markdown),
    related: [ { code: 'XX-xxxxxxxx', etag: <태깅 시점 etag> }, ... ],
    createdAt, updatedAt,
  }
  ```
  `branch`/`commit_id`는 아예 없다 - git 추적 대상이 아니기 때문.
- **스코프**: 프로젝트 하나에만 종속된다 - 설계자/collaborator 단위로
  여러 프로젝트에 걸쳐 공유되는 스코프는 두지 않는다.
- **개인화**: 같은 프로젝트 안에서도 **설계자(collaborator)별로
  개인화되어 관리된다** - 즉 실제 스코프는 (프로젝트, 설계자) 조합
  단위다. 같은 프로젝트에 collaborator가 여럿이어도, 한 설계자의
  `remember` 항목이 다른 collaborator에게 공유되지 않는다.

### 동시 편집 충돌 방지 (etag)
- **목적**: 같은 문서를 여러 에이전트/설계자가 동시에 수정하는 것을
  막기 위함.
- 문서마다 순수 랜덤 문자열로 만든 가상의 `etag`를 발급한다 - 앞서
  "상태값" 절에서 말한 "변경 코드"와 같은 개념이다(문서가 등록/변경/
  상태 전이될 때마다 재발급).
- **Read**: 응답에 그 문서의 마지막 `etag` 값을 포함해서 반환한다.
- **Update**: 요청에 (읽어갔을 때 받은) `etag`를 실어 보내고, 서버는
  현재 문서의 실제 `etag`와 대조한다 - 지금 편집하려는 내용이 정말
  그 시점에 읽어갔던 버전이 맞는지 확인하는 것. 다르면 conflict로
  처리한다.
- **Delete**: 마찬가지로 `etag`를 실어 보내서, 지금 지우려는 게 그
  버전이 맞는지 확인한다(용도는 `answer` 철회뿐 - 위 "액션 카탈로그"
  의 `docs.delete` 절 참고).
- 확인 결과 conflict거나 실패면, 위에서 정한 bulk 응답 규격 그대로
  `{ ok: false, reason: [...] }`로 실패 사유를 담아 반환한다 - 별도
  에러 포맷을 두지 않는다. (`docs.transition`의 `[새 상태, 기존
  상태(예상)]` 튜플도 같은 발상의 낙관적 동시성 체크지만, 그건 상태
  값 자체를 대조하는 것이고 `etag`는 문서 전체에 대한 범용 버전
  토큰이라는 차이가 있다.)

### API 설계 원칙
- v1/v2와 달리 **bulk 동작만 정의한다** - 여러 개를 한 번에 제출하는
  것이 기본이 되도록. **모든 명령 세트는 bulk가 기본이고, 단일
  동작을 위한 별도 API/명령 형태를 두지 않는다** - 항목 하나만
  처리하고 싶으면 그냥 bulk 요청에 항목을 하나만 넣어서 보낸다.
- **bulk의 실체 = 단일 엔드포인트 + command 패턴**: 모든 동작을
  액션 객체의 JSON 배열로 만들어 **단일 API 엔드포인트** 하나로
  던진다:
  ```
  [
    { "action": "docs.add", ... },
    { "action": "docs.transition", ... },
    ...
  ]
  ```
  서버는 이 엔드포인트에서 **command 패턴**으로 동작한다 - `action`
  문자열(예: `docs.add`)을 키로 각 항목을 해당 핸들러에 매핑해서
  순서대로 처리한다. 응답은 위에서 정한 표준 규격(`notices`/
  `status`/`result`)을 그대로 따르고, `result`가 각 액션의 처리
  결과를 액션 순서대로 담은 배열이 된다.
- **상태 전환도 하나의 액션(`docs.transition`)으로 취급한다**:
  ```
  {
    "action": "docs.transition",
    "state": {
      "XX-xxxxxxxx": [ <새 상태 코드>, <기존 상태 코드(예상)> ]
    }
  }
  ```
  키는 추적 코드, 값은 `[새 상태, 기존 상태(예상)]` 튜플이다 - 기존
  상태를 같이 보내서, 실행 시점에 실제 현재 상태와 다르면(동시
  변경 등으로 어긋난 경우) 실패로 처리하고 `reason`으로 알려준다.
- 검색 엔진이 뱉어내는 결과는 문서 추적 코드, git branch 명칭, 해당
  문서의 git commit ID, 그리고 **`etag`**도 같이 반환한다 - 검색
  결과에서 바로 최신 버전인지 알 수 있게.

### 인터페이스
- API뿐 아니라 **CLI와 MCP도 만들어서 배포해야 한다** - v2와 같은
  구조(백엔드가 API를 제공하고, CLI/MCP는 그 API를 감싸는 클라이언트)
  를 유지한다. CLI/MCP가 갖춰지면 v2 때처럼 이 저장소의
  CLAUDE.md/SKILL.md도 실제 명령 사용법에 맞춰 같이 갱신해야 한다.
- **CLI/MCP 명령 체계는 최대한 압축해서 컨텍스트를 많이 차지하지
  않는 방향으로 설계한다** - 명령/도구 개수, 옵션 설명, 응답 형식
  전부 LLM 컨텍스트 소비를 염두에 두고 최소화한다(이미 정해둔 "응답
  규격화"/"bulk 동작 기본"과 같은 방향).
- **문서 구조를 다루는 모든 동작에 동일하게 적용**: 등록뿐 아니라
  조회/수정/상태 전이/연결 등 `문서` 구조를 사용하는 모든 동작이,
  `type`이나 동작 종류별로 명령을 따로 만드는 대신 통합된 명령을
  쓴다(예: 등록은 `plan new`/`question new`/`tracker new` 대신
  `docs add` 하나). 대신 내부에서 유효성을 검증해서, 허용되지 않는
  동작이거나 유효성에 문제가 생기는 시도면 명령을 늘리는 대신 그
  사유를 반드시 설명해줘야 한다 - 예: "해당 문서는 OOOO 동작을 할 수
  없습니다. 대신 VVVV를 이용하세요."
- **모든 `type`의 상태 전이가 같은 통합 명령 세트를 쓴다** -
  `doc`/`plan`/`question`/`answer`/`tracker`/`test` 전부, 상태 전이
  전용 명령을 type별로 따로 두지 않고 하나의 통합된 명령으로
  처리한다. `question`/`answer`처럼 액터 규칙(질의자/답변자 구분,
  답변은 상대편만 등록 가능 등)이 복잡한 경우도 예외 없이 같은
  명령을 쓰고, 내부적으로 누가 요청했는지/어떤 상태인지 검증해서
  안 되는 이유를 그대로 응답에 담아 알려준다(예: "이 질의의 답변은
  설계자만 등록할 수 있습니다").

### 문서 스키마 (초안)
```
{
  id: 'xxxxxxxx', // 추적 코드의 뒷 8자리, [A-Z0-9]
  parent_id: 'xxxxxxxx' | null, // 상위(부모) 문서의 id - 문서 체인
  etag: <순수 랜덤 문자열, 변경마다 재발급 - 동시 편집 충돌 방지용>,
  type: 'doc' | 'plan' | 'question' | 'answer' | 'tracker' | 'test' | 'opinion',
  kind: 'SP' | 'RP' | 'RM' | 'QA' | 'BT' | 'PL' | 'QU' | 'AN' | 'TC' | 'OP',
  state: <문서/계획/질의/답변 등의 상태>,
  branch: <git branch 명칭>,
  commit_id: <git commit ID>,
  title: 제목,
  author: 작성자,
  related: [ { code: 'XX-xxxxxxxx', etag: <태깅 시점 etag> }, ... ],
  dependsOn: [ { code: 'XX-xxxxxxxx', etag: <태깅 시점 etag> }, ... ], // 구현 우선순위 계산용 의존성
  createdAt: <등록 시각>,
  updatedAt: <마지막 변경 시각 - etag 갱신 시점과 같이 움직임>,
  ...
}
```

### `type`별 전용 필드는 만들지 않는다

`tracker`/`opinion`도 별도 구조화 필드(`flow`/`step`/`context`/
`chapter` 등)를 두지 않는다 - **내용 자체를 자유 양식의 Markdown으로
기록**해서, 다른 `type`과 완전히 같은 일반 본문 필드를 그대로 쓴다.

**왜**: 절차/필드가 복잡해질수록 실제로는 잘 지켜지지 않더라(경험적
판단) - `tracker`가 지금 어떤 흐름의 몇 단계인지, `opinion`이 문서의
어느 부분을 가리키는지는 구조화된 필드 대신 본문 Markdown 안에 자유
서술로 남긴다. `parent_id`(무엇에 붙어있는지)와 `type`/`kind`/`state`
정도의 최소한의 구조만 유지하고, 나머지는 전부 자유 기록에 맡긴다.

### 칸반 보드
- v2에서 의외로 실효성이 낮았다 → v3에서는 채택하지 않는다.

### 문서 등록 현황 조회 응답 (`docs.status` 액션)

액션 카탈로그의 `docs.status`가 반환하는 형식이다 - 표준 응답 규격
(`notices`/`status`/`result`) 그대로를 따르고, `result`는 `kind`별
(`SP`/`RP`/`RM`/`QA`/`BT`/`PL`/`QU`/`AN`/`TC`/`OP`)로, 그 안에서
다시 상태별로 묶는다:

```
{
  notices: [ ... ],
  status: <응답 코드>,
  result: {
    lastEtag: <시스템 전체에서 가장 최근에 바뀐 문서의 변경 코드>,
    byKind: {
      "SP": { byState: { "draft": { count, lastUpdatedAt }, "review": { ... }, ... } },
      "RP": { byState: { ... } },
      "PL": { byState: { "added": { count, lastUpdatedAt }, ... } },
      "QU": { byState: { ... } },
      "AN": { byState: { ... } },
      "OP": { byState: { ... } },
      ...
    }
  }
}
```

라운드 1 초반에 스케치했던 `opinions`/`plans`/`questions`처럼
`type`별로 최상위 필드를 따로 두는 방식은 폐기하고, 위처럼 `kind`
단위로 통일한다 - `opinions`가 필요하면 `result.byKind.OP`, `plans`가
필요하면 `result.byKind.PL`을 보면 된다.

### 메시지 시스템 (상세 스펙)

- **문서 체계와 완전히 별개의 경량 엔티티다** - `remember`처럼
  `type`/`kind`/`parent_id`/git branch·commit 추적을 전혀 따르지
  않는다. 짧은 알림을 클로드(또는 architect)에게 전달하는 용도.
- **필드(초안)**: `id`, `from`('notice'|'from-web'|'etc'|'emerg'),
  `to`('agent'|'architect'|`<architectId>`), `body`(자유 텍스트),
  `state`('sent'|'read'|'done'|'canceled'), `ttl`(기본 `-1` =
  무제한), `createdAt`.
- **`to`(수신자) - 세 가지 값을 가질 수 있다**:
  - `agent` - 클로드 쪽으로(CLI/MCP 채널 응답의 `notices`에 실림).
  - `architect` - **아무 architect나** 받으면 되는 메시지(특정
    architect를 콕 집지 않음) - 그 프로젝트의 architect라면 누구든
    WEB UI에서 받을 수 있다.
  - `<architectId>` - **특정 architect 한 명**에게만 가는 메시지 -
    그 architectId로 로그인한 사람만 받는다.
- **보낸 주체**:
  - `notice` - 자동화된 메시지, 백엔드가 스스로 생성(예: 질의 등록
    같은 이벤트에 대한 알림) - 보통 `to: 'agent'`.
  - `from-web` - architect가 WEB UI에서 보낸 일반 메시지 - `to:
    'agent'`(클로드에게 전달).
  - `emerg` - architect가 WEB UI에서 보낸 **긴급** 알림 - 아래
    "전달 방식"에서 `notice`/`from-web`과 다르게 취급된다.
  - `etc` - 그 외.
- **전달 방식(piggyback)**: 별도 폴링 API 없이, **표준 응답
  envelope의 `notices` 배열이 곧 이 메시지 시스템에서 그 채널
  (`to`)에 아직 전달되지 않은(`sent`) 메시지들**이다 - **예외 없이
  모든 응답에 통합되어 함께 발신되는 구조**다(조회든 변경이든, 어떤
  액션의 응답이든 전부 포함해서 - 메시지 전용 조회 액션을 따로 부르지
  않아도 된다). 전달되는 순간(그 응답에 실리는 순간) 그 메시지는
  `sent` → `read`로 자동 전이한다.
  - 예시 `notice` 문구: "[SP-xxxxxxxx]가 등록되었습니다",
    "[SP-xxxxxxxx]에 질의가 등록되었습니다".
- **`emerg`는 piggyback을 기다리지 않는다** - 일반 메시지는 클로드가
  다음 API를 호출할 때까지 기다렸다 전달되지만, `emerg`는 그 외에도
  **EMQX로 즉시 브로드캐스트**돼서 실시간으로 알린다(다음 호출을
  기다리지 않아도 되게).
- **상태 전이**:
  1. 생성 시 `sent`.
  2. 다음 응답의 `notices`에 실리는 순간 자동으로 `read`.
  3. 받은 쪽(주로 클로드)이 그 내용을 실제로 처리했다고 판단하면
     `done`으로 전이(수동).
  4. 아직 전달되지 않은(`sent`) 메시지는 보낸 쪽(architect)이
     `canceled`로 철회할 수 있다 - `question`의 `discard`와 같은
     발상으로, **`read` 이후엔 취소할 수 없다**.
- **TTL**: 기본 `-1`(무제한) - TTL이 지정된 메시지가 `sent` 상태로
  유효 시간을 넘기면 자동으로 `canceled` 처리되어 더 이상 어떤
  응답의 `notices`에도 실리지 않는다.
- **액션**: 문서 액션 카탈로그와 같은 원칙(통합 명령, bulk 기본)으로
  `message.send`(주로 architect/WEB UI가 `from-web`/`emerg` 생성),
  `message.list`(이력 조회), `message.transition`(수동 `done`/
  `canceled` 전이) 정도로 최소화한다 - `notice`는 백엔드 내부
  이벤트가 직접 생성하므로 별도 액션이 필요 없다.

### API/MCP/CLI 설계 (제안 - 확인 필요)

*지금까지 정한 원칙(단일 엔드포인트 + command 패턴, bulk 기본,
응답 규격, etag, 문서 체계/체인 규칙, remember, opinion, push-mirror
옵션 등)을 실제 API/MCP/CLI 형태로 정리한 제안이다. 확정 아님 -
설계자 확인/수정 필요.*

**API - 단일 엔드포인트(+ 인증은 예외)**
- `POST /api/actions` 하나만 둔다 - 조회든 변경이든 예외 없이 이
  엔드포인트로, `action` 객체의 배열을 보낸다(위 bulk 형식 그대로).
  조회 전용 액션도 별도 REST 엔드포인트를 만들지 않고 이 안에
  포함시켜서, "명령 체계를 압축한다"는 원칙과 "단일 엔드포인트"를
  일관되게 유지한다.
- **인증(로그인)만은 이 액션 체계 밖에 별도 엔드포인트로 둔다** -
  `/api/actions`는 이미 유효한 `apiKey`가 있어야 호출할 수 있는데,
  로그인은 애초에 그 `apiKey`를 발급받는 절차라 같은 체계 안에 넣을
  수 없다(닭과 달걀 문제). 그래서 `docs auth login`(아이디/패스워드
  로그인)은 액션 카탈로그에 넣지 않고 별도 인증 전용 엔드포인트
  (예: `POST /api/auth/login`)로 처리한다.

**액션 카탈로그(초안)**
- `docs.add` - 문서 등록(`type`/`kind`/`parent_id`/`title`/`content`/
  챕터 등).
- `docs.update` - 내용 수정(`etag` 필요).
- `docs.delete` - **하드 삭제. 용도는 `answer` 철회 하나뿐이다**
  (`etag` 필요) - 문서는 기본적으로 git 이력처럼 계속 추적되는 게
  철학이라 다른 `type`은 하드 삭제하지 않고 상태 전이(`discard`
  등)로 처리한다. `answer`만 예외인 이유: `answer`엔 `discard`가
  없고(위 "discard가 없는 이유" 참고) 한 질의당 답변이 최대 1개로
  제한되므로, 완전히 새로 쓰고 싶으면(부분 수정이 아니라 통째로
  철회) 기존 답변을 삭제해야 그 자리에 새 답변을 다시 등록할 수
  있다 - 부분 수정은 여전히 `docs.update`.
- `docs.transition` - 상태 전이(이미 정의된 `state` 튜플 형식).
- `docs.tag` - 연관 문서 태깅(`{code, etag}[]`).
- `docs.get` - 단일 문서 조회(`etag` 포함 반환).
- `docs.list` - 목록 조회(`{page, total, items}`).
- `docs.search` - Meilisearch 검색(추적 코드/branch/commit_id/etag
  반환).
- `docs.status` - 시스템 상태 종합 조회(형식은 위 "문서 등록 현황
  조회 응답" 절 참고).
- `docs.grep` - 특정 문서(추적 코드) 안에서 패턴 하나만 짚어서 본다
  (v2에서 실제로 자주 쓰던 흐름 - 패턴/키워드 하나만 확인하고 싶을
  때 전체 본문을 받는 대신 이걸로 그 부분만 발췌). 패턴은 **POSIX
  정규식(ERE)** 형태를 쓴다 - PostgreSQL이 `~`/`~*` 연산자로 POSIX
  ERE를 네이티브 지원하므로 그대로 SQL로 위임할 수 있다.
- `remember.add`/`remember.update`/`remember.delete`/`remember.list`
  - `remember` 항목 관리(문서 체계와 별개 엔티티지만 같은 액션
  배열/엔드포인트를 공유).
- `repo.push` - 내부 저장소를 외부로 동기화(옵션 push-mirror 기능,
  설계자가 명시적으로 눌러야 하는 동작에 대응).

**CLI**
- 액션과 1:1 매핑되는 서브커맨드(`docs add`, `docs update`, `docs
  transition`, `docs tag`, `docs get`, `docs list`, `docs search`,
  `docs status`, `docs grep`, `remember add`/..., `repo push`) -
  내부적으로 액션 배열을 만들어 위 단일 엔드포인트로 보낸다.
- 액션과 무관하게, 인증/설정용으로 `docs auth login`도 둔다(아래
  "CLI 설정 파일" 절 참고).
- "변경 사항 스테이징"(로컬에 쌓았다 한 번에 push) 흐름은 CLI가
  로컬에 액션 배열을 파일로 쌓아두고, `docs push` 시점에 한 번에
  전송하는 방식으로 구현한다.

**CLI 로컬 스테이징**
- 로컬 스테이징은 **파일로 쌓는다** - CLI가 액션 객체를 로컬 파일에
  누적하고, `docs push` 시점에 그 파일 내용을 배열로 읽어 한 번에
  단일 엔드포인트로 전송한다.

**CLI 로컬 캐시 - list/read 분리는 CLI의 책임**
- `docs.list`/`docs.search` API 자체는 각 문서의 전체 내용을 그대로
  돌려준다(위 "조회 액션의 result 모양" 참고) - 요약은 API 책임이
  아니다.
- 대신 **CLI 유틸리티가 매번 로컬 캐시를 만들고 갱신한다** - `docs
  list`/`docs search`를 실행할 때마다 그 전체 응답으로 로컬 캐시를
  새로 만들거나 갱신해둔다.
- **AI(클로드)에게 실제로 보여주는 출력은 이 캐시를 근거로 list와
  read 두 가지로 나뉜다**:
  - `docs list`/`docs search` 실행 결과로 AI에게는 **요약**(추적
    코드/type/kind/title/state/etag/updatedAt 정도)만 보여준다 -
    본문은 로컬 캐시에는 있지만 굳이 다 보여주지 않는다("도구 호출
    응답 최소화" 원칙).
  - `docs get`(read)을 실행하면 그제서야 **본문 전체**를 보여준다 -
    이미 로컬 캐시에 있으면 그걸 그대로 쓰고, 없거나 오래됐으면
    새로 조회해서 캐시를 갱신한 뒤 보여준다.
  - 즉 API는 단순하게(list=전체) 유지하고, "AI 컨텍스트를 아낀다"는
    책임은 CLI 계층에서 진다.

**CLI 설정 파일 (프로젝트별 + 홈 디렉터리)**
- **프로젝트별 설정**: 프로젝트 루트에 `.cnw/config.json`을 두고,
  **설계자 식별자는 넣지 않는다** - 누가 작업하든 값이 똑같은
  두 가지만 둔다:
  ```
  { "httpEndpoint": "<HTTP 끝점>", "projectId": "<프로젝트 ID>" }
  ```
  이렇게 하면 이 파일은 개인 식별 정보가 전혀 없으므로 **git으로
  커밋해도 문제가 없다**(여러 설계자가 같은 프로젝트를 체크아웃해도
  다같이 공유해도 되는 값만 들어있음).
- **홈 디렉터리 설정**: `$HOME/.cnw/config.json`에 `httpEndpoint` →
  `projectId` → `architectId` 순으로 중첩해서, 각 조합마다 실제
  호출에 쓸 `endpoint`/`apiKey`를 저장한다:
  ```
  {
    "<httpEndpoint>": {
      "<projectId>": {
        "<architectId>": { "endpoint": "https://...", "apiKey": "..." }
      }
    }
  }
  ```
  `architectId`는 여전히 **API 키와는 별개로, 이 시스템 내부에서만
  유효한 절대 식별값**이다(키가 재발급/회전돼도 바뀌지 않는 값) -
  다만 이제 이 값은 프로젝트 설정이 아니라 홈 디렉터리에만 있다.
- **`.cnw/session.json` (커밋 금지)**: 프로젝트 설정과 같은 `.cnw/`
  디렉터리에 두되, **git으로 커밋하면 안 된다** - 커밋해도 동작이
  깨지진 않지만, 그 저장소를 새로 clone한 다른 architect는 자신의
  architectId가 아니라 커밋된 남의 architectId를 보게 되어 혼란을
  겪는다. 내용:
  ```
  { "architectId": "<이 로컬 체크아웃이 사용할 architectId>" }
  ```
  이 파일이 바로 "같은 `httpEndpoint`/`projectId` 조합 아래
  `architectId`가 여러 개 있을 때 어떤 걸 쓸지" 선택 문제의 답이다 -
  `docs auth login` 시 로그인한 architectId를 이 파일에 기록해두고,
  이후 CLI는 이 파일의 architectId로 홈 설정에서 정확히 그 항목만
  찾아 쓴다.
- CLI는 실행될 때 (1) 현재 디렉터리에서 위로 올라가며(git의 `.git`
  탐색과 동일한 방식) `.cnw/config.json`을 찾아 `httpEndpoint`/
  `projectId`를 얻고, (2) 같은 위치의 `.cnw/session.json`에서
  `architectId`를 얻고, (3) 홈 설정에서 그 `httpEndpoint`/
  `projectId`/`architectId` 조합을 조회해 실제 호출할 `endpoint`/
  `apiKey`를 얻는다.

**`docs auth login` (홈 디렉터리 설정을 만드는 명령)**
- `docs auth login --rest-url=<서버 URL>` - **아이디/패스워드로
  로그인**해서 홈 디렉터리 설정(`$HOME/.cnw/config.json`)에 그
  architect의 `endpoint`/`apiKey`를 기록한다(로그인 자체는 아이디/
  패스워드, 이후 CLI/MCP 호출은 그때 발급된 `apiKey`로).
- `--rest-url`을 생략하면 **기본 서버**를 쓴다 - 지금 단계의 기본값은
  `http://127.0.0.1:8388`.
- **최초 설치 시 부트스트랩 관리자 계정**: 최소 설치 작업(초기 설정)을
  진행할 때, 특수 관리자 계정을 자동 생성한다 - 아이디 `admin`,
  패스워드 `12345678`. (실제 운영에 들어가면 최우선으로 비밀번호를
  바꿔야 하는 임시 계정이라는 점은 설치 문서에 명시해야 한다.)

**MCP - 조회/변경 도구 분리**
- type/액션별로 도구를 잘게 쪼개지는 않되, **조회(query)와 변경
  (mutation)만큼은 최소한 별도 도구로 나눈다** - 도구 하나로 전부
  뭉치면 (a) 그 하나의 설명/스키마가 조회+변경 액션을 전부 커버해야
  해서 오히려 커지고, (b) 조회는 부작용이 없어 자동 허용해도 되는
  반면 변경은 승인이 필요하다는 성격 차이를 도구 단위로 구분하기
  어려워진다(이 세션 자체의 권한 모델과 같은 이유). 그래서:
  - `docs_query` - `docs.get`/`docs.list`/`docs.search`/`docs.status`
    등 조회성 액션 전담.
  - `docs_action` - `docs.add`/`docs.update`/`docs.delete`/
    `docs.transition`/`docs.tag`/`repo.push`/`remember.*` 등 변경성
    액션 전담.
  둘 다 내부적으로는 여전히 액션 배열 + 단일 API 엔드포인트를 그대로
  쓰는 얇은 래퍼일 뿐이다 - "명령 체계 압축" 원칙은 유지하되, 안전성
  구분이 필요한 지점(조회 vs 변경)에서만 도구를 나눈다.

### UI 설계 - GitHub 유사 매핑 (수정)

라운드 1 초반에 정한 "UI는 GitHub과 최대한 유사하게 구성한다"를
구체화한 것 - 처음 제안(Wiki/Issues/Actions 화면을 그대로 재사용하는
매핑)은 기각되고, "역할은 GitHub의 그것과 유사하되 화면 자체는
독립적으로 새로 설계한다"는 원칙으로 정정됐다.

- **`doc`(SP/RP/RM/QA/BT)** - GitHub Wiki를 그대로 쓰는 게 아니다.
  역할은 비슷하지만(문서를 쌓아두고 본다) **독립된 Tab**을 하나
  두고, 그 안에 **목록(List)**과 **Source View**(본문/챕터를 보는
  화면)로 구성한다.
- **`plan`** - 역할은 GitHub Issues 목록과 비슷하지만(할 일 목록),
  **내용물은 스타일(시각적 톤)만 맞추고 구성 자체는 독립적으로
  설계한다** - Issues 화면의 필드/기능을 그대로 재사용하지 않는다.
- **`question`/`answer`** - 별도의 독립 화면(Q&A 전용 탭)을 만드는
  게 아니라, **각 문서(`doc`/`plan`/...)의 화면 안에 그 문서의
  역할에 맞게 통합**된다 - PR 리뷰 코멘트처럼 그 문서를 보는
  화면 안에서 바로 달고 볼 수 있어야 한다.
- **`opinion`** - `question`/`answer`와 같은 방식으로 각 문서 화면에
  통합되되, 방향이 고정(architect → 클로드)이라는 것만 다르다.
- **`tracker`/`test`** - 둘 다 Actions/Checks 탭을 그대로 재사용하지
  않고, **각자의 목적에 맞게 독립적으로 UI를 설계한다**.
- collaborator 관리 - GitHub의 "Settings → Collaborators"와 유사한
  형태(권한 레벨 `Read`/`Write`/`Admin` 선택 포함).
- git branch/commit을 따라다니는 문서 조회 - GitHub의 "특정 브랜치/
  커밋 시점의 파일 보기"와 같은 감각으로, 브랜치/커밋을 선택해 그
  시점의 문서 상태를 볼 수 있게.
- `remember` - **UI 화면 자체를 두지 않는다** - 사람이 볼 필요 없는
  데이터라, API/CLI/MCP로만 다루고 GitHub 유사 UI에는 아예 노출하지
  않는다.

### API 응답 규격 — 통합 정리 (제안 - 확인 필요)

지금까지 여러 절에 흩어져 나온 응답 규격(표준 envelope, 리스트,
bulk, etag, `docs.status`)을 액션별로 한데 모은 정리다. 새로운
결정은 아니고, 지금까지 정한 걸 모아서 빠진 부분(조회 액션들의
`result` 모양)을 채운 것이다.

**공통 envelope** (모든 액션 배열 응답의 최상위):
```
{ notices: [ ... ], status: <응답 코드>, result: <액션별 result 배열> }
```

**조회 액션의 `result` 모양**
- `docs.get` - 문서 하나를 그대로: 위 "문서 스키마" 그대로(본문
  포함) + `etag`.
- `docs.list` - `{ page, total, items: [ <문서 전체(본문 포함) 배열> ] }`
  - **API 자체는 요약이 아니라 각 문서의 전체 내용을 그대로 돌려준다**
  (`docs.get`과 같은 모양의 객체들의 배열). "리스트인데 왜 본문까지
  주냐"의 답은 CLI 계층에서 나온다 - 아래 "CLI 로컬 캐시" 절 참고:
  API는 단순하게 전체를 주고, **AI에게 실제로 보여줄 내용을
  list/read로 나누는 건 CLI의 책임**이다.
- `docs.search` - `{ page, total, items: [ { code, branch, commit_id,
  etag, ... } ] }` (Meilisearch 결과).
- `docs.status` - `{ lastEtag, byKind: { ... } }` (위 "문서 등록
  현황 조회 응답" 절 그대로).
- `docs.grep` - 문서 하나 안에서 매칭된 부분만: `{ code, matches:
  [ { line, text } ] }` 형태로 발췌(전체 본문은 포함하지 않음 -
  "도구 호출 응답 최소화" 원칙).

**변경 액션(`docs.add`/`update`/`delete`/`transition`/`tag`,
`remember.*`, `repo.push`)의 bulk 결과**: 이미 정한 대로 요청 액션
배열과 인덱스 1:1 매칭되는 `{ ok, reason? }` 배열.

**해결**: `ok: true`인 항목도 `data` 필드로 결과 데이터(새 추적
코드/`etag` 등)를 같이 돌려준다 - 위 "API 응답 규격"의 bulk 형식에
반영됨.

**문서 전체에 적용되는 메모**: 이 문서에 나오는 JSON 예시들은 그
"모양"과 의도를 보여주는 예시이지, 바이트 단위로 지켜야 하는 고정
계약이 아니다 - 실제로 필요하면 필드를 추가/조정해도 된다(이번
`data` 필드 추가가 그 예).

### `question`/`answer` 액터 규칙 — 통합 정리

여러 절에 흩어진 질의/답변 규칙을 한데 모았다.

- **질의자**: `question`은 클로드 또는 architect 누구나 등록할 수
  있다 - 부모 문서 타입 제한도 없다(어디든 부착 가능, 위 "체인 제약"
  절 참고).
- **답변자**: `answer`는 질의자의 **반대편만** 등록할 수 있다 -
  질의자가 클로드면 architect만, architect면 클로드만 답변 가능.
- **1문 1답**: `answer`의 `parent_id`는 반드시 그 `question`을
  가리키고, 한 질의에 직접 달리는 답변은 최대 1개다. 답변을
  고치고 싶으면 새 답변을 만드는 게 아니라 기존 답변을 갱신한다
  (`discard` 없음 - 위 "답변 상태" 절의 이유 그대로).
- **답변의 내용 형식**: 전용 필드 없이 자유 Markdown - 질의가
  승인/거부를 요구하면 그 형태로, 애초에 자유 서술이 요구되면
  자유 서술로(위 "`answer`도 전용 구조화 필드를 두지 않고" 절 참고).
- **상태 전이 흐름**:
  1. 질의자가 `question`을 `added`로 등록.
  2. 상대방(답변자)이 열람하면 `question`이 `read`로 전이.
  3. 답변자가 `answer`를 `added`로 등록.
  4. 질의자가 답변을 열람하면 `answer`가 `read`로 전이.
  5. 질의자가 "이걸로 해소됨"을 확정하면 `answer`가 `done`으로,
     동시에 원래 `question`도 `done`으로 전이.
- **철회(`discard`)는 질의자 본인만**, 그리고 **아직 해소되지 않은
  질의(`added`/`read`)에서만** 가능하다 - 이미 `done`으로 해소된
  질의는 다시 `discard`할 수 없다(`done`/`discard`는 서로 다른 두
  종료 경로이지, `done` 다음 단계가 `discard`인 게 아니다).
- **후속 질의**: 답변에 또 의문이 생기면, 그 답변을 `parent_id`로
  가리키는 새 `question`을 등록해서 체인을 이어간다(카디널리티
  제한 없음 - 같은 답변에 여러 후속 질의가 달릴 수 있음).
- **연쇄 전이**: architect가 요청한 작업을 처리하는 흐름 안에서는
  클로드가 이 질의/답변 상태들을 여러 단계 한 번에 연쇄 전이시킬 수
  있다 - 다만 breaking change에 해당하면 예외(위 "연쇄 전이" 절
  그대로 적용).

### 문서 검색/목록 필터 조건

`docs.list`/`docs.search`(및 CLI/MCP의 대응 명령)에 쓸 수 있는 필터
조건을 정리한 초안이다. 여러 필터는 AND로 좁혀진다.

- `type` - `doc`/`plan`/`question`/`answer`/`tracker`/`test`/
  `opinion` 중 하나 또는 배열.
- `kind` - `SP`/`RP`/.../`OP` 중 하나 또는 배열.
- `state` - 그 `type`에 유효한 상태값 중 하나 또는 배열.
- `branch` - git branch 명칭.
- `commit_id` - 특정 commit 시점의 문서만.
- `parent_id` - 특정 문서의 직계 자식만(문서 체인 하위 탐색).
- `author` - 작성자(`architect` 식별자 또는 클로드) 기준.
- `related` - 특정 추적 코드와 연관 태깅된 문서만.
- `updatedSince`/`updatedBefore` - `docs.status`가 집계에 쓰는
  "마지막 업데이트 일자"와 같은 필드 기준 범위 필터. (이 필드가
  문서 스키마에 명시적으로 없었는데, 상태 조회 응답이 이미 이 값을
  전제하고 있으므로 스키마에도 `updatedAt`/`createdAt`을 정식으로
  추가한다.)
- `q` - 일반 전문 검색어(`docs.search` 전용, Meilisearch, `docs.list`
  는 구조화 필터만).
- `grep` - `docs.search`가 `q` 대신 `grep`을 받으면 여러 문서에
  걸친 **POSIX 정규식(ERE)** 검색이 된다(`docs.grep`과 같은 문법,
  PostgreSQL `~`/`~*` 경로) - `q`/`grep`은 파라미터 이름으로 확실히
  구분되고, 휴리스틱으로 정규식 여부를 추측하지 않는다.
- `sort` - 정렬 기준. 일반적인 필드(예: `updatedAt`) 외에 **`dependency`**
  를 지원한다 - "아직 해소되지 않은 `dependsOn` 개수"가 적은(=바로
  시작 가능한) 문서부터 정렬(위 "문서 의존성" 절 참고).

`chapter` 전용 필터는 두지 않는다 - 챕터는 어차피 제목 문자열이므로,
그 챕터를 찾고 싶으면 `q`(자유 텍스트 검색)로 커버한다. 구조화 필터를
따로 만들지 않는 것도 "절차/필드가 복잡해질수록 잘 안 지켜진다"는
원칙과 같은 방향이다.

### Meilisearch 활용 최적화 방안

POSIX 정규식은 Meilisearch가 못 다루므로 하이브리드가 불가피한데,
그렇다고 Meilisearch를 정규식 우회 경로 정도로만 쓰면 아깝다 - 아래
방향으로 적극 활용하는 걸 제안한다.

- **일반 검색과 정규식 검색을 파라미터 이름으로 분기한다** - 휴리스틱
  (메타 문자 감지) 없이, **`q`는 항상 일반 검색(Meilisearch), `grep`
  파라미터로 들어오면 항상 POSIX 정규식(PostgreSQL `~`/`~*`)**으로
  고정한다. `docs.grep`(단일 문서 발췌)과 이름을 맞춰서, `docs.search`
  가 `{ q }` 대신 `{ grep }`을 받으면 여러 문서에 걸친 정규식 검색이
  된다 - 전수 정규식 스캔을 기본 경로로 두지 않는다.
- **구조화 필터도 Meilisearch에 함께 태운다**: `type`/`kind`/`state`/
  `branch`/`author`/`related` 등을 Meilisearch의 filterable/facet
  속성으로 인덱싱해서, `docs.list`/`docs.search`의 구조화 필터 +
  텍스트 질의를 **Meilisearch 한 번의 조회로 같이 처리**한다(PostgreSQL
  으로 다시 join할 필요 없이). PostgreSQL은 쓰기/etag 동시성 제어의
  정본으로 남고, Meilisearch는 읽기 전용 검색 인덱스로 특화된다.
- **`docs.status` 집계도 Meilisearch의 facet distribution으로**:
  `kind`별/`state`별 개수 집계(위 "문서 등록 현황 조회 응답")를
  PostgreSQL `GROUP BY` 대신 Meilisearch의 facet 카운트로 뽑으면,
  문서가 많아져도 빠르게 유지된다.
- **정규식 검색의 사전 축소**: 정규식 검색이 필요할 때도, 먼저
  Meilisearch로 구조화 필터(예: `type`/`branch`)를 적용해 후보를
  좁힌 다음, 그 후보 집합에 대해서만 PostgreSQL 정규식을 돌리면
  전수 스캔을 피할 수 있다.
- **인덱싱은 EMQX 브로드캐스트를 구독해서 비동기로**: 이미 모든
  문서 CRUD가 EMQX로 브로드캐스트되므로(위 "실시간 브로드캐스트"
  절), Meilisearch 인덱서를 그 브로드캐스트의 구독자로 붙여서
  변경이 생길 때마다 비동기로 재인덱싱한다 - 쓰기 API가 Meilisearch
  인덱싱 완료를 기다리지 않아도 된다("git 동작을 오버라이드하지
  않고 내부 콜백으로만 추적"과 같은 발상).

### 백엔드 캐시 (검색/리스트류)

- **목적**: `docs.list`/`docs.search`/`docs.status`처럼 조회 위주인
  액션은 **백엔드에서도 캐시해야 한다** - CLI 로컬 캐시(위 "CLI
  로컬 캐시" 절)는 클라이언트 하나마다 따로 있는 캐시일 뿐이라,
  여러 클라이언트/여러 architect가 동시에 같은 걸 조회하면 매번
  Meilisearch/PostgreSQL을 다시 치게 된다.
- **방식**: 지금 단계에서는 새 인프라(Redis 등)를 추가하지 않고
  **백엔드 프로세스 내 인메모리 캐시**로 시작한다 - 키는 액션 +
  필터 + 프로젝트 조합, 값은 그 조회 결과.
- **무효화 시점은 세 가지다**:
  1. **git으로 파일이 커밋될 때** - "git 동작을 오버라이드하지 않고
     내부 콜백으로만 추적"하는 그 콜백을 캐시 계층도 구독한다.
  2. **문서가 수정/삭제될 때** - 이미 모든 CRUD가 EMQX로
     브로드캐스트되므로(Meilisearch 인덱서와 같은 구독 패턴), 캐시
     계층도 그 브로드캐스트를 구독해서 무효화한다.
  3. **더 일반적으로, 그 캐시가 만들어질 때 근거로 삼은 원본이
     바뀌었다고 감지되는 시점** - 즉 캐시 항목마다 "이 결과가 어떤
     원본(문서/커밋)에서 나왔는지"를 같이 기억해두고, 그 원본 중
     하나라도 바뀌면 그 캐시를 무효화한다(단순히 같은 키를 지우는
     걸 넘어, 그 결과에 포함됐던 원본들과의 의존 관계를 추적).
- **확장 여지**: 나중에 백엔드가 여러 인스턴스로 스케일아웃되면
  인메모리 캐시가 인스턴스마다 따로 놀게 되므로, 그때는 공유 캐시
  (Redis 등)로 옮기는 걸 검토한다 - 지금 단계에서는 도입하지 않는다.

### 예시: 답변에 재질의를 등록하는 흐름

지금까지 정한 규칙(문서 체인, 챕터 부착, 액션 카탈로그, 연쇄 전이,
"질의가 해소되기 전까지 문서 상태 변경 불가")을 하나의 시나리오로
엮은 예시다. `SP-XJQCTF6Y`(이 설계 노트 자신)의 "라운드 1" 챕터에
architect가 질문을 다는 상황을 가정한다.

1. **architect가 질문 등록** - `SP-XJQCTF6Y`의 특정 챕터를 가리켜서:
   ```
   { "action": "docs.add", "type": "question", "kind": "QU",
     "parent_id": "XJQCTF6Y", "chapter": "라운드 1 ...",
     "content": "이 부분 왜 이렇게 했나요?" }
   ```
   → 새 질의 `QU-AAAA1111` (`added`).
2. **클로드가 열람**: `{ "action": "docs.transition", "state": { "AAAA1111": ["read", "added"] } }`.
3. **클로드가 답변 등록** - 부모는 그 질의:
   ```
   { "action": "docs.add", "type": "answer", "kind": "AN",
     "parent_id": "AAAA1111", "content": "그건 ~ 때문입니다." }
   ```
   → 새 답변 `AN-BBBB2222` (`added`).
4. **architect가 답변 열람**: `{ "action": "docs.transition", "state": { "BBBB2222": ["read", "added"] } }`.
   이 시점 `QU-AAAA1111`은 아직 `done`이 아니므로(자신은 여전히
   `read`), `SP-XJQCTF6Y`의 상태는 바뀔 수 없다.
5. **architect가 그 답변을 보고 또 의문이 생겨 재질의 등록** - 이번
   부모는 방금 그 **답변**(`AN-BBBB2222`):
   ```
   { "action": "docs.add", "type": "question", "kind": "QU",
     "parent_id": "BBBB2222", "content": "그럼 ~ 경우엔 어떻게 되나요?" }
   ```
   → 새 질의 `QU-CCCC3333` (`added`). 원 질의 `QU-AAAA1111`은 여전히
   `read`로 묶여있다(체인이 깊어져도 문서 잠금 조건은 그대로 유지).
6. 클로드가 `QU-CCCC3333`을 열람하고 답변 `AN-DDDD4444`를 등록 -
   2~3단계와 동일한 패턴.
7. **architect가 만족** - 이제 체인 전체를 한 번의 `docs.transition`
   으로 연쇄 전이시킨다(위 "연쇄 전이" 원칙 - architect가 요청한
   작업이므로 클로드가 한 번에 처리 가능):
   ```
   { "action": "docs.transition", "state": {
       "DDDD4444": ["done", "read"],
       "CCCC3333": ["done", "read"],
       "BBBB2222": ["done", "read"],
       "AAAA1111": ["done", "read"]
   } }
   ```
   답변이 `done`으로 전이될 때마다 그 부모 질의도 같이 `done`으로
   전이되므로, 이 한 번의 호출로 체인 전체가 해소된다 - 그제서야
   `SP-XJQCTF6Y`의 상태를 바꿀 수 있게 된다.

### 문서 의존성 (`dependsOn`) - 구현 우선순위 자동 책정용

- **목적**: 문서(특히 `plan`)가 다른 문서에 **의존성**을 가질 수
  있어야 한다 - "이 계획은 저 계획이 먼저 끝나야 시작할 수 있다"
  같은 관계를 명시적으로 표현해서, **구현 우선순위를 자동으로
  책정**하는 데 쓴다.
- **`parent_id`/`related`와는 다른 세 번째 관계**다:
  - `parent_id` - 계층적 부모-자식(1:N), "하위 문서".
  - `related` - 대칭적 다대다 태깅, 순서/방향 의미 없음.
  - `dependsOn` - **방향이 있는** 다대다 관계, "이 문서는 저 문서에
    의존한다"(저게 먼저 끝나야 한다) - 그래프로 보면 방향 그래프
    (DAG)를 이룬다.
- **입력 형식은 `related`와 동일**: `[{ code, etag }, ...]`(태깅
  시점 etag 포함, 동시 편집 충돌 방지 원칙 재사용).
- **순환 의존성도 허용한다** - A가 B에 의존하고 B가 다시 A에
  의존하는 것도 유효하다(등록/수정 시 순환을 거부하지 않는다).
  한 문서가 여러 개의 `dependsOn`을 가지는 것도 당연히 가능하다.
- **우선순위 계산은 엄격한 위상 정렬이 아니다** - 순환을 허용하는
  이상 전체를 하나의 순서로 딱 떨어지게 정렬할 수는 없다. 대신
  문서마다 **"아직 해소(`done`)되지 않은 `dependsOn` 개수"**를
  readiness 지표로 계산해서, 그 개수가 적을수록(0이면 바로 시작
  가능) 우선순위가 높다고 본다 - 순환이 있는 문서들은 서로를 계속
  가리키며 개수가 안 줄어들 수 있는데, 이는 오류가 아니라 "서로
  맞물려 있다"는 실제 신호로 그대로 보여준다.
- **노출 방식**: 별도 액션을 만들지 않는다 - `dependsOn`/readiness는
  이미 각 문서 응답 자체에 들어있는 정보이고(문서마다 자기
  `dependsOn`을 갖고 있으므로), `docs.list`에 **정렬 옵션으로
  `의존성`(readiness 지표 기준 정렬)을 추가**해서 노출한다.

### 회원가입/초대 절차 (제안 - 확인 필요)

- **계정(로그인 가능한 자격)과 프로젝트 collaborator는 분리된
  개념이다** - 계정은 시스템 전역에 하나만 존재하고(아이디/패스워드,
  로그인하면 `architectId`가 그 계정에 묶임), 그 계정이 여러
  프로젝트에 서로 다른 권한 레벨(`Read`/`Write`/`Admin`)로
  collaborator로 붙을 수 있다.
- **시스템 전체 가입(계정 생성)은 누구나 할 수 있다** - 셀프 가입이
  열려있다(아이디/패스워드를 스스로 정해서 가입). 부트스트랩
  `admin`/`12345678` 계정은 시스템 전체의 첫 `Admin`으로서, 최소
  설치 작업(초기 설정)을 진행하기 위한 것일 뿐 계정 생성 자체를
  독점하지 않는다.
- **다만 프로젝트 참여는 다르다** - 계정이 있다고 아무 프로젝트에나
  들어갈 수 있는 게 아니라, **그 프로젝트 안에서 `Admin` 권한을
  가진 사용자가 초대해야만** collaborator가 될 수 있다(아래 "프로젝트
  초대" 참고).
- **프로젝트 초대**: 프로젝트의 `Admin`이 (이미 존재하는) 계정을
  그 프로젝트에 `Read`/`Write`/`Admin` 중 하나로 초대한다 - 계정이
  아직 없으면 먼저 계정을 만든 뒤 초대한다(계정 생성과 프로젝트
  초대가 한 번에 이뤄지는 흐름도 가능).
- **비공개 프로젝트는 초대 수락 전까지 보이지 않는다** - 초대는
  바로 collaborator로 확정되는 게 아니라 **대기(pending) 상태**로
  생성되고, 초대받은 계정이 로그인해서 그 초대를 **수락**해야만
  실제 collaborator가 되어 그 프로젝트가 보이기 시작한다(수락 전엔
  프로젝트 목록/내용 모두 비공개 상태 그대로).
- **미정**: 임시 패스워드 최초 로그인 시 강제 변경 여부, 계정
  비활성화/삭제 절차 - 이번 라운드에서는 다루지 않고 다음으로
  넘긴다.

### 프로젝트 공개/비공개 스코프 (제안 - 확인 필요)

- 프로젝트는 `visibility: 'public' | 'private'`를 가진다. **새
  프로젝트는 기본적으로 `private`**다(안전한 기본값 - 위 "비공개
  프로젝트는 초대 수락 전까지 보이지 않는다"와 일관되게).
- **`private`** - 그 프로젝트에 초대를 수락한 collaborator만 볼 수
  있다(목록에도 안 뜨고 내용도 접근 불가).
- **`public`** - 이 시스템에 계정이 있는 사람이면 **누구나 읽기
  (Read)는 가능**하다(collaborator로 초대되지 않아도 조회 가능) -
  다만 쓰기(`Write`/`Admin`)는 여전히 초대받은 collaborator만
  할 수 있다. 이 시스템이 인터넷에 공개되는 상황을 가정하지 않으므로
  "누구나"는 **로그인된 계정 전체**를 뜻하고, 비로그인 익명 접근까지
  허용하는 건 아니다.
- `visibility` 전환(`private` ↔ `public`)은 그 프로젝트의 `Admin`만
  할 수 있다.

### 닉네임 정책 / 사용자별 API 키 관리 - v2 정책 계승

- **닉네임 정책**과 **사용자별(개인/프로젝트 단위) API 키 관리
  정책**은 새로 설계하지 않고 **v2의 정책/규칙을 계승**한다 - 다만
  "그대로 따른다"(v2 코드를 그대로 가져다 쓴다)는 건 부적절하다.
  v3는 데이터 모델/API(단일 엔드포인트+액션 카탈로그)/팀·프로젝트
  그룹 폐지 등으로 아키텍처 자체가 다르므로, 구현은 v3 구조에 맞게
  새로 하되 **정책(닉네임 규칙, 키의 스코프·발급/회수 개념 등)만
  v2와 동일하게** 가져간다 - v2 브랜치는 "이 정책이 정확히 뭐였는지"
  확인할 참고 자료로 쓴다.
- v2의 "팀 키"(`TeamKeysManager` 등 팀/프로젝트 그룹 단위 키)는
  이번 라운드에서 팀/프로젝트 그룹 자체를 없앴으므로 자동으로
  대상이 아니다 - 개인 키/프로젝트 키 범위만 계승 대상이다.

### 프로젝트 설정 항목

지금까지 나온 결정들 중 "프로젝트마다 값이 다를 수 있는 것"을
모으면 아래가 프로젝트 설정 화면에 들어갈 후보다:

- **기본 정보** - 이름, 설명.
- **`visibility`**(`public`/`private`) - 위 "프로젝트 공개/비공개
  스코프" 절 그대로, 전환은 그 프로젝트의 `Admin`만.
- **collaborator 관리** - 초대/제거, `Read`/`Write`/`Admin` 권한
  레벨 변경(위 "회원가입/초대 절차" 절).
- **기본 브랜치(default branch)** - WEB UI에서 `parent_id` 없는 새
  문서를 만들 때 "HEAD 기준"이라고 한 그 HEAD가 어느 브랜치의
  HEAD인지(위 "git 연동"의 branch/commit_id 자동 채움 규칙과 연결).
- **push-mirror 대상**(옵션 기능) - 외부 저장소 URL과 인증 정보.
  `repo.push`가 실제로 어디로/무엇으로 인증해서 내보낼지가 아직
  정해지지 않았던 부분인데, 여기 프로젝트 설정에 저장하는 것으로
  채운다.
- **메시지 TTL 기본값** - **프로젝트별 override를 허용한다** - 시스템
  전역 기본값(`-1`)을 그대로 쓸 수도, 프로젝트 설정에서 그 프로젝트
  전용 기본 TTL로 바꿀 수도 있다.
- **양도/파기("제한구역")** - GitHub의 "Danger Zone"에 해당하는
  구역으로, Admin이 프로젝트를 다른 collaborator에게 **양도**하거나
  프로젝트 자체를 **파기**하는 기능이 여기 있다(위 "collaborator
  권한" 절 - Admin이 나가려면 이 둘 중 하나뿐).
- **템플릿(`CLAUDE.md`/`SKILL.md`) 배포 설정** - v2의 "다른 프로젝트에
  이 시스템을 도입" 기능을 v3도 유지한다. **전역 기본 템플릿이라는
  건 없다** - 대신 **architect별로 자기 템플릿을 갖는다**(그
  architect 개인 소유, 여러 프로젝트에 재사용 가능). 이 프로젝트에
  배포할 때는 그 프로젝트의 **`Admin`이 자신의 템플릿을 골라
  배포**하는 식이다 - **이 기능 자체가 그 프로젝트의 `Admin`만
  쓸 수 있다**(아래 "collaborator 권한" 절의 Admin 단일성 참고).
- **Webhook/외부 연동 설정** - v2의 push-hook류 기능도 유지한다 -
  이 프로젝트에 등록된 webhook 대상/시크릿 등을 여기서 관리한다.

### Phase 1 완료 기록 (2026-09-20)

`doc`/`plan`/`question`/`answer` 네 타입에 대해 `docs.add`/`get`/
`update`/`delete`/`transition`/`tag`/`list`를 실제로 구현하고
실기동으로 검증했다 - 새 파일: `backend/src/core/{trackingCode,
documentRules,channel,membership,refs,documents}.ts`.

**실제로 검증한 시나리오** (임시 postgres+backend 기동, CLI(클로드
채널)와 curl(architect 채널, `X-Cnw-Channel` 헤더 없음)을 오가며):
- `doc`(SP) 등록 → `question`(챕터 참조) 등록 → **같은 채널로 답변
  시도 시 거부**, architect 채널로 질의 `read` 전이 → **반대 채널
  로만 답변 등록 허용** 확인.
- 같은 질의에 **두 번째 답변 등록 시 카디널리티 제약으로 거부**.
- 답변 `read`→`done` 전이 시 **원 질의도 함께 `done`으로 연쇄 전이**
  (한 `docs.transition` 호출 안에서 atomic하게 처리).
- `docs.delete`가 answer가 아닌 타입엔 거부되고, 등록자 채널이
  다르면 거부되는 것 확인(자신이 등록한 답변만 철회 가능).
- `docs.update`/`docs.tag`의 **etag 불일치 시 conflict로 거부**,
  `docs.tag`가 참조 대상의 stale etag도 거부하는 것 확인.
- `doc`의 `review → active`는 **architect만** 가능하고 agent는
  거부됨을 확인, **`BT` kind는 예외로 agent가 스스로 승인** 가능함을
  확인.
- 프로젝트 멤버십 없는 프로젝트에 대한 액션은 거부됨을 확인.

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **역할(채널) 판별 방식**: "CLI/MCP=클로드, WEB UI=architect"만
  정해져 있고 서버가 실제로 어떻게 판별하는지는 없었다 → `shared/
  apiclient.ts`가 모든 `/api/actions` 요청에 `X-Cnw-Channel: agent`
  헤더를 싣고, 서버는 이 헤더가 없으면 architect로 간주한다(Phase 9
  WEB UI는 이 헤더를 보내지 않을 것이므로 자연히 구분된다). -
  `backend/src/core/channel.ts`.
- **액션이 어느 프로젝트 것인지 지정하는 방법**: `ApiKey`가 계정
  단위일 뿐 프로젝트에 묶여있지 않아서, **모든 `docs.*` 액션
  payload가 명시적으로 `projectId`를 받는다**(CLI/MCP는 `.cnw/
  config.json`의 값을 자동으로 채워 넣으므로 매번 타이핑할 필요는
  없음) - `backend/src/core/membership.ts`가 매 액션마다 그 계정이
  그 프로젝트에 최소 권한(Read/Write)을 가졌는지 검증한다.
- **답변 재등록 흐름**: "답변을 완전히 새로 쓰려면 `docs.delete`로
  철회 후 재등록"이 설계 문서의 서술이었는데, 실제로 그 카디널리티
  제약(질문당 답변 1개)이 `docs.delete`로 기존 답변이 사라져야만
  풀린다는 것까지 구현/검증했다.
- **MCP SDK 타입 버그 회피**: `@modelcontextprotocol/sdk@1.30` +
  `zod@3.25.76` 조합에서 `registerTool()`을 두 번 이상(심지어 한 번만
  써도) 호출하면 TS가 "Type instantiation is excessively deep" 오류를
  낸다(최소 재현으로 SDK 쪽 타입 정의 문제로 확인 - zod의 내부
  `ZodEffects`/`_refinement` 타입이 SDK가 기대하는 형태와 어긋남).
  런타임에는 전혀 문제가 없어서(tsx 실행 + 실제 MCP 프로토콜 핸드셰이크
  로 확인) `mcp/src/server.ts`에서 `registerTool` 호출 자체를 얇게
  타입 소거하는 우회를 적용했다 - SDK가 업데이트되면 제거를 시도해
  볼 것.
- **branch/commit_id는 아직 수동**: Phase 5(git/인프라 연동)에서
  다루기로 한 자동 인식 전까지는, `docs.add`가 그 필드들을 payload로
  받은 값을 그대로 저장할 뿐 자동으로 채우지 않는다.

**아직 스텁인 것**: 프론트엔드 실제 화면(Phase 9) - `docs.search`/
`docs.status`/`docs.grep`(Phase 3), `remember.*`/`message.*`
(Phase 4), `repo.push`(Phase 5)는 이후 라운드에서 실제로 구현됨
(아래 "Phase 3/4/5 완료 기록" 참고).

### Phase 2 완료 기록 (2026-09-20)

`tracker`/`test`/`opinion` 세 타입 + `dependsOn` readiness 정렬을
구현하고 실기동으로 검증했다 - `backend/src/core/documentRules.ts`에
kind/state/전이 규칙 추가, `backend/src/core/documents.ts`에
`docs.list`의 `sort: 'dependency'` 옵션 추가.

**실제로 검증한 시나리오**: `tracker`/`test` 등록 및 agent 전용
전이(architect 시도 시 거부) 확인, `opinion`은 architect만 등록
가능(agent 시도 시 거부)하고 상태 전이는 반대로 agent만 가능
(architect 시도 시 거부)함을 확인, `plan`끼리 `dependsOn`을 걸고
`docs.list`에서 미해결 의존성이 적은 순으로 정렬되는 것 확인,
**순환 의존성**(A→B, B→A)도 등록이 거부되지 않는 것 확인.

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **`tracker`의 kind가 설계 문서에 없었다** - 다른 타입들처럼 2글자
  코드가 필요해서 `TR`로 정했다(`doc`=SP/RP/RM/QA/BT, `plan`=PL,
  `question`=QU, `answer`=AN, `test`=TC, `opinion`=OP와 같은 관례).
- **`test`의 종결 상태 판단**: readiness 계산에서 "해소됐다"고 볼
  상태가 타입마다 다른데, `test`는 `added` 자체가 이미 완결된
  기록이라 `added`/`discard` 둘 다 종결 상태로 취급했다(그 외
  타입은 done류 상태만 종결로 침).
- **readiness 정렬은 애플리케이션 레이어에서 계산**: DB에 미해결
  의존성 개수를 저장해두지 않고 `docs.list` 호출 시점에 매번
  계산·정렬한다 - 문서가 많아지면 느려질 수 있는데, 최적화는 Phase 3
  "조회 고도화"(캐시/Meilisearch) 스코프로 미룬다.

### Phase 3 완료 기록 (2026-09-20)

`docs.search`(Meilisearch `q` / PostgreSQL POSIX 정규식 `grep`),
`docs.grep`, `docs.status`(집계), 백엔드 인메모리 캐시를 구현하고
실기동으로 검증했다 - 새 파일: `backend/src/core/{searchIndex, grep,
cache}.ts`.

**실제로 검증한 시나리오** (임시 postgres+Meilisearch+backend 기동):
- `docs.add`로 등록한 문서가 Meilisearch에도 인덱싱돼 `docs.search`
  의 `q`로 바로 찾아짐 확인.
- `docs.search`의 `grep`(PostgreSQL POSIX ERE, 여러 문서에 걸쳐)과
  `docs.grep`(문서 하나 안에서 매칭 줄+줄번호 발췌) 둘 다 정상 동작
  확인 - `q`/`grep` 동시 지정·둘 다 미지정 시 명확한 사유로 거부됨도
  확인.
- `docs.status`가 `kind`별/`state`별 집계 + `lastEtag`를 정확히
  반환하고, **캐시가 실제로 재사용**되다가 `docs.add` 직후
  **무효화되어 새 집계가 반영**되는 것까지 확인(`invalidateProject`).

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **Meilisearch 인덱싱을 지금은 동기 직접 호출로 구현**했다 - 설계
  원안은 "EMQX 브로드캐스트를 구독해서 비동기로"(Phase 5 스코프)
  였는데, 아직 EMQX 연동이 없어서 `documents.ts`가 CRUD 직후
  `searchIndex.ts`를 직접 호출한다. Meilisearch가 꺼져 있어도
  문서 CRUD 자체는 실패하지 않도록 try/catch로 감싸 경고만 남긴다 -
  Phase 5에서 EMQX 구독 방식으로 교체하며 이 직접 호출은 제거될
  예정이다.
- **`docs.status`는 Meilisearch facet이 아니라 PostgreSQL
  `groupBy`로 구현**했다 - "Meilisearch 활용 최적화 방안"의 제안
  이었지만, Phase 3 범위에서는 정확성과 구현 단순성을 우선했다.
  문서량이 커지면 facet 기반으로 교체를 검토할 것(현재는 캐시로
  반복 호출 비용만 줄여둠).
- **백엔드 캐시 무효화는 "문서 CRUD" 시점만 구현**했다(design-notes.md
  의 세 시점 중 하나) - 프로젝트 단위로 버전을 올려 그 프로젝트의
  캐시를 통째로 무효화하는 러프한 방식이다(개별 문서 의존성 추적
  아님). "git 커밋 시점" 무효화는 Phase 5(git 연동)에서 실제 커밋
  훅이 생긴 뒤에나 의미가 생긴다.
- **`docs.search`가 Meilisearch/grep 결과의 id만 받고, 실제 응답
  내용은 PostgreSQL에서 다시 채운다** - Meilisearch 인덱스는 검색
  전용이고 PostgreSQL이 여전히 정본이라는 원칙을 지켰다.

**실제로 검증한 시나리오** (임시 postgres+EMQX+backend 기동, 실제
MQTT 구독자까지 붙여서):
- `remember.add`/`list`가 (프로젝트, architect) 단위로 개인화됨을
  확인(다른 architect 것은 안 보임 - 별도 계정 테스트는 다음 라운드
  과제로 남김, 이번엔 소유권 필터링 로직만 확인).
- `message.send`의 `from` 검증(`notice`는 시스템 전용이라 직접 못
  보냄, `emerg`/`from-web`은 architect 채널만) 확인.
- **`notices` piggyback**: architect가 보낸 메시지가 agent의 다음
  아무 액션 호출 응답에 자동으로 실리고, 그 순간 `sent`→`read`로
  전이되어 이후 호출엔 다시 안 실리는 것까지 확인.
- **질의/답변/의견 등록 시 자동 `notice` 생성** 확인 - 정확히
  design-notes.md 예시 문구("[QU-xxxxxxxx]에 질의가 등록되었습니다")
  그대로 나옴.
- `message.transition`의 `done`(수신자만, `read` 상태에서만)/
  `canceled`(보낸 쪽만, `sent` 상태에서만) 권한 규칙 확인 - 수신자가
  취소 시도하면 거부됨도 확인.
- **`emerg` 메시지가 실제 EMQX로 즉시 발행**되는 것을 실제 MQTT
  구독자(`cnw/<projectId>/emerg` 토픽)로 수신 확인 - agent가 emerg를
  보내려 하면 거부되는 것도 확인.

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **`message.transition`의 `canceled` 권한**: design-notes.md는
  "보낸 쪽이 취소 가능"이라고만 했지 정확한 판별 규칙이 없었다 →
  `to` 필드로 역산했다 - `to`가 그 메시지의 수신자를 가리키므로,
  **그 반대 채널을 "보낸 쪽"으로 간주**한다(`to:'agent'`면 architect
  만 취소 가능, `to:'architect'`나 특정 architectId면 agent만 취소
  가능 - 특정 architectId 지정 메시지는 클로드/시스템이 보낸 것으로
  간주).
- **CLI에 `remember`/`message` 서브커맨드 그룹을 새로 추가**했다 -
  기존 `docs.*` 전용 서브커맨드 목록에는 없었던 액션 네임스페이스라,
  누락되어 있었다(발견 즉시 수정).
- **MCP 액션 분류 버그 수정**: 스캐폴딩 때 `remember.list`(조회
  성격)가 실수로 `docs_action`(변경) 쪽 목록에 들어가 있었다 -
  `docs_query`로 옮기고 `message.list`도 조회 쪽에, `message.send`/
  `message.transition`은 변경 쪽에 추가했다.
- **CLI가 `notices`를 버리고 있었다** - `apiclient.runOne()`이
  envelope의 `notices`를 버리고 개별 액션 결과만 반환하고 있어서,
  실제로 메시지가 잘 전달되는데도 CLI 사용자에게는 안 보이는
  버그였다. `docs`/`remember`/`message` 서브커맨드 전부 `notices`가
  있으면 같이 출력하도록 고쳤다.

Gitea/es-git 기반 내부 저장소 메커니즘 + `repo.push`, CLI의 로컬 git
branch/commit_id 자동 인식, EMQX 문서 CRUD 전체 브로드캐스트(Meilisearch

**실제로 검증한 시나리오** (임시 postgres+Meilisearch+EMQX+backend

- **EMQX 구독 기반 비동기 인덱싱/캐시 무효화**로 바뀐 뒤에도
  Meilisearch 검색과 `docs.status` 캐시 무효화가 여전히 정상 동작

- **`repo.push`**: es-git으로 내부 저장소에 파일을 커밋한 뒤, 실제

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **"내부 저장소" 스코프를 이번 라운드에선 축소했다** - 원래 설계는
  Gitea *서버*가 실제로 저장소를 프로비저닝하는 그림이었는데,
  프로젝트 생성 플로우(Phase 6+)가 아직 없어서 "어떤 프로젝트의

  라운드는 `./data/repos/<projectId>`에 es-git으로 로컬 저장소를
  유지하는 메커니즘 자체만 구현했다 - 실제 Gitea 서버 프로비저닝
  (조직/저장소 생성, admin API 연동)은 Phase 6에서 프로젝트 생성과
  함께 다시 다룬다.
- **es-git에는 remote URL을 바꾸는 API가 없다** - `findRemote`/
  `createRemote`만 있고 update가 없어서, `pushToMirror`는 이미
  "mirror"라는 이름의 remote가 있으면 URL이 그 사이 바뀌었어도 기존
  걸 그대로 쓴다. 프로젝트 설정에서 push-mirror 대상을 바꾸는
  시나리오는 remote를 지우고 다시 만드는 방법을 찾아 다음 라운드에서
  보강한다.
- **문서가 파일로 커밋되는 액션은 아직 없다** - "문서가 git
  branch/commit을 따라다닌다"는 각 문서에 그 시점의 branch/commit_id
  값을 *기록*해두는 것이지, 문서 자체가 내부 저장소에 파일로 커밋되는
  것과는 별개다(design-notes.md에도 그렇게 쓰여 있지 않았다) - 그래서
  이번 검증에서는 `commitFile()`을 직접 호출해 내부 저장소에 테스트
  커밋을 만든 뒤 `repo.push`만 실제 액션으로 확인했다. 문서 내용을
  실제 파일로 내부 저장소에 반영하는 기능이 필요한지는 다음 라운드
  판단 사항으로 남긴다.
- **`emqx.ts`를 Phase 4의 `emerg` 전용 클라이언트에서 문서 브로드
  캐스트까지 겸하는 공용 모듈로 합쳤다** - 별도 MQTT 연결을 두 개
  띄울 이유가 없어서, `publishEmerg`/`publishDocEvent`가 같은
  연결을 공유한다.

**아직 스텁인 것**: 프론트엔드 실제 화면(Phase 9) - `project.*` 액션은
Phase 6에서 실제로 구현됨(아래 "Phase 6 완료 기록" 참고). 실제 Gitea

**실제로 검증한 시나리오** (임시 postgres+backend 기동, 계정 3개
(admin/bob/carol)로 실제 멀티유저 시나리오):
- `project.create` - 만든 사람이 그 프로젝트의 유일한 Admin이 됨.
- **비멤버는 private 프로젝트에 READ조차 거부**됨을 확인.
- **초대 → 수락 전엔 여전히 접근 불가 → 수락 후 즉시 WRITE 권한
  발동**까지 순서대로 확인.

- **`project.invite`는 ADMIN 역할 부여 자체를 거부** - Admin은 오직
  `project.transfer`로만 넘어간다는 설계를 그대로 구현.
- **`project.transfer` 후 Admin 권한이 정확히 스왑**됨을 확인(기존
  Admin은 WRITE로 강등돼 이후 Admin 전용 액션이 거부되고, 새 Admin은
  바로 허용됨) - "Admin은 프로젝트당 1명" 불변식이 실제로 유지됨.
- **`visibility`를 `PUBLIC`으로 바꾸자 비멤버(carol)도 그 프로젝트와

  자동으로 이 예외가 적용됨을 확인.
- **`project.destroy`(제한구역)가 프로젝트/멤버십/초대/문서를 전부
  cascade 삭제**하는 것을 DB에서 직접 확인(0건으로 정리됨).

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **`onDelete: Cascade`를 프로젝트 스코프 관계 전체에 추가**했다
  (ProjectMembership/ProjectInvite/Document/RememberItem/Message) -
  "제한구역"에서의 파기가 단일 `prisma.project.delete()` 호출로
  깔끔하게 전체를 정리하도록.
- **`project.invite`의 대상 지정은 `username`으로 받는다** -
  architectId(계정 id)는 사용자에게 불친절한 값이라, 사람이 알고 있는

- **양도(`project.transfer`) 대상은 이미 그 프로젝트의 collaborator
  여야 한다** - 완전히 새로운 외부인에게 바로 Admin을 넘기는 경로는
  없다(먼저 초대→수락으로 collaborator가 된 뒤에만 양도 가능) -

  "제한구역" 절의 취지(모르는 사람에게 프로젝트를 통째로 못 넘기게)에

**실기동 중 발견한 심각한 버그와 수정**: `templateDeploy`가 같은
저장소에 파일 두 개를 연속으로 커밋하면 두 번째 `commitFile()`
호출에서 백엔드 Node 프로세스 전체가 처리되지 않은 네이티브 예외로
죽었다 - `es-git` 에러 `"current tip is not the first parent"`.
원인: `es-git`의 `Repository.commit(tree, message, options)`는
`options.parents`를 명시하지 않으면 매번 "부모 없음"(root commit)
으로 취급한다 - 첫 커밋은 문제없지만(아직 HEAD가 없으니 충돌 안 남),
두 번째 커밋부터는 `updateRef: "HEAD"`가 "새 커밋의 첫 parent가
현재 HEAD와 같아야 한다"는 불변식을 요구해서 실패한다. **수정**:
`gitRepo.ts`의 `commitFile()`에서 커밋 전에 `repo.head().target()`을
시도해 있으면 `parents`에 넣고(없으면 - 아직 커밋이 하나도 없는 새
저장소 - `parents`를 빈 배열로 둔다) `repo.commit(tree, message,
{ author, updateRef: "HEAD", parents })`로 명시적으로 넘긴다.

**실제로 검증한 시나리오** (임시 postgres+backend 기동, 격리된
EMQX_MQTT_URL로 호스트의 실제 EMQX와 접속 차단):
- `template.set` → `template.get`으로 저장된 `claudeMd`/`skillMd`
  확인.
- **Admin 계정으로 `template.deploy`** → 두 커밋(CLAUDE.md,
  SKILL.md)이 순서대로 내부 저장소에 생성되고 각각 유효한 commitId를
  반환 - 위 버그 수정 전에는 두 번째 커밋에서 프로세스가 죽었지만,
  수정 후엔 정상적으로 부모-자식 체인이 이어진 두 커밋이 만들어짐을
  `git log`로 직접 확인.
- **비Admin(신규 가입, 그 프로젝트에 멤버십 자체가 없는 계정)으로
  `template.deploy` 시도** → `{"ok":false,"reason":["ADMIN access to
  project \"demo-project\" required"]}`로 정확히 거부됨을 확인 -
  `requireMembership(projectId, architectId, "ADMIN")`이 기존
  프로젝트 액션들과 동일한 방식으로 재사용됨.

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **`es-git`의 `commit()`은 HEAD를 암묵적으로 parent로 채워주지
  않는다** - 이 라이브러리로 내부 저장소에 커밋을 쌓는 모든 코드는
  항상 명시적으로 현재 HEAD를 `parents`에 넣어야 한다는 걸 이번에
  실제 크래시로 확인했다. `gitRepo.ts`가 이 라이브러리를 감싸는
  유일한 지점이라 향후 새 커밋 로직도 전부 이 수정된 `commitFile()`을
  거치면 되고, 다른 곳에서 `repo.commit()`을 직접 호출하지 않는다.
- **템플릿 배포 커밋의 author는 `{name: ctx.channel, email:
  "<channel>@cnw.local"}`로 뒀다** - 실제 architect 계정 정보(이메일
  등)를 아직 커밋 작성자 메타데이터에 노출하지 않기로 판단(git 커밋은
  push-mirror를 통해 외부에 공개될 수 있는데, 계정 이메일을 자동으로
  실어 보내는 게 적절한 기본값이 아니라고 봄) - 실제 architect
  식별자를 커밋에 남기고 싶다면 다음 라운드에서 별도 옵션으로 설계.

**로컬 스테이징**(파일에 액션 쌓기 → `docs push`): 액션 서브커맨드
전부에 `--stage` 옵션을 추가했다 - 주면 네트워크로 바로 보내는 대신
`.cnw/staging.json`(git 추적 안 함, `session.json`과 같은 취급)에
`{action, projectId, ...payload}`를 쌓기만 한다. 새 최상위 명령
`docs push`가 쌓인 배열 전체를 `client.run()` 한 번(진짜 bulk 호출)
으로 전송하고 전송 시도 후엔 성공/실패와 무관하게 스테이징을
비운다(부분 실패는 서버가 이미 받았다는 뜻이라 각 항목의
`ok:false`를 사용자가 보고 판단). `docs stage list`/`docs stage
clear`로 보관/폐기 관리. `shared/src/config.ts`에
`readStaging`/`appendStaging`/`clearStaging` 추가.

**로컬 캐시**(list=요약/get=본문 분리): `docs.list`(정렬 방식 두
분기 모두)는 이제 `content` 필드를 뺀 요약만 반환한다 -
`backend/src/core/refs.ts`의 새 `toDocSummary()`(`toDocResponse()`의
결과에서 `content`만 제외). `docs.get`은 기존처럼 본문 전체를
반환하고, CLI는 그 응답을 받을 때마다 `.cnw/cache.json`(git 추적
안 함)에 트래킹 코드별로 저장해둔다. 새 명령 `docs cat <code>`는
그 로컬 캐시만 읽고 네트워크를 전혀 타지 않는다(백엔드를 실제로
내려놓고도 캐시된 문서를 그대로 출력하는 것으로 확인, 캐시에 없는
코드는 "먼저 docs get으로 조회하라"는 안내와 함께 exit 1로 명확히
실패). `docs.search`는 설계상 검색 스니펫 성격이 강해 본문 포함을
그대로 유지했다(아래 판단 참고) - 대신 CLI에 `--codes-only`(코드/
제목/타입/kind/state만)와 `--lines <n>`(본문을 앞 n줄까지만)을
추가해 클라이언트 쪽에서 다듬을 수 있게 했다.

**실제로 검증한 시나리오** (임시 postgres+backend 격리 기동, EMQX/
Meilisearch는 접속 불가 포트로 지정해 호스트의 실제 서비스와 완전
차단):
- `docs add ... --stage` 두 번 → `docs stage list`에 둘 다 그대로
  쌓여있고, 그 사이 `docs list`는 여전히 `total: 0`임을 확인(네트워크
  요청이 실제로 안 나갔다는 증거).
- `docs push` → 두 액션이 한 번의 bulk 호출로 전송되고 각각 실제
  `code`/`etag`를 받으며 생성됨을 확인, 이후 `docs stage list`는
  빈 배열.
- 잘못된 `kind`("DN")로 먼저 스테이징 → 푸시했을 때 **서버가 실제로
  거부**(`"DN"는 doc의 유효한 kind가 아닙니다`)하면서도 스테이징은
  정상적으로 비워짐을 확인(전송 자체는 성공, 개별 항목 거부는
  별개라는 설계대로).
- `docs list` 응답에 `content` 필드가 전혀 없음을 확인, `docs get`
  응답엔 `content`가 온전히 있음을 확인.
- `docs get`으로 문서 하나를 조회한 뒤 `.cnw/cache.json`에 그
  전체 응답이 기록됨을 파일로 직접 확인.
- **백엔드 프로세스를 완전히 죽인 뒤** `docs cat <그 code>` →
  네트워크 없이 캐시에서 그대로 본문을 출력함을 확인. 캐시에 없는
  코드로 `docs cat` 시도 → 명확한 안내 메시지 + exit code 1 확인.
- 4줄짜리 본문 문서를 만들어 `docs search --grep ... --lines 2` →
  실제로 앞 2줄까지만 잘려서 나옴을 확인(1줄짜리 문서로 먼저
  시도했을 땐 자를 게 없어 차이가 안 보였어서, 잘림 자체를 증명하려고
  일부러 여러 줄 문서로 재시도).
- `docs search --grep ... --codes-only` → `code`/`title`/`type`/
  `kind`/`state`만 남고 나머지(특히 `content`)가 전부 빠짐을 확인.

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **`docs.search`는 요약화 대상에서 제외**했다 - 로드맵 원문은
  "list=요약/get=본문 분리"라고 `list`만 명시했고, `docs.search`는
  검색 결과 자체가 본문 매칭 여부를 사람이 바로 확인해야 하는
  스니펫 성격이 강하다(게다가 CLAUDE.md의 미래 규칙 6이 이미 "`docs
  search`는 기본적으로 본문 전체를 돌려준다"는 걸 전제로 `--codes-
  only`/`--lines` 완화책을 규칙으로 못박아 두고 있다 - 이 저장소가
  나중에 자기 자신을 그렇게 운영하게 된다는 강한 선례로 보고 그대로
  따랐다). 그래서 백엔드 응답 자체는 그대로 두고, CLI 쪽에서만
  `--codes-only`/`--lines`로 다듬게 했다 - MCP는 이번 라운드에 이
  옵션을 추가하지 않았다(MCP 호출자는 어차피 응답 전체를 JSON으로
  받아 스스로 판단할 수 있고, "요청 횟수/응답 내용 최소화"는 결국
  호출자 쪽 재량이라 서버 응답 형태를 바꾸는 것과는 다른 문제로
  판단) - 필요해지면 다음 라운드에 MCP 쪽에도 같은 옵션을 추가할 수
  있다.
- **스테이징 실패 시 재시도 방법은 "다시 stage해서 다시 push"뿐**
  이다 - `docs push`가 전송 시도 후 무조건 스테이징을 비우므로,
  일부 항목만 실패했을 때 그 실패한 항목만 골라 재전송하는 기능은
  없다(설계에 없던 지점이라 가장 단순한 동작으로 결정) - 필요해지면
  다음 라운드에 "실패한 항목만 다시 스테이징"류의 보조 명령을 추가할
  수 있다.
- **캐시는 신선도를 보장하지 않는다** - `docs cat`은 마지막으로
  `docs get`한 시점의 스냅샷을 그대로 보여줄 뿐, 그 사이 다른
  협업자가 문서를 바꿨어도 알려주지 않는다(정본은 항상 서버,
  `fetchedAt` 타임스탬프만 남겨 오래된 캐시임을 사람이 판단할 수
  있게 했다) - 실제 편집(`docs update`)은 여전히 서버에서 받은
  최신 `etag`가 필요하므로 이 캐시로 인한 동시성 버그 위험은 없다.
- **`.cnw/staging.json`/`.cnw/cache.json`도 `.cnw/session.json`과
  같은 이유로 git 추적 대상에서 제외**했다(`.gitignore`에 추가) -
  개인 작업 상태이지 프로젝트 설정이 아니다.

**실제 검증 중 발견해서 그 자리에서 고친 프론트엔드 버그 두 가지**
(둘 다 백엔드는 정상이었고, 프론트엔드가 실제 계약을 잘못 가정한
경우 - curl로 백엔드를 직접 찔러 "프론트가 틀렸다"를 먼저
확정한 뒤 고쳤다):
1. `docs.transition`의 실제 payload는 `{projectId, state: {
   "코드": [다음상태, 예상되는현재상태] }}`(여러 문서를 한 번에
   묶어 전이시킬 수 있는 bulk 형태, 동시성 체크도 etag가 아니라
   "지금 이 상태일 것"이라는 현재 상태 문자열로 한다)인데, 처음
   구현한 `DocTypeWorkspace.vue`/`QaTab.vue`는 `{code, etag,
   nextState}`라는 존재하지 않는 형태로 보내고 있었다 - 브라우저에서
   "리뷰 요청"을 눌렀더니 실제로 `state는 { "XX-xxxxxxxx": [새 상태,
   기존 상태] } 형태여야 합니다` 에러가 그대로 화면에 떴고, 이걸 보고
   `documents.ts`의 실제 구현을 다시 읽어 고쳤다.
2. `QaTab.vue`의 `openQuestion()`이 "이미 연 적 있는 질문이면
   아무것도 다시 안 한다"는 캐시 가드를 질문 본문과 답변 존재 여부
   양쪽에 걸쳐 걸어놔서, 답변을 새로 등록한 직후 같은 함수를 다시
   불러도(질문이 이미 펼쳐진 상태라) 방금 생긴 답변을 못 찾는
   버그가 있었다(페이지를 새로고침하면 정상적으로 보였다 - 캐시가
   비어있는 최초 호출에서만 답변 조회 로직이 실행됐기 때문). 질문
   "본문"은 캐시하되 답변 "존재 여부" 확인은 매번 다시 하도록 분리해
   고쳤다.

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):

  나란히 두는 별개 탭으로 추가하는 게 맞다(Source View 자체를

  design-notes.md`의 "프로젝트 설정 항목" 절에서 처음 언급된 이후

### Phase 9 후속 라운드 2 (2026-09-20) - 웹훅(외부 연동) 기능 구현

설계자가 명시적으로 요청해 앞서 미룬 "웹훅 설정" 항목을 이번
라운드에 실제로 구현했다. 착수 전 `v2` 브랜치(참고 자료)의
`pushHooks.ts`/`webhookRoutes.ts`를 열람했는데, v2는 이 시스템이
**Gitea 시스템 웹훅을 수신**해 push/delete 이벤트를 파싱하고
`PushHookPrompt` 매칭 규칙으로 AI 처리를 트리거하는 훨씬 큰 구조였다
(자체 Gitea 운영을 전제). v3는 아직 Gitea를 운영하지 않고(내부
저장소는 es-git 로컬 유지 + 옵션 push-mirror뿐 - Phase 5 판단
그대로) design-notes.md의 "프로젝트 설정 항목" 절도 원래
"이 프로젝트에 등록된 webhook **대상**/시크릿"이라고 표현해 방향이
반대(수신이 아니라 발신)임을 시사하고 있었다 - 그래서 **v2의
수신형 구조를 그대로 옮기지 않고, 이미 있는 문서 CRUD 브로드캐스트
인프라(EMQX `cnw/<projectId>/docs`)에 얹어 발신형으로 재구성**했다.
서명 방식(HMAC-SHA256, 다이제스트를 hex로 헤더에)은 v2가 Gitea/
GitHub 웹훅 **검증**에 쓰던 것과 같은 관례를 그대로 채용했다 -
방향은 반대여도 "본문을 그대로 HMAC해서 헤더로 보낸다"는 업계
표준 검증 모델 자체는 동일하게 유지하는 게 맞다고 판단했다.

**구현 내용**: 새 Prisma 모델 `Webhook`(projectId, url, secret,
createdAt - `onDelete: Cascade`)과 마이그레이션
`20260920125436_phase9_webhooks`. `webhook.add`/`list`/`delete`
세 액션(전부 그 프로젝트 **Admin만**, 기존 `requireAdmin` 패턴
재사용) - `backend/src/core/webhooks.ts`. `webhook.add`가 서버에서
`crypto.randomBytes(24)`로 secret을 생성해 **그 응답에만** 실어
보내고, `webhook.list`는 절대 secret을 다시 내려주지 않는다(재발급
하려면 삭제 후 재등록). 실제 발송은 새 함수 `deliverWebhooks()`를
`backend/src/core/broadcastSubscriber.ts`의 기존 `cnw/+/docs`
구독 콜백 안에서 그대로 호출하는 방식으로 연결했다(새 구독을 따로
만들지 않고, 이미 흐르는 이벤트를 재사용) - 그 프로젝트에 등록된
웹훅마다 `fetch()`로 POST하고 `X-Cnw-Signature: sha256=<hex>`
헤더에 서명을 싣는다. CLI(`webhook add/list/delete`)/MCP(`webhook.
list`는 조회, `webhook.add`/`delete`는 변경)에도 반영했다. 프론트
엔드 Settings 탭에 Webhooks 섹션(Admin만 노출) - 목록/추가/삭제,
추가 직후 secret을 노란 배너로 한 번만 보여준다.

**실제로 검증한 시나리오** (임시 postgres+backend 격리 기동, 이번엔
EMQX를 접속 불가 포트로 막지 않고 **실제로 격리된 테스트 EMQX
컨테이너**(호스트 포트 11883/18084, 기존 관례대로 호스트의 실제
EMQX와 겹치지 않는 포트)를 띄워 브로드캐스트 배관 전체를 실동작으로
확인했다 - 로컬 Node HTTP 서버(포트 19191)를 수신용으로 별도 기동):
- `webhook.add`로 등록 → 응답에 담긴 secret을 저장.
- `docs.add`로 문서 하나 생성 → **로컬 수신 서버가 실제로 POST를
  받고**, 받은 `X-Cnw-Signature` 헤더값을 저장해둔 secret으로 직접
  재계산(Python `hmac`)해 **완전히 일치**함을 확인 - 서명 검증
  로직이 이론이 아니라 실제로 맞물려 동작함을 증명.
- `webhook.list` 응답에 `secret` 필드가 전혀 없음을 확인.
- 비Admin 계정으로 `webhook.list` 호출 → `ADMIN access to project
  "demo-project" required`로 거부됨을 확인.
- `webhook.delete` 호출 후 문서를 새로 만들어도 **더 이상 수신
  서버에 아무것도 안 옴**을 확인(삭제가 실제로 발송을 멈춤).
- 프론트엔드 Settings 탭에서 실제로 웹훅 추가(secret 배너 노출
  확인) → 문서 생성 → 수신 서버가 받는 것까지 브라우저 조작으로
  재확인 → 삭제 버튼 클릭 → 목록이 "등록된 웹훅이 없습니다"로
  바뀌는 것 확인.

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **발송 실패는 재시도하지 않는다** - `deliverWebhooks()`는
  실패를 경고 로그로 삼키기만 한다(5초 타임아웃). 문서 CRUD라는
  핵심 기능이 외부 URL의 장애 때문에 막히면 안 된다는 우선순위
  판단 - 재시도 큐/실패 알림이 필요해지면 그건 완전히 별도 라운드
  (지수 백오프, dead-letter, 재시도 상태 조회 API 등 설계 자체가
  새로 필요함)로 남긴다.
- **이벤트 종류는 문서 CRUD(`DocEvent`) 하나뿐**이다 - `emerg`
  메시지나 `repo.push`(실제 git push-mirror) 등 다른 이벤트 종류로
  웹훅을 확장하는 건 이번 스코프에 넣지 않았다(design-notes.md가
  "웹훅 대상/시크릿 관리"라고만 했지 이벤트 종류를 특정하지
  않았음 - 이미 존재하는 브로드캐스트 하나에만 얹어 최소로
  구현했다). 여러 이벤트 종류를 지원하게 되면 그때
  `webhook.add`에 `events` 필터 필드를 추가하는 식으로 확장 가능.
- **secret은 평문으로 DB에 저장한다**(해시하지 않음) - 로그인
  비밀번호와 달리 이 secret은 매 발송마다 그 원문으로 HMAC을
  계산해야 하는 용도라 단방향 해시로는 애초에 쓸 수 없다(webhook
  secret은 일반적으로 다 이렇게 다룬다) - 대신 `webhook.list`
  응답에서 절대 다시 노출하지 않는 것으로 노출 표면을 최소화했다.
- **URL 형식만 검증하고 실제 도달 가능성은 검증하지 않는다** -
  `webhook.add`는 `http(s)://`로 파싱 가능한지만 확인한다(SSRF 류
  악용 방지를 위한 내부 IP 차단 등은 이번 스코프 밖 - 이 시스템은
  아직 신뢰된 단일 architect/agent 환경을 전제하므로 이번엔 넣지
  않았지만, 외부에 공개되는 배포 형태가 생기면 재검토가 필요하다는
  점을 계획으로 남겨둔다).

  `targetId`+`etag` + `@@index([targetId])`)로 분리했다 -
  `backend/prisma/schema.prisma`, 마이그레이션
  `20260920140000_refs_relational`(비대화형 셸에서는 `prisma
  migrate dev`가 데이터 손실 확인 프롬프트 때문에 항상 실패해서,

  옮기는 데이터 마이그레이션 스크립트는 만들지 않고 그냥 버렸다).
  `backend/src/core/refs.ts`에 `replaceRelated`/`replaceDependsOn`
  (전체 교체 - 기존 로우 삭제 후 새로 insert, docsAdd/docsUpdate/
  docsTag가 항상 배열 전체를 받는 시맨틱 그대로) +
  `loadRelated`/`loadDependsOn`(+배치 버전)을 추가하고,
  `documents.ts`의 모든 CRUD/목록/검색 경로가 이걸 쓰도록 고쳤다.
  **부수 효과로 두 가지가 자연히 좋아졌다**: (1) `sort: 'dependency'`
  의 미해소 개수 계산이 이제 배치 쿼리 한 번(이전엔 "다음 라운드
  최적화 스코프"로 미뤄뒀던 N+1), (2) 문서를 삭제하면 그 문서를
  가리키던 related/dependsOn 로우도 FK `onDelete: Cascade`로 자동
  정리된다(이전 Json 배열 방식은 대상이 지워져도 죽은 참조가 영원히
  남았음). 프론트엔드에는 `DocTypeWorkspace.vue`에 related/dependsOn
  태그 배지(클릭하면 타입이 달라도 그 문서로 바로 이동) + "태그
  추가" 다이얼로그(대상의 최신 etag를 `docs.get`으로 확인 후 기존
  배열에 이어붙여 `docs.tag`) + "의존성 순 정렬" 토글을 추가했다.

**실제로 검증한 시나리오**: 새 문서 생성 → `docs.tag`로
related+dependsOn 태깅(curl) → `docs.get` 응답에 정확히 반영 확인
→ `sort: dependency`로 미해소 의존이 있는 문서가 없는 문서보다
뒤로 가는 것 확인 → 웹 UI에서 그 태그 배지 클릭 시 실제로 다른
문서로 이동 확인 → 웹 UI의 "태그 추가" 다이얼로그로 새 related
태그를 실제로 추가하고 반영까지 확인. Messages: 웹 UI에서
"긴급" 아닌 일반 메시지를 agent에게 전송 → agent 채널로 조회 시
`from-web → agent` 메시지가 정확히 도착한 것을 curl로 별도 확인.
Q&A 통합: 특정 문서에 질문/의견을 달면 그 문서 화면에서만 보이고
다른 문서 화면에는 안 보이는 것을 `parent_id` 값까지 직접 대조해

**Code/Pull requests 탭 - es-git 기반**: `backend/src/core/

`.next()` 드레인 헬퍼를 만들어 우회했다(제네릭 타입 인자를 호출부
마다 명시해야 함 - `unknown` 인자로는 추론이 안 됨).
`backend/src/core/repoBrowse.ts`(신규)가 이 함수들을 액션
(`repo.branches`/`repo.tree`/`repo.file`/`repo.commits`/
`repo.writeFile`)으로 노출한다.

PR은 `backend/src/core/pullRequests.ts`(신규)로 완전히 새로운
Prisma 모델(`PullRequest` - state open/merged/closed)이며 **의도적
으로 Document 타입 체계 밖에 둔다** - git 머지 시맨틱(브랜치 diff,
머지 커밋)이 문서 상태 전이 모델과 안 맞는다는 판단. 액션
`pr.create`(브랜치 존재를 `listBranches`로 검증)/`pr.list`/
`pr.get`(diff는 매번 `diffBranches`로 **실시간 계산** - merged/
closed PR도 항상 최신 두 브랜치 diff를 보여줄 뿐 머지 시점에
"고정"되지 않는다는 한계를 알고 있는 상태로 남겨둠)/`pr.merge`/
`pr.close`.

**`mergeBranches()` 버그 두 개 발견/수정** (실제 머지를 반복
실행하며 찾음):
1. `repo.mergeCommits()`가 반환하는 `Index`는 그 저장소에 바인딩
   되지 않은 인메모리 객체라 `.writeTree()`가 `"the index file is
   not backed up by an existing repository"`로 죽었다 -
   `repo.setHead()` + `repo.checkoutHead({force:true})` +
   `repo.merge([annotated])` + (인메모리 Index 대신) `repo.index()`
   (실제 디스크에 바인딩된 인덱스)를 쓰는 방식으로 교체.
2. **더 심각한 것**: 저장소에 지저분한/staged 상태가 남아있으면
   `repo.merge()`가 `"1 conflict prevents checkout"`을 던지는데,
   `backend/src/api/actions.ts`의 액션 디스패치 어디에도 예외
   처리가 없어서 **이 하나의 예외가 백엔드 프로세스 전체를
   크래시**시켜 모든 사용자의 연결이 끊겼다. 두 겹으로 고쳤다:
   (a) `mergeBranches()` 자체가 항상 강제 체크아웃부터 하고, 실패
   시 `repo.cleanupState()` + 강제 체크아웃으로 정리한 뒤
   `{ok:false, reason}`을 반환(throw 대신), (b) **`actions.ts`의
   `dispatch()`에 모든 액션 핸들러를 감싸는 전역 try/catch를
   추가** - 이건 이번에 새로 생긴 버그가 아니라 Phase 0 스캐폴딩
   때부터 있던 구조적 결함이었다(어떤 액션이든 핸들러 내부에서
   uncaught exception이 나면 서버 전체가 죽는 상태였음). 재현
   시나리오를 그대로 다시 돌려 서버가 죽지 않고 깨끗한 에러
   응답을 반환한 뒤 `/api/health`가 계속 살아있는 것, 그리고
   재시도로 머지가 실제로 성공하는 것까지 확인했다.

**Source View 정의 확정 + yiitap 도입**: 설계자가 "Source View"를
보기 모드(마크다운→HTML 렌더링만)/편집 모드(마크다운 편집) 둘로

components/MarkdownSourceView.vue`(신규)로 구현:

  (클립보드 붙여넣기/복사에만 markdown 지원) `marked`(md→html,

  경계에서 직접 변환한다 - 정본은 항상 마크다운 텍스트(백엔드
  content 필드)이고 yiitap의 HTML은 그 화면 표현일 뿐.

- `DocTypeWorkspace.vue`의 Source View(예전엔 `<pre>`로 원문 그대로
  표시)와 Code 탭의 README 뷰어가 전부 이 컴포넌트로 교체됐다.

**Code 탭 README 자동 표시/작성**: 선택된 파일이 없고 현재 브랜치

**실제로 검증한 시나리오**: Code 탭에서 브랜치 전환/파일 트리 탐색/
커밋 목록/README 자동 표시 확인 → README 없는 브랜치에서 "작성하기"
→ 편집 → 저장 → 실제 커밋 생성 확인. PR: 새 페이지에서 제목/
source·target 브랜치/설명(yiitap)을 채워 생성 → 목록에 반영 →
상세에서 diff 확인 → Merge 클릭 → 실제 머지 커밋 생성 확인(es-git
`listCommits`로 병합 커밋이 그래프에 나타나는 것까지). 크래시
안전성: 지저분한 상태에서 강제로 머지 충돌을 재현해 서버가 죽지
않고 에러 응답만 반환하는 것, 이어서 `/api/health`가 계속 응답하는
것, 재시도 시 정상적으로 머지되는 것을 순서대로 확인. 문서/플랜/
이슈: 새 페이지에서 제목+yiitap 본문을 채워 생성 → 목록/상세 화면에
본문이 정확히 반영되는 것 확인. Discussion: 질문하기 다이얼로그의
새 입력창(yiitap)으로 질문 등록 → 스레드에 정확히 반영 확인.
검증에 쓴 테스트 PR 2건/테스트 문서 1건/테스트 질문 1건은 실제
데모 데이터를 어지럽히지 않도록 각각 close/discard 처리했다.

**이번 라운드에서 판단해 기록해두는 것** (설계에 없던 지점):
- **PR은 Document 타입이 아니다** - 위에서 설명한 대로 git 머지
  시맨틱과 문서 상태 전이 모델이 근본적으로 다르다는 판단(별도
  Prisma 모델 + 별도 액션 네임스페이스 `pr.*`).
- **`pr.get`의 diff는 항상 실시간 계산**이라 머지/닫힘 이후엔 두
  브랜치가 서로 갈라져 있으면(예: source 브랜치가 삭제되거나 더
  진행된 경우) 실제 머지 당시의 diff와 달라 보일 수 있다는 한계를
  안고 있다 - "머지 시점 diff를 스냅샷으로 저장"하는 건 다음
  라운드 후보로 남긴다.
- **Discussion(질문하기/답변/의견)은 페이지가 아니라 다이얼로그+
  리치 에디터로 절충**했다 - 근거는 위 "다이얼로그 → 별도 페이지
  전환" 절 참고. 만약 나중에 질문/답변 자체가 훨씬 길어지는
  용례가 생기면 그때 페이지 분리를 재검토한다.
- **`actions.ts`의 전역 try/catch는 모든 액션에 걸리므로, 앞으로
  새 액션을 추가할 때 핸들러 내부에서 별도로 try/catch를 하지
  않아도 프로세스가 죽지는 않는다** - 다만 각 핸들러가 의미 있는
  에러 메시지를 반환하는 것 자체는 여전히 핸들러 책임.

**yiitap 실제 기능 결함 발견 및 수정 (이번 라운드의 핵심)**:
Code 탭의 파일 뷰어/에디터도 yiitap 기반으로 바꾸면서(비-markdown
파일은 마크다운 펜스 코드 블록 ` ```lang ... ``` `으로 감싸 넣고
저장 시 다시 벗기는 방식 - `frontend/src/pages/project/CodeTab.vue`
의 `wrapAsCodeFence`/`unwrapCodeFence`) 실기동 검증을 하다가,
**`MarkdownSourceView.vue`가 지금까지 `YiiEditor`의 `extensions`
prop을 한 번도 넘긴 적이 없었다는 게 실제 버그로 드러났다**:
- `YiiEditor`의 `extensions` prop 문서 주석은 "기본으로 BuiltinExtensions
  를 켠다"고 돼 있지만, `node_modules/@yiitap/vue/dist/index.mjs`를
  직접 뜯어보면 그 prop의 **실제 기본값은 빈 배열**이고, 내부
  베이스 에디터(Tiptap StarterKit 격)도 `codeBlock: false,
  document: false, horizontalRule: false, link: false, blockquote:
  false`로 명시적으로 꺼둔 채 만들어진다 - 즉 `extensions` prop을
  안 넘기면 문서 주석과 달리 codeBlock/blockquote/horizontalRule/
  link 툴바 버튼이 **눌러도 아무 일도 안 일어난다**(버튼은 렌더링
  되지만 그 노드/마크 자체가 에디터 스키마에 없음 - 예를 들어 코드
  블록 버튼을 눌러도 그냥 일반 문단이 되고, 여러 줄 텍스트를
  붙여넣으면 `<p><code>줄1<br>줄2<br>...</code></p>`처럼 인라인
  code+수동 줄바꿈으로 뭉개진다).
  - **발견 경위**: 코드 탭에서 펜스 코드 블록으로 감싼 TypeScript
    파일을 열어보니 들여쓰기가 안 보존되는 이상한 렌더링이 나왔고,
    DOM을 직접 까보니 실제 `<pre><code>` 노드가 아니라 `<p><code>`
    (인라인 code 마크 + `<br>`)였다 - 이걸 보고서야 `codeBlock`
    자체가 스키마에 없다는 걸 알았다.
  - **수정**: `@yiitap/vue`가 공개 export하는 `OStarterKit`
    (`OStarterKit.configure(options)` - `node_modules/@yiitap/vue/
    dist/index.mjs`의 `export` 목록에서 직접 확인, `@yiitap/
    vue-preset`은 이름과 달리 실제로는 `export default {}`뿐인
    빈 메타 패키지라 쓸모없었음)을 `MarkdownSourceView.vue`에서
    호출해 `extensions` prop으로 넘긴다. 동시에 이 `configure()`
    옵션으로 마크다운과 안 맞는 기능(BackgroundColor/Color/
    FontFamily/Highlight/TextAlign/TextStyle/Typography/OCallout/
    OTable/Subscript/Superscript/Focus)은 **확장 자체를 꺼서
    제외**한다(설계자 요청 "마크다운과 호환되지 않는 기능은 제외해도
    돼"를 main-menu에서 버튼만 숨기는 것보다 확실하게 만족 - 슬래시
    커맨드 등 다른 경로로도 그 기능이 못 들어오게 됨). 나머지
    (OBlockquote/OCodeBlock/OHorizontalRule/OLink/TaskItem/TaskList/
    OSlash/OSlashZh/OSelectionDecoration/UniqueID)는 yiitap의
    `DefaultExtensionNames` 그대로 유지.
  - 수정 후 코드 탭에서 실제 `.ts` 스크래치 파일을 열어 문법
    하이라이팅이 되는 진짜 코드 블록(언어 셀렉터+다운로드+복사
    버튼까지 딸린)으로 렌더되는 것, 편집 후 저장한 내용이 펜스

    Issues/Trackers Source View, PR 설명, Template, Discussion
    작성창)에 동시에 적용된다.
  - **알아둘 잔여 한계**: marked→turndown 코드 블록 왕복에서 파일
    끝 줄바꿈이 하나 없어지는 경우가 있어(별도로 Node 스크립트로

    `\n`으로 끝났으면 저장 직전에 되돌려준다 - 안 그러면 저장할

  감싸는 방식**을 택했다 - yiitap이 근본적으로 마크다운/리치텍스트
  에디터라 원문을 그대로 넣으면 공백/들여쓰기가 문단으로 뭉개지는데,
  펜스 코드 블록(`<pre><code>`)은 공백을 보존하는 유일한 마크다운

  줄바꿈 하나를 빼면 완전한 왕복(원본=편집 후 저장본)이 되는 것을
  Node 스크립트로 직접 검증했다.
- **`OStarterKit` 발견은 순전히 컴파일된 번들을 직접 읽어서** 한
  것이다 - `@yiitap/vue`의 공개 타입 선언(`.d.ts`)과 README성
  문서 주석은 "extensions 기본값이 BuiltinExtensions"라고 하지만
  실제 코드와 다르므로, **이 패키지의 동작을 확인할 땐 타입
  선언이나 문서 주석을 곧이곧대로 믿지 말고 `node_modules/@yiitap/
  vue/dist/index.mjs`를 직접 grep해서 확인해야 한다**(이번에
  `showMainMenu`/`showBubbleMenu` 등 다른 prop들의 실제 기본값도
  전부 이 방식으로 재확인했음) - 다음에 이 라이브러리를 또 건드릴
  일이 있으면 이 방법부터 쓴다.
- **PR 설명 편집(수정) 기능은 아직 없다** - `pr.update` 액션이
  없어서 생성 시점에만 입력 가능하고 이후엔 읽기 전용이다. 필요해
  지면 다음 라운드 후보.

### WEB REST API 전환 + PR/커밋 diff 뷰어 + Q&A 계층/에디터 정비 라운드 (2026-09-21)

설계자가 이번엔 12가지를 한 번에 요청했다: (1) WEB UI를 `/api/actions`
단일 엔드포인트에서 액션별 REST 엔드포인트로 전환, (2) RECENT Q&A
탭 이름 변경 + 클릭 시 그 문서로 이동・스크롤, (3) Q&A 계층 구조를
"more" 아이콘 + 별도 페이지로 드러내기, (4) 질문하기 등을 다이얼로그
대신 인라인 확장 에디터로, (5) yiitap 좌측 사이드 메뉴/여백/최소
높이/배경, (6) PR diff 뷰어 전면 개편(파일 트리+분할 diff+컨텍스트
접기+이미지/바이너리 처리+툴바), (7) Contributors를 팝업으로, (8)
코드 탭 우측 뷰어 탭 분리, (9) 좌측 "최근 커밋" 제거+눈알 아이콘,
(10) 커밋 diff 페이지, (11) README 없음 안내 중앙 정렬, (12) 툴바 밑
내용이 옆으로 새는 버그.

**(1) REST API 전환 - 가장 큰 구조 변경**: "/api/actions 단일
엔드포인트 + command 패턴"은 애초에 CLI/MCP(`shared/apiclient.ts`,
항상 `X-Cnw-Channel: agent`)를 위한 설계였지 WEB UI까지 그리로
몰아넣으라는 뜻이 아니었다는 설계자 지적 - `backend/src/api/rest.ts`
(신규)에 프로젝트/문서/repo/PR/메시지/웹훅/템플릿/remember 전
영역에 걸쳐 REST 라우트(GET/POST/PATCH/PUT/DELETE, 자원 기반 경로)
를 만들었다. **core/*.ts의 액션 핸들러(`(payload, ctx) => ActionResult`
모양)는 전혀 안 건드리고 그대로 재사용**했다 - `rest.ts`의 `web()`
헬퍼가 `req.params`/`req.query`/`req.body`를 그 핸들러가 기대하는
payload 모양으로 조립해서 그대로 호출하고, 결과를 REST 응답(성공은
`data`를 그대로 200/201, 실패는 `{error: reason[]}`을 422)으로
매핑한다 - **비즈니스 로직/검증/권한 로직이 완전히 하나(같은 함수)
라 CLI/MCP와 WEB UI가 서로 다른 규칙을 갖게 될 위험이 없다**.
notices piggyback도 그대로 유지하되(REST 자원 응답 모양을 안
어지럽히려고) `X-Cnw-Signature`처럼 `X-Cnw-Notices`(JSON을 base64로
인코딩한) 응답 헤더로 옮겼다 - `frontend/src/api/client.ts`가 그
헤더를 읽어 Quasar `Notify` 토스트로 띄운다(기존과 동일한 사용자
경험, 표준 응답 모양만 REST에 맞게 바뀜). `/api/actions`는
`server.ts`에 **그대로 남아있고** CLI/MCP는 전혀 안 건드렸다 - 실제로
`X-Cnw-Channel: agent` 헤더로 그 엔드포인트를 다시 호출해 여전히
정상 동작하는 것까지 확인했다.
- `frontend/src/api/client.ts`를 완전히 새로 썼다 - `runActions`/
  `runAction`을 없애고 자원별 함수(`listDocuments`/`createDocument`/
  `getFileDiff`/`mergePullRequest` 등 40여 개)로 대체했다. 각 함수는
  기존 `ActionResult`(`{ok, data}`/`{ok:false, reason}`)와 똑같은
  모양을 돌려주도록 만들어서, 컴포넌트 쪽의 `if (!result.ok) { ...
  result.reason ... }` 코드는 호출부 하나만 바꾸면 되게 했다 -
  덕분에 `stores/auth.ts`의 `run`/`runBulk`를 지우고 14개 파일,
  53곳의 호출부를 전부 옮겼는데도 각 컴포넌트의 나머지 로직은
  거의 그대로였다.
- **문서 전이(`docs.transition`)처럼 원래 여러 문서를 한 번에
  받는 벌크 액션은 REST에서 "그 문서 하나"짜리 엔드포인트
  (`POST .../documents/:code/transition`)로 단순화**했다 - 웹 UI는
  실제로 한 번에 하나씩만 전이시키므로 벌크 계약을 그대로 노출할
  필요가 없었다(내부적으로는 여전히 `{state: {[code]: [to, from]}}`
  모양으로 조립해서 같은 핸들러를 호출한다).

**(6)(10) PR/커밋 diff 뷰어 전면 개편**: 기존엔 PR 상세에 통짜
patch 텍스트(`git diff` 원문)만 `<pre>`로 보여줬는데, 이번에
`components/DiffViewer.vue`(신규, PR/커밋 diff 페이지가 공유)로
바꿨다:
- 백엔드에 `backend/src/core/gitRepo.ts`의 `readFileAtRef`/
  `readBlobRawAtRef`(이미지 미리보기용 base64 data URL)/`diffCommit`
  (커밋 하나 대 그 부모)/`getApproxParentCommitId`(es-git `Commit`에
  parent 접근자가 없어 Revwalk로 그 커밋 다음 것을 부모로 근사 -
  머지 커밋처럼 부모가 여럿이면 "정확히 첫 부모"가 아닐 수 있다는
  한계를 알고 감수)/`listCommitsForPath`(특정 경로를 실제로 건드린
  커밋만, 브랜치 히스토리를 훑으며 커밋마다 그 부모와의 diff에 그
  경로가 있는지 직접 확인 - es-git에 그런 필터가 없어서)/
  `getCommitInfo`를 추가하고, `repoBrowse.ts`에 `repo.diffFile`/
  `repo.commitDiff`/`repo.commitInfo`/`repo.fileCommits` 액션으로
  노출했다(CLI/MCP `/api/actions`와 REST 둘 다).
- 파일 하나의 diff 계산(라인 단위, ±6줄 컨텍스트, 그 사이는 접어서
  "변경되지 않은 코드 보기" 버튼으로 펼치기)은 **백엔드가 아니라
  프론트엔드에서** 한다 - `frontend/src/utils/lineDiff.ts`(신규,

**그런데 이 수정 자체도 처음엔 전혀 적용되지 않는 2차 버그가 있었다**:
그 CSS 규칙 바로 위에 있던 설명 주석을 `/* ... */`(CSS 주석)로
시작해놓고 **닫을 때 실수로 HTML 주석 닫기 문법인 `-->`를 썼다**
(다른 곳에서 Vue 템플릿 HTML 주석을 많이 쓰다 보니 습관적으로
잘못 씀) - CSS는 `-->`를 주석 종료로 인식하지 않으므로 그 주석이
안 닫힌 채로 남아 있었다. 신기하게도 Vue의 scoped-CSS 컴파일러가
이 상태에서 `:deep()`를 실제 셀렉터로 전혀 변환하지 않고
(`.yiitap-source-view[data-v-hash] main.yiitap`가 아니라 `:deep(...)`
문자열이 그대로) 최종 CSS에 그대로 흘려보냈고, 그 결과물은 브라우저가
파싱 불가능한 문법이라 `document.styleSheets`에서 그 규칙 자체가
통째로 사라져 있었다(다른 정상 규칙들은 그대로 있었음) - `curl`로
Vite dev 서버가 실제로 내려주는 컴파일된 스타일 모듈
(`?vue&type=style&index=0&scoped=...&lang.css`)을 직접 읽어보고서야
`-->`가 그대로 남아있는 걸 발견했다. `*/`로 고치자 곧바로
`.yiitap-source-view[data-v-4cfd93c2] main.yiitap { flex-direction:
column; }`로 정상 컴파일됐고, 실기동에서 View/Edit 두 모드 전부(코드
탭 README, Documents Source View, Discussion "질문하기" 컴포저)
내용이 툴바 아래로 정확히 쌓이는 것을 확인했다.

**이번에 판단해 기록해두는 것**: 프론트엔드 CSS 버그를 "고쳤다"고
보고하기 전에 **`getComputedStyle`로 그 속성값 자체(여기선
`flexDirection`)를 직접 찍어 확인하는 것만으로는 부족하다** - 지난
라운드에도 관련 속성(`padding-inline`)은 실제로 검증했지만 진짜
원인(`flex-direction`)은 놓쳤다. `document.styleSheets`를 뒤져 내가
작성한 셀렉터가 **실제로 스타일시트에 규칙으로 존재하는지**까지
확인하는 습관이 이런 종류의(특히 `:deep()`처럼 컴파일 과정을 거치는)
버그를 훨씬 빨리 잡아준다.

### Q&A 계층 구조 - RecentQaFeed.vue에서 실제로는 회귀돼 있었다 (2026-09-21, 같은 날 후속)

설계자가 "Q&A 계층 구조가 빠져있다"고 다시 지적했다 - `DocumentDiscussion.
vue`(문서 화면에 끼워진 Discussion 패널)엔 이미 지난 라운드에 more
아이콘 + `DocumentThreadPage.vue`를 구현해뒀던 터라 처음엔 "이미 했는데"
싶었지만, 실제로 확인해보니 **`RecentQaFeed.vue`(Trackers 탭의
"RECENT Q&A")는 완전히 평평한 목록으로 남아 있었다** - 그리고 지난
라운드에 이 컴포넌트를 REST 전환하며 다시 쓰는 과정에서, **원래
있던 `parent_id` 표시(`· parent: {{ item.parent_id }}`)까지 실수로
빼먹고 안 옮겼다는 걸 발견**했다 - 계층 관계를 보여주던 유일한
단서를 오히려 후퇴시킨 것. 설계자가 실제로 매번 보는 화면(RECENT
Q&A 목록)에는 계층 구조가 전혀 안 보였으니 "빠져있다"는 지적이
정확했다 - 다른 화면(개별 문서의 Discussion)에 구현해뒀다는 사실이
변명이 되지 않는다는 걸 확인한 라운드.

`RecentQaFeed.vue`를 다시 고쳤다:
- 각 항목에 **부모 관계를 배지로 복원**했다 - 단순히 raw parent_id를
  보여주던 예전 방식 대신, `resolveByRawId`(자리 표시 kind 트릭)로
  부모의 실제 제목/타입까지 resolve해서 "↳ 질문: ..."/"↳ 답변: ..."/
  "↳ doc: ..." 처럼 사람이 읽을 수 있는 배지로 보여주고, 클릭하면
  그 부모의 스레드 페이지로 이동한다.
- `DocumentDiscussion.vue`와 동일하게 **자식이 있으면 more 아이콘**
  (`childCounts` - `docs.list({parentId})`로 배치 계산)을 side
  섹션에 붙였다 - 눌러도 `DocumentThreadPage.vue`로 바로 간다(항목
  자체를 누르면 여전히 "그 문서로 이동+스크롤", 아이콘을 누르면
  "이 항목의 자식들을 보여주는 스레드 페이지로 이동"으로 두 동작이
  분리된다, `@click.stop`으로 구분).

**이번에 판단해 기록해두는 것**: 같은 기능(Q&A 계층 표시)이 **여러
화면에 나뉘어 구현될 수 있는 경우, 하나에만 구현하고 "이미 했다"고
여기면 안 된다** - 설계자가 실제로 보고 있는 그 화면 기준으로
검증해야 한다. 또한 컴포넌트를 다른 이유(이번엔 REST 전환)로
다시 쓸 때는 **그 컴포넌트가 이미 갖고 있던 정보 표시(이번엔
parent_id 캡션)를 빠짐없이 옮겼는지 diff 수준으로 대조**해야
한다 - 새 요구사항을 구현하는 데 집중하다 기존 기능을 조용히
후퇴시키는 게 이번이 처음이 아니다(design-notes.md의 다른 "회귀"
기록들과 같은 패턴) - 기존 파일을 통째로 다시 쓸 때는 "무엇을
빼는지"를 의식적으로 점검하는 습관이 필요하다.

### PR 설명 수정 기능 (pr.update) 추가 (2026-09-21, 같은 날 후속)

액션이 없어서 PR 생성 시점 이후엔 설명이 읽기 전용이었던 제약을 없앴다.

- `backend/src/core/pullRequests.ts`의 `prUpdate(payload, ctx)` - WRITE
  멤버십 필요, `title`/`description` 중 하나 이상 필요, **PR이 `open`

  보이면 오해를 부른다는 기존 판단을 그대로 유지 - 다른 상태면 거절).
  `backend/src/api/actions.ts`(`"pr.update"` 등록)/`backend/src/api/
  rest.ts`(`PATCH /projects/:projectId/pull-requests/:id`, 자원
  본문을 그대로 200 응답 - 다른 REST 엔드포인트와 동일 패턴)/`cli/src/
  index.ts`(`registerActionCommands("pr", [...])`에 `"update"`
  추가)/`mcp/src/server.ts`(`mutationActions`에 `"pr.update"` 추가)
  네 경로 전부에 노출했다 - CLI/MCP는 `docs.*` 등과 동일하게 그 자리에
  한 줄 추가하는 것만으로 자동 배선되는 기존 패턴(`registerActionCommands`/
  `mutationActions` 배열) 덕에 변경이 아주 작았다.
- 프론트엔드는 `PullRequestsTab.vue`의 설명 뷰어를 항상 `read-only`로
  고정하던 것에서, **`selected.state !== 'open'`일 때만 `read-only`**로
  바꿨다 - `MarkdownSourceView`가 이미 갖고 있던 view/edit 토글+저장
  버튼(문서/README와 동일한 컴포넌트)을 그대로 재사용했을 뿐, 새
  UI를 만들지 않았다.

**검증**: `backend`/`cli`/`mcp`/`frontend` 4개 패키지 전부 `tsc
--noEmit` 클린. REST(`PATCH`)로 open 상태 PR의 설명을 실제로 바꾸고
그 응답에 반영되는 것 확인, 그 다음 PR을 닫고 다시 같은 요청을
보내 `422` + "closed 상태인 PR은 수정할 수 없습니다" 메시지로
거절되는 것 확인. `/api/actions` + `X-Cnw-Channel: agent`(CLI/MCP
경로)로도 같은 액션이 그대로 동작하는 것 확인. 실제 브라우저에서
PR 하나를 열어 "편집" 버튼 → 설명 수정 → "저장" → 뷰 모드로
돌아오며 새 내용이 보이는 것, 그 다음 API로 직접 재조회해 서버에
실제로 저장됐는지 확인, PR을 닫은 뒤 같은 화면에 "편집" 버튼 자체가
사라지는 것까지 확인.

### Admin-per-project를 DB 제약으로도 강제 (2026-09-21, 같은 날 후속)

Phase 1 스캐폴딩 때부터 "Admin은 프로젝트당 1명은 애플리케이션
레이어에서만 검증, Prisma로 부분 unique index를 표현하기 까다로워
TODO로 남김"(`backend/src/core/membership.ts` 상단 주석)이라고 미뤄뒀던
항목을 이번에 실제로 마무리했다.

**먼저 실제로 이 불변식이 지금 코드에서 깨질 수 있는지부터 확인**했다
(`backend/src/core/projects.ts` 전수 조사) - ADMIN role이 쓰이는
자리는 딱 셋: (1) `projectCreate`가 생성자에게만 ADMIN을 부여(프로젝트당
멤버십이 이거 하나뿐이니 항상 유일), (2) `projectInvite`가
`role !== "READ" && role !== "WRITE"`면 명시적으로 거부해서 초대로는
ADMIN을 절대 못 준다, (3) `projectTransfer`가 **한 `$transaction`
안에서 기존 Admin을 WRITE로 내리고(먼저) 새 Admin을 올리는(그다음)**
순서로 실행돼 두 행이 동시에 ADMIN인 순간이 없다 - 즉 **현재 코드
경로만으로는 이 불변식이 실제로 깨질 수 없었다**. 그래도 DB 제약을
추가하기로 한 이유: 코드 경로가 안전한 것과 "앞으로 새 코드가 실수로
이 불변식을 깰 수 없다"는 것은 다른 얘기이고(예: 나중에 관리자 승급
API를 하나 더 만들다가 실수하면), 애플리케이션 버그를 DB 에러로
즉시 잡아내는 편이 훨씬 싸다.

- **Prisma 스키마 DSL은 부분(partial) unique 인덱스를 표현할 수
  없다** - `@@unique`는 항상 테이블 전체에 대해 걸리므로 "role이
  ADMIN인 행만" 조건을 못 넣는다. `npx prisma migrate dev
  --create-only`로 빈 마이그레이션을 만들고 그 `migration.sql`에
  직접 `CREATE UNIQUE INDEX ... ON "ProjectMembership" ("projectId")
  WHERE ("role" = 'ADMIN')`를 써넣었다(`backend/prisma/migrations/
  20260921025909_admin_per_project_unique/`) - READ/WRITE는 여전히
  프로젝트당 여러 명 가능하고, 기존 `@@unique([projectId,
  accountId])`도 그대로 유지된다.
- 적용 전에 **기존 데이터에 이미 이 불변식을 어긴 행이 있는지부터
  확인**했다(있으면 `CREATE UNIQUE INDEX`가 그 자리에서 실패한다) -
  `SELECT "projectId", COUNT(*) FROM "ProjectMembership" WHERE
  role='ADMIN' GROUP BY "projectId" HAVING COUNT(*) > 1`로 위반 0건
  확인 후 `prisma migrate deploy`로 적용.
- **알려진 트레이드오프(다음에 이 스키마를 또 건드릴 사람을 위해
  기록)**: 이 인덱스는 `schema.prisma`에는 전혀 선언돼 있지 않다
  (DSL이 못 하므로) - 그래서 나중에 `prisma migrate dev`로 새
  마이그레이션을 또 만들 때, Prisma가 "마이그레이션 히스토리를 전부
  재생한 shadow DB"와 "schema.prisma"를 diff하면서 이 인덱스를
  "schema.prisma엔 없는데 DB엔 있는" drift로 착각해 **그걸 지우는
  `DROP INDEX`를 새 마이그레이션에 자동으로 끼워 넣을 수 있다** -
  다음에 `prisma migrate dev`가 생성한 마이그레이션 SQL에 이
  인덱스를 지우는 줄이 보이면 그 줄만 지우고 진행할 것(마이그레이션
  자체를 취소하지 말 것 - 그 라운드의 실제 스키마 변경까지 같이
  날아간다).

**검증**: 마이그레이션 적용 후 애플리케이션 코드를 거치지 않고
raw SQL로 이미 Admin이 있는 프로젝트(`demo-project`)에 두 번째
ADMIN 행을 직접 INSERT 시도 → Postgres `23505`(unique_violation,
`Key ("projectId")=(demo-project) already exists`)로 실제 거부되는
것 확인. 그다음 **실제 `project.transfer` 흐름이 이 제약 아래서도
정상 동작하는지** 임시 계정+임시 프로젝트로 실제 라운드트립 확인
(가입 → 프로젝트 생성 → WRITE로 초대 → 수락 → `project.transfer`로
Admin 양도 → `project.members`로 기존 Admin이 WRITE로, 대상이
ADMIN으로 정확히 바뀐 것 확인 → 검증에 쓴 임시 프로젝트는
`project.destroy`로 정리, 임시 계정은 계정 삭제 기능이 아직 없어
프로젝트 없이 남겨둠).

### 프로젝트별 웹 접속 path를 /{생성자}/{project id}로 전환 + project id를 생성자별 유일로 재정의 (2026-09-21, 같은 날 후속)

설계자가 두 가지를 연달아 요청했다: (1) 프로젝트별 웹 접속 path를
`/{프로젝트 생성자의 login명}/{프로젝트 id}`(및 그 아래 모든 경로)로
바꿀 것(GitHub의 `/{owner}/{repo}` 스타일), (2) project id는 전역
유일이 아니라 **설계자(생성자)별로 유일**해야 한다 - 설계자 A가 `pA`
라는 프로젝트를 가졌어도 설계자 B가 똑같이 `pA`라는 id로 자기
프로젝트를 만들 수 있어야 한다. 두 요청이 사실상 하나로 합쳐진다 -
(1)의 두 번째 URL segment가 바로 (2)가 재정의하는 그 "project id"다.

**이 라운드가 진행되던 도중 설계자가 (2)를 추가로 요청**했다(원래는
(1)만 진행 중이었다) - 이미 URL scheme을 `/:owner/:projectId`로 바꾸는
작업을 반쯤 마친 상태에서 받았는데, 다행히 뒤엎을 필요는 없었다(owner
segment 자체는 그대로 필요했고, 그 안의 projectId가 "전역 유일"에서
"owner 범위 유일"로 의미만 바뀌는 것이었기 때문). 다만 project id가
더는 전역 유일이 아니게 되면서 그동안 `Project.id`(하나의 문자열)를
그대로 CLI 설정 파일/`/api/actions` payload/REST 경로/DB FK 전부에서
공유해 쓰던 설계 전체가 흔들리는 훨씬 큰 변경이 됐다.

**판단 - 내부 surrogate PK를 그대로 두고, "owner+slug -> 내부 PK" 변환을
진입점 한 곳에만 둔다**: `Project.id`(cuid)는 손대지 않고 여전히
전역 유일한 내부 PK로 남겨 Document/PullRequest/Message/Webhook/
RememberItem/ProjectMembership/ProjectInvite 등 **기존 관계 테이블은
전혀 스키마를 안 건드렸다**. 대신 `Project.slug`(설계자가 직접 고르는
문자열, `@@unique([creatorAccountId, slug])`)를 새로 추가해 "밖에서
부르는 project id"로 삼았다. `backend/src/core/projectResolve.ts`의
`resolveProjectId(owner, slug)`가 owner username -> creatorAccountId ->
`(creatorAccountId, slug)` 조합으로 실제 내부 PK를 찾아주는 유일한
통로이고, 이걸 `api/actions.ts`의 `dispatch()`와 `api/rest.ts`의
`web()` - CLI/MCP와 WEB UI 각각의 유일한 진입점 - 딱 두 곳에서만
호출해서, payload에 `owner`+`projectId`(slug)가 같이 오면 그 자리에서
`projectId`를 실제 내부 PK로 바꿔치기한다. **이 판단 덕분에 지금까지
있던 액션 핸들러(`core/documents.ts`/`repoBrowse.ts`/`pullRequests.ts`/
`messages.ts`/`webhooks.ts`/`remember.ts`/`templates.ts` 전부)는
단 한 줄도 안 고쳤다** - 그 핸들러들은 지금까지처럼 `payload.projectId`
를 "이미 유일하게 식별된 값"으로 그대로 받는다, owner/slug 개념
자체를 몰라도 된다. `project.create`만 예외로 실제로 고쳤다 - 이제
호출자가 `id`(원하는 slug)를 직접 골라 보내야 하고, `creatorAccountId`
범위에서 중복이면 거절한다(`SLUG_PATTERN`으로 영문/숫자 시작+영문/
숫자/-/_ 1~64자 형식도 검증).

**설계 시점에 판단해 기록해두는 것(다음 라운드 참고)**:
- **URL의 owner segment는 "장식"일 뿐 검증하지 않는다** - `/{누구든}
  /{projectId}`처럼 owner 문자열 자체는 그 프로젝트의 실제 생성자와
  달라도 서버는 신경 쓰지 않고 owner+projectId 조합으로 조회해서
  틀리면 그냥 404(프로젝트 없음)를 준다. GitHub처럼 "잘못된 owner로
  접근하면 정확한 owner로 redirect"하는 정합성 기능은 이번 라운드
  스코프 밖으로 남긴다(요청받은 건 "path를 이 형태로 바꿔라"였지
  "잘못된 owner를 정정해라"가 아니었다).
- **project.transfer 이후에도 owner segment는 안 바뀐다** - owner는
  "생성자"(`creatorAccountId`, 영구)를 가리키지 Admin(양도로 바뀔 수
  있음)을 가리키지 않는다 - "웹 URL이 Admin 양도 때마다 바뀌면
  북마크/CI 설정이 깨진다"는 판단.
- **CLI 홈 설정 캐시 키에 owner를 추가하면서 4단 중첩이 됐다** - 실제
  로는 이 값(`{endpoint, apiKey}`)이 같은 architectId면 owner/projectId와
  무관하게 항상 같은 값이라 이 중첩 자체가 (설계 처음부터) 다소
  과한 정규화였다는 걸 이번에 알아챘지만, 이번 라운드 스코프(URL/project
  id 변경)에 집중하려고 그 구조 자체를 단순화하는 건 손대지 않았다 -
  필요해지면 다음 라운드에 architectId 하나로만 캐시하도록 단순화할 수 있다.

**검증**: `backend`/`shared`/`cli`/`mcp`/`frontend` 5개 패키지 전부
`tsc --noEmit`(프론트는 `vue-tsc`) 클린. 마이그레이션 적용 전 기존
데이터에 백필 대상 문제가 없는지 확인 후 적용, `demo-project`가
`admin` 소유로 정확히 조회되는 것 확인. **핵심 시나리오를 실제로
재현**했다 - 계정 `admin`과 새로 만든 `designer-b` 둘 다 각자
`pA`라는 id로 프로젝트를 생성(둘 다 성공, `POST /projects` 201),
`admin`이 `pA`를 또 만들려 하면 거절(422, 같은 owner 안에서만
중복 검사), `GET /projects/admin/pA`와 `GET /projects/designer-b/pA`가
각각 다른 프로젝트를 정확히 돌려주는 것, `admin`이 `designer-b`의
`pA`를 읽으려 하면 멤버십 없음으로 거절(422)되는 것, 존재하지 않는
owner로 조회하면 404로 깔끔히 실패하는 것까지 curl로 직접 확인.
실제 브라우저에서 `/admin/pA/code`로 진입해 About/Contributors/탭
전부 정상 렌더링, `/admin/pA/documents/new`에서 실제로 문서를
만들어 `POST /api/projects/admin/pA/documents`가 201로 성공하고
목록 화면(`/admin/pA/documents`)에 반영되는 것까지 네트워크 탭으로
확인. 검증에 쓴 두 `pA` 프로젝트는 `project.destroy`로 정리.

### Q&A 계층 구조 - 표시는 있었지만 "만들 방법"이 아예 없었다 (2026-09-21, 같은 날 후속)

설계자가 다시 지적했다: "Q&A와 opinion들은 분명 계층 구조라고 말했었는데,
계층 구조가 빠져있네." 지난 라운드에 이미 more 아이콘 + `DocumentThreadPage.vue`
(자식 항목 표시+재귀 드릴다운) + `RecentQaFeed.vue`(부모 배지+more 아이콘)
까지 구현하고 실기동으로 검증까지 마쳤던 터라 "또 빠뜨렸나" 싶어 먼저
**직접 재현**해봤다 - 놀랍게도 표시 자체는 여전히 정상 동작했다(RECENT
Q&A 탭의 배지/more 아이콘, `/admin/demo-project/thread/QU-VWOBXD0M`
드릴다운 전부 그대로 살아있음, 스크린샷으로 확인). 그런데 실제 진짜
문제를 찾았다: **`DocumentThreadPage.vue`가 순수 읽기 전용이었다** -
자식 항목을 보여주기만 할 뿐, 그 페이지 안에서 질문/의견을 새로
남기거나 질문에 답할 방법이 전혀 없었다. 즉 **웹 UI만으로는 계층을

(질문→답변→재질의)은 전부 이번 세션 검증 중에 curl로 직접 만든
테스트 데이터였다. 설계자 입장에서는 "계층 구조를 보여준다"는 기능
자체가 UI에 실질적으로 없는 것과 마찬가지였다 - 표시 코드가 있다는
사실이 변명이 되지 않는다(이전 라운드의 RecentQaFeed.vue 교훈과

- 자식 목록(`children`, `docs.list({parentId})`로 타입 무관하게 전부
  조회)과 재귀 more 아이콘 로직은 그대로 유지했다 - 이게 있어야 방금
  단 답변/재질의가 바로 "자식 항목" 목록에 나타난다.

**처음에 시도했다가 되돌린 접근**: 처음엔 `DocumentThreadPage.vue`가
`DocumentDiscussion.vue`를 `parent-code="item.code"`로 그대로 끼워
넣으면 컴포저를 공짜로 얻을 수 있을 거라 생각했다 - 하지만 실제로
껴보니 **item이 이미 답변을 가진 질문일 때, 그 답변이 화면에서 사라졌다**.
`DocumentDiscussion.vue`의 데이터 모델은 "이 문서에 달린 question들 +
각 question에 달린 answer 하나"를 한 카드로 묶어서 보여주는
구조라(PR 리뷰 코멘트 스타일), `parentCode`로 넘긴 항목 자신의 답변
(=parentCode 자신이 question이고 그 직접 answer)은 애초에 이 모델이
표현하는 범위 밖이다(그 컴포넌트는 "parentCode에 달린 question/opinion
목록"만 다루지 "parentCode 자신의 답변"은 안 다룬다) - 반면 기존
`DocumentThreadPage.vue`의 손으로 짠 `docs.list({parentId})` 조회는
타입을 안 가리므로 답변도 자연스럽게 "자식"으로 잡혔었다. 재사용으로
코드는 줄일 수 있었지만 이 케이스에서 실제로 회귀가 생기는 걸 실기동
확인 중에 발견하고, 컴포저 부분만 `DocumentDiscussion.vue`와 같은
패턴으로 새로 작성하는 쪽으로 되돌렸다.

**검증**: `vue-tsc` 클린. 실제 브라우저에서 `/admin/demo-project/
thread/QU-VWOBXD0M`(agent가 만든 질문, 이미 답변 "ㄹㄹ" 있음) 진입 -
"답변 작성" 버튼은 안 보이는데(이미 답변 있음, 올바름) "재질의하기"는
보이는 것 확인 → 실제로 "재질의하기"로 새 질문("재질의 테스트")을
등록 → 자식 항목이 1개에서 2개로 늘어나는 것, RECENT Q&A 탭에 그
새 항목이 "↳ 질문: 디자인 관련 질문" 배지와 함께 나타나는 것까지
확인 → 검증에 쓴 재질의는 `docs.transition`(discard)으로 정리.
설계자가 요청 원문에 "Q&A와 opinion들"이라고 opinion을 명시적으로
짚은 만큼, **opinion 자신에게 opinion을 중첩**하는 것도 별도로
확인했다 - 기존 opinion(`OP-0S5XFT0B`, 자식 0개)의 스레드 페이지에서
"의견 남기기"로 새 opinion을 등록 → 자식 항목이 0개에서 1개로
늘어나는 것 확인 → 정리.

### "모든 페이지에서" 검증하다가 발견한 진짜 버그 - answerEditorRef가 처음부터 배열이었다 (2026-09-21, 같은 날 후속)

설계자가 이어서 요청했다: "Document 뿐만 아니라 Q&A와 opinion이
달려있는 모든 페이지에서 이걸 적용해야해." `DocumentDiscussion.vue`는
`DocTypeWorkspace.vue`에 무조건(타입 안 가리고) 끼워져 있어서
Documents/Plans/Issues/Trackers/Tests 다섯 화면 전부가 이미 같은
컴포넌트를 공유한다는 걸 코드로 먼저 확인했다 - 즉 위 수정
(DocumentThreadPage.vue의 컴포저)은 이미 전부에 적용돼 있어야
맞았다. 그래도 "이미 그렇다"고 말로만 답하지 않고 다섯 화면을
전부 직접 열어 실기동으로 확인했다:

- **Plans**(`UI 디자인 계획`의 opinion `OP-0S5XFT0B`) - 스레드
  페이지의 재질의하기/의견 남기기 정상 동작.
- **Issues**(`Test issue`의 question `QU-ZKD41M9S`) - 스레드
  페이지에서 실제로 재질의 등록 → 자식 0→1 확인.
- **Trackers**(기존 데이터에 tracker가 하나도 없어서 agent 채널로
  검증용 tracker 하나를 직접 만들었다) - Discussion 패널에서
  agent 질문에 "확인함"→"답변 작성" 흐름을 테스트하다가 **진짜
  버그를 발견**했다: **"등록하기"를 눌러도 아무 일도 안 일어났다**
  (로딩 스피너만 무한히 돔, 에러 메시지도 안 뜸). 콘솔을 열어보고서야
  원인을 확인 - `Uncaught (in promise) TypeError:
  answerEditorRef.value?.getMarkdown is not a function`.

**근본 원인**: `DocumentDiscussion.vue`의 답변 작성 컴포저
(`<MarkdownSourceView ref="answerEditorRef">`)가 `v-for="item in
thread"` **루프 안**에 있었다 - Vue는 v-for 내부에서 같은 이름의
`ref`를 항상 **배열**로 모은다(Vue 공식 문서에 명시된 동작). 그런데
`submitAnswer()`는 `answerEditorRef.value?.getMarkdown()`처럼 단일
객체인 것처럼 호출하고 있었다 - 실제로는 배열이라 `.getMarkdown`이
없어서 항상 예외를 던졌고, 이게 async 함수 안에서 uncaught promise
rejection으로 조용히 사라져 사용자에게는 그냥 "아무 반응 없음"으로만
보였다. **질문하기/의견 남기기 컴포저는 v-for 밖(스레드 목록
다음의 독립 블록)에 있어서 이 버그가 없었다** - 그래서 그동안의
검증(이번 세션 포함 여러 라운드)에서 재질의하기/의견 남기기는
매번 정상 동작했고 유독 "답변 작성"만 아무도 눈치 못 채고 있었다 -
docs.get/list 응답을 봐서는 절대 알 수 없는, 순수 프론트엔드
런타임 버그라 서버 로그에도 전혀 안 남는다.

이 버그는 **이번 세션에서 처음 만들어진 게 아니라 훨씬 이전
라운드("질문하기/답변 작성/의견 남기기를 다이얼로그에서 인라인
컴포저로 바꾼 라운드")부터 있었을 가능성이 높다** - `DocumentDiscussion.vue`
가 그 이후로 REST 전환/owner 리팩터 등 여러 번 다시 쓰였지만
`answerEditorRef` 관련 로직 자체는 그대로 옮겨 다녔을 뿐이다. 즉
"답변 작성" 버튼은 이 세션에서 실제로 클릭해서 등록까지 확인한 적이
**단 한 번도 없었다** - 매번 "재질의하기"/"의견 남기기"만 확인하고
"답변 작성 버튼이 보인다"까지만 확인한 뒤 넘어갔었다(버튼이
보이는 것과 실제로 동작하는 것은 다르다는 걸 이번에 값비싸게
배웠다).

**고친 것**: `answerEditorRef`의 타입을 `ref<MarkdownSourceViewRef
| null>(null)`에서 `ref<MarkdownSourceViewRef[]>([])`로 바꾸고
`answerEditorRef.value?.[0]?.getMarkdown()`으로 접근한다 -
`answeringCode`가 한 번에 최대 하나만 가리키므로 이 배열엔 항상
0개 또는 1개만 들어있다.

**검증**: `vue-tsc` 클린. 버그 재현 후(같은 Trackers 화면에서 같은
조작 반복 - 콘솔에서 정확히 같은 에러 확인) 수정 → **같은 화면에서
다시 시도해 실제로 답변이 등록되는 것**(`architect의 답변` 카드로
표시)까지 확인. Documents/Plans/Issues 세 화면도 다시 열어 Discussion
패널이 정상 렌더링되는 것(이 화면들은 애초에 답변 작성 흐름까지
직접 재현하진 않았지만, 코드 경로가 100% 동일한 컴포넌트이므로
Trackers에서의 수정이 그대로 적용된다) 확인. 검증에 쓴 tracker와
그 Q&A는 이미 답변이 달려 "해소된" 상태라(질문자 본인만, 미해소
상태에서만 discard 가능한 규칙과 안 맞음) 지우지 않고 다른 데모
Q&A(디자인 관련 질문 등)와 같은 방식으로 남겨뒀다 - 다른 테스트로
만든 이슈 질문(`QU-8MRRHMFB`)은 discard로 정리.

**이번에 판단해 기록해두는 것**: "버튼이 보인다"는 "기능이 동작한다"의
증거가 아니다 - 특히 `v-for` 안에 있는 템플릿 `ref`는 컴파일도
타입체크도 통과하고 화면에도 정상적으로 그려지지만, 실제로 상호작용
(누르기)해보기 전까지는 런타임 오류가 절대 드러나지 않는다. 이후
컴포저류 UI를 검증할 땐 "버튼이 보인다"에서 멈추지 말고 반드시
"실제로 눌러서 등록/저장까지 끝까지" 확인해야 한다.

### Q&A 카드 중복 제거(`DiscussionItemCard.vue`) + PR/DocTypeWorkspace 통합 여부 결정 (2026-09-22)

지난 "프론트엔드 UI 일관성 정리" 라운드(PL-PLANFEUI)에서 두 항목을
회귀 이력이 있는 민감한 영역이라며 별도 조사로 미뤘었다 - 이번 라운드가
그 후속이다. Explore 에이전트 둘로 각각 조사하고, `DocumentDiscussion.vue`/
`DocumentThreadPage.vue`는 내가 직접 전체를 다시 읽어 교차 확인했다.

**결정 1 - `PullRequestsTab.vue` ↔ `DocTypeWorkspace.vue` 통합은 하지
않는다.** 겉모습(리스트+상세 분할 패널)만 비슷하고 실제로는 API/데이터
모델이 근본적으로 다르다 - `DocTypeWorkspace`는 `api.listDocuments`/
`getDocument`/`transitionDocument`/`tagDocument`를 직접 호출하는
`docs.*` 전용 컴포넌트인데, PR은 `api.listPullRequests`/`getPullRequest`/
`mergePullRequest`/`closePullRequest`라는 별개 액션군을 쓰고 태그/의존성
정렬 개념 자체가 없으며 우측 패널도 파일 트리+`DiffViewer`가 필요하다.
억지로 합치려면 `DocTypeWorkspace` 내부의 하드코딩된 API 호출을 전부
주입식 콜백/슬롯으로 바꿔야 하는데, 이는 지금 이 컴포넌트를 쓰는 4개
탭(Documents/Plans/Issues/Trackers·Tests)의 검증된 동작(특히 `related`/
`dependsOn` 교차 탭 이동, etag 태그 로직)을 건드리는 위험을 감수하는
것 - 얻는 건 PR 탭 하나와 공유하는 약 60줄의 상용구뿐이라 리스크 대비
이득이 작다. `PullRequestsTab.vue`는 지금 구조 그대로 유지한다.

**결정 2 - `DiscussionItemCard.vue` 추출은 실행한다.** 네 곳의 카드
렌더링(Discussion의 메인 항목/중첩 답변, ThreadPage의 focal item/child)
은 공통 골격(타입뱃지+제목 | 상태뱃지+아바타+more메뉴, 마크다운 본문,
에러 줄)은 동일하지만 more 메뉴 항목/게이팅 조건은 넷 다 다르므로,
**렌더링 단위(카드)만 추출하고 게이팅 로직/데이터 계층(thread/children
계산)은 각 파일에 그대로 뒀다** - 과거 `DocumentThreadPage`가
`DocumentDiscussion` 전체를 통째로 재사용하려다 실패한 교훈(위 "표시는
있었지만..." 라운드) 그대로. 컴포저(답변 작성/재질의하기/의견 남기기)도
카드 밖(메인/focal 카드의 기본 슬롯 또는 페이지 레벨)에 그대로 둬서,
`v-for` 안에서 `v-for`마다 중복 렌더링되는 실수를 피했다.

`DocumentDiscussion.vue`의 `answerEditorRef`가 `v-for` 안에 있어
배열로 수집된다는 것(위 "answerEditorRef가 처음부터 배열이었다" 라운드
버그) - 컴포저를 슬롯으로 옮겨도 `v-for`는 여전히 부모 템플릿에 있으므로
이 배열 처리는 그대로 뒀다. 실제로 "질문하기" → "답변 작성" → "등록하기"
전체 경로를 브라우저로 직접 클릭해 새 답변이 실제로 생성/표시되는 것까지
확인했다(과거 정확히 이 경로가 조용히 실패했던 자리).

**발견·수정한 버그**: `DocumentDiscussion.vue`의 중첩 답변 카드는
`markAnswerRead`/`markAnswerDone` 실패 시 `actionError[answer.code]`에
에러를 쓰는데, 기존 템플릿의 에러 표시 줄은 `actionError[item.code]`
(메인 항목 것)만 보여주고 있었다 - **중첩 답변 액션이 실패해도 화면에
아무 표시가 안 되던 진짜 버그**. 각 카드 인스턴스가 자기 `error` prop만
보도록 배선하면서 자연히 고쳐졌다.

**의도적으로 같이 고친 것**: `DocumentThreadPage.vue`엔 중복 클릭 방지
(`busy`) 가드가 아예 없었다(`DocumentDiscussion.vue`엔 있었음) - 정확히
이번에 옮기는 그 클릭 핸들러들이라 위험이 거의 없어서 같이 추가했다.

**의도적 UX 변화(기록)**: 메인/focal 항목의 에러 줄이 기존엔 카드 맨
아래(중첩 답변/컴포저 다음)에 떴는데, 새 카드 구조에서는 본문 바로
아래(중첩 답변/컴포저보다 위)로 옮겨졌다 - 항목 자신의 에러가 그 항목
바로 밑에 뜨는 게 더 자연스럽다고 판단해 의도적으로 그렇게 뒀다.

**검증**: `vue-tsc --noEmit` 통과. `git diff HEAD -- DocumentDiscussion.vue
DocumentThreadPage.vue | grep '^-'`로 삭제된 모든 줄이 카드/슬롯으로
이동했거나 의도적으로 삭제(죽은 `stateColor`/`kindLabel`/`kindColor`)/
의도적으로 고친 것(에러 위치, busy 가드)임을 확인. 브라우저로 답변
작성/등록, 중첩 답변 확인함/완료 처리(연쇄 전이로 질문도 done까지
확인), RecentQaFeed 하이라이트 스크롤, ThreadPage의 재질의하기 컴포저,
child 완료 처리까지 전부 실제 클릭으로 확인.

### notices 토스트 mojibake 버그 수정 (2026-09-22, 같은 날 후속)

위 라운드를 검증하던 중 우연히 발견한, 완전히 별개의 버그 - 액션 성공
시 뜨는 notices 토스트(예: `[QU-xxxx]에 질의가 등록되었습니다.`)가
한글 부분만 깨진 문자(mojibake)로 표시됐다. 설계자가 즉시 고쳐달라고
요청해서 이 라운드에서 바로 처리.

**근본 원인**: REST 경로(`api/rest.ts`)는 notices를 응답 바디가 아니라
`X-Cnw-Notices` 헤더에 "JSON을 base64로 인코딩"해서 싣는데, 백엔드는
`Buffer.from(JSON.stringify(notices), "utf-8").toString("base64")`로
올바르게 UTF-8 인코딩하고 있었다. 문제는 프론트(`frontend/src/api/
client.ts`의 `surfaceNoticesFromHeader`)가 이걸 그냥 `atob(header)`로
디코딩한 것 - **`atob()`는 브라우저 표준 동작 그대로 "바이트 하나당
문자 하나"인 바이너리 문자열만 돌려준다**(버그 아님, 원래 그런
함수). 한글처럼 UTF-8에서 한 글자가 여러 바이트인 문자는 그 바이트들이
그대로 각각 다른 UTF-16 코드유닛으로 취급돼 항상 깨졌다 - 순수 영문
notices였다면 절대 안 드러났을 클래스의 버그.

**수정**: `decodeBase64Utf8()` 헬퍼를 추가해 `atob()`의 바이너리
문자열을 `Uint8Array`로 바꾼 뒤 `TextDecoder("utf-8").decode()`로
다시 해석하도록 고쳤다(`frontend/src/api/client.ts`).

**검증**: 브라우저에서 직접 `fetch()`로 실제 REST 엔드포인트를 호출해
같은 헤더를 두 가지 방식(기존 `atob()` vs 새 `decodeBase64Utf8()`)으로
나란히 디코딩해봐서 기존 방식이 정확히 그 mojibake 패턴을 재현하고
새 방식이 올바른 한글을 내는 것을 직접 비교 확인. 이어서 `window.fetch`
를 몽키패치해 앱이 실제로 사용하는 코드 경로(SPA 내 탭 클릭으로 트리거)
로도 올바른 한글 notices(`[QU-8BXKR2W1]에 질의가 등록되었습니다.`)가
나오는 것까지 재확인. 이 버그를 재현하려고 만든 질문 6개는 전부
discard로 정리.

grep으로 `atob(` 사용처가 이 한 곳뿐임을 확인 - CLI/MCP가 쓰는
`shared/src/apiclient.ts`는 REST가 아니라 `/api/actions` 단일
엔드포인트를 쓰고 notices를 응답 바디에 그대로(JSON, base64 아님)
받으므로 이 버그와 무관하다.

### `DocTypeWorkspace` 필터 다이얼로그 - 분류/상태/키워드 검색 통합, URL 영속화 (2026-09-22, 같은 날 후속)

설계자 요청 두 건이 이어졌다: (1) "Documents에서 문서 분류별로 보는
기능과, 전체 분류를 모아 보는 기능이 필요해. 분류를 바꿀 땐, router
path에도 어떤 분류를 보고 있는지 반영되어야 뒤로가기 했을 때 혹은
새로고침 했을 때 이전 분류로 돌아갈 수 있어." (2) 곧바로 이어서 "'상태별',
'분류별' 보기 뿐만 아니라 키워드로 검색도 가능해야 하니, 탭 보단
다이얼로그를 띄워서 필터를 설정할 수 있도록 만들어야해." - 처음엔
`q-tabs`로 분류(kind)만 구현했었는데, 좁은 사이드바(~270px)에 6개
탭(전체+SP/RP/RM/QA/BT)이 들어가며 Quasar 기본 스크롤 화살표가 뜨는
문제가 있었고, 상태·키워드 두 축이 더 늘어나는 두 번째 요청 때문에
탭 구조를 버리고 다이얼로그로 전면 교체했다.

**구현 (`DocTypeWorkspace.vue`)**:
- 새 props: `kindLabels?: Record<string,string>`(분류 코드→한글 라벨),
  `states?: string[]`(그 타입이 가질 수 있는 상태 목록 - 빈 배열이면
  상태 필터 자체를 다이얼로그에서 숨김).
- `분류`/`상태`/`키워드 검색` 세 축을 각각 `route.query.kind`/
  `.state`/`.q`에 매핑 - **값이 없으면 쿼리 키 자체를 지운다**("전체"를
  리터럴 값으로 쓰지 않음, 기존 URL과의 하위 호환 유지).
- 필터 버튼 + 활성 필터마다 removable `q-chip`(분류/상태/검색 각각)을
  리스트 위에 표시. 다이얼로그는 draft 상태(`draftKind`/`draftState`/
  `draftQuery`)를 따로 두고 "적용"을 눌러야 실제 필터에 반영 - 여는
  순간 매 키 입력마다 재조회하지 않기 위해서다("초기화"는 draft만
  비우고 적용 전까지 URL/조회에 영향 없음, "취소"는 draft를 버리고
  닫기만 함 - 브라우저로 반복 확인, 실수로 다이얼로그를 닫아도 이미
  걸린 필터가 사라지지 않음을 확인).
- `load()`가 `searchQuery`가 있으면 `api.searchDocuments`(Meilisearch
  `q` + `type`/`kind`/`state` 구조적 필터), 없으면 기존
  `api.listDocuments`(+ `sort=dependency`)로 분기 - 백엔드
  `docs.search`가 `sort`를 지원하지 않으므로 "의존성 순 정렬" 토글은
  키워드 검색 중엔 숨긴다(`v-if="!searchQuery"`).
- 브라우저 뒤로/앞으로가기 대응: `route.query`의 세 키를 감시하는
  `watch`를 추가해 값이 실제로 바뀐 경우에만 내부 상태를 되돌리고
  재조회 - 새로고침 시에도 초기 `ref` 값을 `route.query`에서 읽어와
  복원.
- `select(code)`(related/dependsOn 태그 클릭, 목록 항목 클릭)는 이동
  대상 문서의 `type`이 지금 이 워크스페이스의 `type`과 같을 때만 현재
  필터 세 축을 새 경로의 쿼리로 그대로 실어 보낸다 - 다른 type(예:
  tracker에서 plan으로)으로 건너뛸 땐 그 필터가 그쪽에서 의미가 없으므로
  싣지 않는다. 같은 type 안에서 분류가 다른 문서로 이동해도(예:
  kind=SP 필터가 걸린 채 dependsOn으로 RP 문서로 이동) 필터는 유지된다
  - 이건 의도적: `kind` 쿼리는 "목록에 뭘 보여줄지"이지 "지금 보고 있는
  문서가 뭔지"가 아니므로, 상세 패널이 필터 밖의 문서를 보여줘도 목록
  자체는 그대로 필터링된 채 있는 게 맞다(실제 클릭으로 확인:
  `SP-R0FNGXX7?kind=SP` → dependsOn 태그 클릭 →
  `RP-M4P3H2S7?kind=SP`, 목록은 SP만 보이는 채 유지, 상세는 RP 문서
  정상 표시).
- 호출부 5곳(`DocumentsTab`/`PlansTab`/`IssuesTab`/`TrackersTestsTab`
  ×2)에 각 타입의 `documentRules.ts` 상태 어휘대로 `:states` prop 추가
  (doc: draft/review/active/done/discard, plan: added/read/done/
  discard, issue: open/closed, tracker: added/resumed/ended/canceled,
  test: added/discard). `DocumentsTab`에만 `:kind-labels`도 추가(다른
  4곳은 kind가 1개뿐이라 분류 선택 자체가 다이얼로그에서 숨겨짐 -
  `v-if="kinds.length > 1"`).
