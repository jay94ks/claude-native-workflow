# RV-00001 대시보드 좌측 패널 — 폴더 트리 대안 (상태/워크플로우 중심 + 필터/뱃지 보강)

설계자가 "폴더 뷰로 좌측 패널을 구성하는 것보다 더 나은 방식이 있는지
연구가 필요하다"고 요청해 진행한 조사. `tier1/tools/docs`, `tier2/dashboard`,
`tier3/dashboard` 세 대시보드가 전부 같은 컴포넌트(`tier2/dashboard/src/components/DocTree.vue`,
tier3는 이걸 그대로 import해서 씀)를 쓰고 있어 하나를 바꾸면 사실상
세 곳 모두에 영향을 준다 - 그만큼 신중하게 결정할 사안이라 바로
구현하지 않고 RV로 등록한다.

## 현재 상태 진단

`DocTree.vue`는 `docs/<타입 폴더>/` 구조를 그대로 미러링한다 - 폴더 =
문서 TYPE(spec/plan/decision/design/done/fix/logs/remind/reply/review/temp),
각 폴더를 펼치면 그 안의 문서가 배지(TYPE)+제목+`id · status`로
나열된다. 이 저장소 자신의 `docs/`로 실측한 결과: 문서 12개, 타입
폴더 11개 중 **7개가 비어 있다**(fix/logs/remind/reply/review/temp 등).
트리를 열어보면 절반 이상이 빈 폴더를 펼쳐보는 것부터 시작하게 된다.

더 근본적인 문제: 트리가 인코딩하는 축은 "타입"뿐이다. 그런데 이번
세션 QA 과정에서 실제로 필요했던 정보 - "지금 답변 대기 중인 게
뭔지", "이번 주에 뭐가 바뀌었는지", "검증에 문제는 없는지" - 는 타입
트리가 전혀 보여주지 못해서 전부 별도 탭(답변 대기/검증 버튼)으로
따로 붙여야 했다(이 세션에서 tier1/tier2/tier3 세 대시보드 모두에
동일하게 발생). 트리 자체가 "지금 뭘 봐야 하는가"에 답을 못 주고
있다는 신호로 본다.

## 방향 A. 상태/워크플로우 중심 뷰 (권장 - 큰 방향 전환)

폴더(타입) 대신 **설계자가 지금 뭘 해야 하는지**를 1차 그룹 기준으로
바꾼다:

```
▾ 답변 대기 (2)          ← DC/RV/FX 중 reply_pending
    ⚠ DC-00003  tier2/tier3 CLI npm 공개 배포 여부
    ⚠ RV-00001  대시보드 좌측 패널 ...
▾ 진행 중 (1)             ← status: draft/open (PL 진행 중, 미답변 DC/RV/FX)
    ▶ PL-00002  ...
▸ 최근 변경 (3)            ← git 커밋 이력 기준, 최근 N일/N건
▸ 완료/보관 (9)            ← DN, applied 처리된 DC/RV/FX (기본 접힘)
─────────────
  전체 문서 (검색 가능한 평면 목록으로)
```

각 항목은 여전히 TYPE 배지(SP/PL/DC/...)를 달고 있어 타입 정보를
잃지 않는다 - 바뀌는 건 "무엇을 기준으로 묶는가"뿐이다. `답변
대기`/`최근 변경` 그룹은 지금 별도 탭으로 떼어둔 `client.pending()`/
`client.changes()`를 그대로 재사용하면 되므로 백엔드 API 변경은
필요 없다(클라이언트에서 그룹핑만 다시 함) - `client.tree()`가
돌려주는 폴더 구조 대신, `all()`/`pending()`/`changes()`를 합쳐 상태별로
재분류하는 로직만 새로 짜면 된다.

**장점**: 지금 탭으로 흩어진 "봐야 할 것"이 좌측 패널 맨 위에 항상
보인다 - 세션 초반에 바로 눈에 띄어야 하는 정보(미답변 질문, 최근
변경)가 구조적으로 1순위가 된다. 문서 수가 늘어도 빈 카테고리가 안
생긴다(상태 그룹은 항목이 0개면 그냥 숨기면 됨).

**단점/리스크**: `docs/PROTOCOL.md`가 가르치는 사고방식 자체가 타입
분류(SP/PL/DC/...)인데, 좌측 패널의 1차 축이 타입이 아니게 되면 "SP만
쫙 보고 싶다" 같은 요청에 답하기 위한 타입 필터가 따로 필요해진다
(방향 B의 필터 칩을 여기 얹으면 해결됨 - 아래 "결합안" 참고). 세
대시보드가 컴포넌트를 공유하므로 한 번 바꾸면 전부 같이 바뀐다 - 먼저
한 곳(예: 이 저장소 자신이 쓰는 tier1, 또는 로컬 전용인 tier2)에
시험해보고 tier3까지 넓히는 단계적 롤아웃이 안전해 보인다.

## 방향 B. 타입 트리 유지 + 필터/뱃지 보강 (점진적, 리스크 낮음)

트리 구조 자체(타입별 폴더)는 그대로 두고, 지금 있는 구체적인
불편만 고친다:

1. **빈 폴더 기본 숨김** - 문서 0개인 타입 폴더는 펼침 목록에서 아예
   빼거나 접어둔다(지금처럼 7/11이 빈 폴더로 노출되는 걸 막음).
2. **폴더 헤더에 개수 배지** - `spec (4)`처럼 펼치지 않아도 구조가
   한눈에 들어오게.
3. **문서 행에 "주의 필요" 배지** - 그 문서가 답변 대기 중이거나
   (`reply_pending`) 최근 변경 큐(`changes`)에 걸려 있으면 트리
   안에서 바로 표시(방향 A의 "답변 대기"/"최근 변경" 그룹이 주는
   신호를 그룹을 안 바꾸고도 트리 위에 얹는 방식).
4. **상단 필터 칩** - `전체 · 진행중 · 완료 · 답변대기` 같은 칩으로
   트리에 보이는 항목을 즉시 좁힘(구조는 안 바뀌고 보이는 범위만
   바뀜).

**장점**: 지금 컴포넌트를 갈아엎지 않고 이어붙이는 구조라 구현/시각적
리스크가 낮고, 세 대시보드에 거의 그대로 이식된다. `docs/PROTOCOL.md`의
타입 중심 사고방식과 그대로 맞아떨어져서 배우는 비용이 없다.

**단점**: 근본적으로 "타입"이 여전히 1차 축이라, 방향 A가 주는
"지금 뭘 봐야 하는지 맨 위에 뜬다"는 효과는 필터/배지로 흉내만 내는
수준 - 필터 칩을 매번 눌러야 그 뷰가 나온다(기본값이 여전히 타입
트리 전체이므로).

## 결합안 (권장)

두 방향은 서로 배타적이지 않다 - 방향 A를 기본 뷰로 두되, 방향 B의
"타입 필터 칩"을 그 위에 얹으면 "SP만 보고 싶다"는 요구도 방향 A
안에서 해결된다. 단계적으로 가는 걸 제안한다:

1. **먼저 방향 B의 낮은 리스크 항목(빈 폴더 숨김 + 개수 배지 +
   주의 필요 배지)만 지금 있는 트리 위에 얹는다** - 코드 변경이
   작고 시각적 충격이 없어 QA 수정과 비슷한 단위로 바로 진행 가능.
2. **방향 A(상태/워크플로우 뷰)는 별도 PL로 설계해 tier1(이 저장소
   자신이 쓰는 대시보드)에서 먼저 시험한다** - 가장 리스크가 낮은
   대상(로컬 전용, 이 세션이 바로 점검할 수 있음)에서 먼저 써보고
   나서 tier2/tier3로 넓히는 편이 세 곳을 한 번에 바꾸는 것보다
   안전하다.
