# CLAUDE.md

이 프로젝트는 claude-native-workflow 시스템으로 관리된다. 문서/설계
기록은 파일이 아니라 이 시스템의 DB에 있고, `docs` CLI 또는 MCP 도구로만
읽고 쓴다 - 파일을 직접 만들거나 수정해서 설계 기록을 남기지 않는다.

## 반드시 지켜야 하는 일곱 가지 규칙

1. **추적 코드 명시**: 어떤 제안을 하거나 설계 내용을 작성할 때는 관련된
   문서/질의의 추적 코드(`XX-XXXXXXXX` 형식)를 정확히 인용한다. 예:
   "이 결정은 DC-A1B2C3D4에서..." 문서 제목만으로 가리키지 않는다.
2. **로컬 스크래치 사본은 git 커밋 금지**: `docs new`/`docs save`
   등에 넘기는 로컬 임시 파일은 정상적인 작업 방식이지만(지금 편집 중인
   문서를 로컬에 복사해 Edit 도구로 다듬은 뒤 다시 올리는 것), 이 사본을
   이 프로젝트의 git 저장소에 `git add`/`git commit`하지 않는다 - 문서의
   정본은 시스템 DB이고, 편집용 임시 파일이 소스 트리에 섞여 들어가면
   안 된다. 임시 디렉터리 등 git 추적 대상 밖에 둔다.
3. **코드 관계도는 실제로 기록한다**: 여러 파일을 가로지르는 탐색이라
   다시 파악하려면 비용이 드는 발견을 했으면(예: "이 버그가 세 파일에
   걸쳐 있다는 걸 확인했다") `docs relation add`로 기록하고, 새 탐색을
   시작하기 전엔 `docs relation list --q <키워드>`로 이미 기록된 게
   있는지 먼저 확인한다 - 사소한 한 줄짜리 조회까지 전부 남기는 감사
   로그는 아니다(정확한 기준은 Skill의 "코드 관계도" 절 참고). 현재
   체크아웃된 브랜치가 자동 감지되므로 별도 설정이 필요 없다.
4. **연관 소스/브랜치/칸반 카드도 실제로 연결·기록한다**: 어떤 문서가
   구체적으로 어떤 파일을 바꿨다고 서술하면 그 핵심 파일들을 `docs
   link-source`로 그 문서에 실제로 연결해둔다(이름 붙은 기능 브랜치에서
   작업했다면 `docs link-branch`도, `main`/`master`에 직접 커밋하는
   흐름이면 생략). 프로젝트에 칸반 컬럼이 있으면(`docs kanban-columns`)
   완료한 작업 단위마다 관련 문서를 `--refs`로 묶어 카드를 만들거나
   (`docs kanban-card-new`) 진행 상황에 맞게 옮긴다(`docs
   kanban-card-move`) - 코드 관계도와 같은 기준으로, 사소한 조사/조회
   까지 전부 기록하는 감사 로그는 아니다(정확한 기준은 Skill의 "연관
   소스코드"/"연관 브랜치"/"칸반 보드" 절 참고).
5. **별도 계획이 필요한 항목도 실제로 기록한다**: 아래와 같은 신호가
   보이면 지금 당장 처리하지 않고 `docs plan new`로 남겨둔다 - "이건
   별도로 계획을 잡아야겠다"는 판단, "나중에 처리한다"고 미뤄둔 것,
   앞으로 생길 것으로 예상되는 이슈/리스크, 설계자의 결정이 필요한
   사항(선택지가 여러 개라 AI 혼자 못 정하는 것), 이번 라운드에서 다
   못 끝내고 남은 사항 등. 제목/본문(Markdown)/관련 문서(`--refs`)를
   남겨둔다 - Document 체계와는 완전히 별개의 독립 엔티티
   (`PN-XXXXXXXX`)다(정확한 사용법은 Skill의 "계획" 절 참고).
6. **도구 호출은 요청 횟수와 응답 내용 둘 다 최소화한다**: `docs
   search`는 기본적으로 각 히트의 본문 전체를 그대로 돌려줘 응답이
   쉽게 비대해진다 - 특별히 본문 내용을 직접 읽어야 하는 게 아니라면
   `--codes-only`로 트래킹 코드만 받고, 실제로 내용이 필요한 결과만
   `docs get`/`docs read`로 이어서 조회한다(본문이 꼭 필요하지만
   전체까지는 아니면 `--lines <n>`으로 앞부분만). 특정 문서 안에서
   패턴/키워드 하나만 확인하려는 거면 전체 본문을 받는 대신 `docs
   grep <trackingCode> <pattern>`으로 그 부분만 짚어서 본다 - 다른
   명령도 마찬가지, 성공 여부나 존재 확인만 필요한 호출에서 응답
   본문을 불필요하게 그대로 출력에 남기지 않는다. 호출 횟수도 같은
   원칙으로 줄인다: 이미 확인한 목록/문서를 근거 없이 다시 조회하지
   않고, 여러 건을 다뤄야 할 땐 한 건씩 반복 호출하기 전에
   일괄(`bulk-*`/`*-batch`) 명령이 있는지 먼저 찾는다(예: 본문 여러
   곳 치환은 `docs patch-batch`, 여러 항목 상태 변경은 해당 도메인의
   `*-bulk` 명령).
7. **문서 간 링크(연관 문서)도 실제로 연결한다**: 여러 문서가 서로
   참고·인용 관계에 있으면(예: 보고서와 그 하위 챕터, 어떤 결정이
   다른 결정을 전제로 한다는 서술 등) `docs link <fromTrackingCode>
   <toTrackingCode>`로 실제로 링크를 만들어둔다 - 본문에 추적 코드만
   언급하고 링크를 안 만들면 "문서간 관계" 그래프(`docs doc-graph
   <projectId>`)에 그 연결이 나타나지 않는다. 중복 링크를 막는 DB
   제약이 없으므로, 새로 링크하기 전에 `docs get <trackingCode>`
   응답의 `linksOut`(이 문서가 링크한 문서)/`backlinks`(이 문서를
   링크한 문서)나 `docs links-out`/`docs backlinks`로 이미 연결돼
   있는지 먼저 확인한다.

## 기본 명령

```bash
docs auth login --api <서버 주소> --username <아이디>   # 최초 1회
docs list <projectId>                                    # 문서 목록
docs get <trackingCode>                                   # 문서 1건 조회(본문+연관 문서 코드)
docs new <projectId> <docTypeCode> --title <제목> --body <로컬 파일>
docs pending <projectId>                                  # 답변 대기 질의 목록
docs reply <questionTrackingCode> <답변 텍스트...>
```

전체 명령/MCP 도구 목록과 문서 타입/상태 흐름 설명은 Skill
(`.claude/skills/claude-native-workflow/SKILL.md`)을 참고한다.
